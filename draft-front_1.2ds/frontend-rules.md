# Правила разработки фронтенда (Vue 3 + TS + Vuetify)

Правила целевого стандарта для `draft-front_1.2ds`. Применяются при любой работе с фронтом. При конфликте с текущим кодом код приводится к правилам (рефакторинг).

## 1. Структура SFC

- **Порядок тегов**: строго `<script setup lang="ts">` → `<template>` → `<style scoped>`.
- **Одна задача на компонент**. Если в компоненте появилась вторая независимая задача (в форме — редактор списка, в карточке — диалог, в таблице — фильтры) или сложная вложенная разметка (панели в панелях, табы в табах, матрицы чекбоксов) — выделять дочерний компонент в подпапку рядом.
- Длина файла сама по себе не критерий: файл, делающий одну задачу, резать «по счётчику» нельзя. ~250 строк — сигнал перепроверить декомпозицию по задачам.

## 2. Разделение ответственности

- **Компонент** — только UI: состояние отображения (флаги модалок, `expandedPanels`), привязка данных, эвенты.
- **Логика вне компонента**: расчёты, валидация, работа со справочниками, вотчеры синхронизации, мутации глубоких объектов (`spec`) — выносить из `.vue`.
- Извлечённая логика живёт в подпапках своего модуля (`Service/`, `Dto/`, `Utils/`, `Constant/`, ...) или в модулях ядра (`Core/Engine`, `Core/UI`) в естественной для неё форме:
  - **доменная логика — класс-сервис в `Service/` модуля** (пример: `RuleValidationService`); файлов функций в `Service/` нет;
  - **`Utils/` — небольшой набор независимых stateless утилит**, у которых нет хозяина-класса (нет предметной области и роста; пример: `debounce`). Не «любая чистая функция домена». Расчёт удара, тик DOT, валидация спеки — не Utils. Группировка подпапками внутри допустима;
  - **value-класс — `Core/Engine/Value/`** (пример: `DateTime`, `DimensionalNumber`);
  - мелочь без роста — приватный метод сервиса-потребителя, не отдельный файл.
- **Склонность к ООП.** Логика по умолчанию оформляется классами: класс-сервис (`Service/`), спека-сервис, value-класс (`Value/`). В `Utils/` — только независимые мелочи (см. выше). При сомнении «класс или функция» выбирается класс. Связанное семейство функций одной предметной области — сигнал к классу (пример: интерпретация типа поля — класс-хендлер). «Мелочь без роста» живёт приватным методом сервиса-потребителя, не свободной функцией.
- **Спеки — классы-сервисы в `Service/` модуля** (подпапка по домену, напр. `Service/Spec/`): `*SpecService`, создающий и подготавливающий объекты спека (`createEmpty*`, `prune*`, `resolve*`). Конфигурация (манифесты полей, справочники типов) инъектируется в конструктор — тестируемость и подменяемость. Все константы конфигурации лежат в `Constant/` модуля и инъектируются в конструктор; приватных констант в Service-файлах не держим. Производные справочники (универсумы полей, выводимые из манифестов) живут в `Constant/` как обычные константы, но вычисляются из источника-манифеста, а не дублируются копией.
- **В корне модуля из файлов — только точки сборки**: `init.ts` и `routes.ts`; всё остальное — подпапки. **Папки — в единственном числе.** Если файлу не находится осмысленное место — это сигнал, что он неуместен в текущем виде.
- **Не более одного экспорта на TS-файл**: файл экспортирует не более одной сущности; родственные сущности группируются подпапками по логике, но каждая живёт в своём файле. **Исключения — только точки сборки модуля**: `init.ts` (фасады/реестры) и `routes.ts` (определения роутов, включая связку `routes` + `adminChildren`). `index.ts`-баррелей не создаём: компоненты и внутренние файлы импортируются по прямому пути.
- **Анатомия модуля**: иерархия `src/modules/{Группа}/{Модуль}/`. Группа объединяет модули по предметной области (Messages: Chat, Notifications; Roleplay: Rule, Space, Character, Game). Подпапки: `Interface/` (контракты сервисов), `Dto/` (контракты данных), `Enum/` (перечисления — string-literal union), `Service/` (классы; сервисные синглтоны — в `Service/Instance/`), `Constant/` (справочники), `Component/` (Vue-компоненты), `Mock/` (моки), `Utils/` (независимые stateless мелочи, с подпапками), `Store/`, `Page/`, `Composables/`, `__tests__/`. **Папки — в единственном числе.** Внутри любой подпапки допустимы подпапки по логической группировке. `init.ts` — если модуль отдаёт наружу сервисы/доменную логику, `routes.ts` — если есть страницы; минимальный модуль — Page + routes. Модули лежат внутри групп; на уровне группы — только сами модули (агрегирующий `routes.ts` группы допустим, пример: Roleplay). **Core — группа фундамента**: её модули Engine (инфраструктура и логика) и UI (переиспользуемые Vue-компоненты и UI-утилиты) доступны из любого модуля напрямую. **Разделение Engine/UI**: всё, что касается отображения (Vue-компоненты, UI-утилиты — напр. `debounce`), — в `Core/UI`; логика/инфраструктура — в `Core/Engine`. **Общий UI проекта живёт в `Core/UI`, а не в `Core/Engine`.** `Core/Engine` не импортирует `Core/UI` (ни типы, ни утилиты): зависимость направлена только UI → Engine. `Core/Engine` — обычный модуль с анатомией (`Dto/`, `Service/`, `Interface/`, `Mock/`, `Value/`, `Composables/`); value-классы — в `Core/Engine/Value/`. Generic-логика и generic-компоненты — это подпапки модулей Engine/UI, а не отдельные папки на уровне группы; появление новых модулей в Core (и других группах) — обычная практика. Перечень подпапок анатомии не закрыт — введение новой подпапки/паттерна это осознанное решение, применяется согласованно в модулях.
- **Композаблы — в корневой `Composables/` модуля**, с подпапками по логической группировке; в `Component/` композаблов не держим (там только Vue-компоненты). Композабл — для stateful-логики с реактивностью и/или жизненным циклом; независимая stateless-мелочь — в `Utils/` или приватная функция (YAGNI), композабл не ради паттерна. Кросс-модульные композаблы: отображение — в `Core/UI/Composables/`, инфраструктура — в `Core/Engine/Composables/`.
- **Сервисы через ServiceLocator**: API-сервисы модуля регистрируются в ServiceLocator через `init.ts` (`register`/`get`); доступ — только через фасады `getXxxApi()`, даже к своим. Импорт Service-реализации обходит централизованную подмену mock/real.
- **Сервисные синглтоны — в `Service/Instance/`**: класс сервиса живёт один на файл (`Service/XService.ts`); его готовый экземпляр — отдельный файл `Service/Instance/xService.ts` (один экспорт). НЕ в `init.ts` (тянет Vue-зависимости и ломает unit-тесты) и НЕ в файле класса (имена `XService`/`xService` различаются только регистром — коллизия на case-insensitive ФС, ошибка TS1149). `init.ts` при необходимости реэкспортирует синглтон.
- **Межмодульный доступ** — через публичные точки: `init.ts` (`get*` / `register*` / узкий composable-фасад, не реэкспорт `useXxxStore`), `Interface/`/`Dto/`/`Enum/`. Чужие `Service/`/`Component/`/`Constant/`/`Store/`/`Page/`/`Composables/`/`Utils/` не импортируем. **Исключение — Engine и UI**: весь модуль — публичный API фундамента. Auth и User — как прикладные. Импорт mock-фикстур между модулями допустим. Pinia только в своём модуле. Канон рёбер — `docs/tr/architecture.md`. Линтер: `powerscale/no-foreign-module-internals`.
- **Плагинные точки** (пример: Chat, профиль пользователя) — когда чужой прикладной модуль должен встроить в модуль-хост свой UI/логику, хост объявляет generic-контракт (`Interface/`) **без типов чужих прикладных модулей** и реестр в `init.ts` (`register`/`get`), а донор регистрирует вкладку через публичную точку хоста (вызов `register*` из своего `init.ts`); композиция — в `main.ts`. Хост не импортирует доноров (ни компоненты, ни их Dto). Стрелка «Chat → Character» на графе ложная: донор зовёт `register*`.
- **Моки — в `Mock/` модуля**: фикстуры и mock-API-имплементации — это in-memory источник данных / фейк-бэк, не сервисы; в `Service/` их не кладём.
- **Направление зависимостей.** Канон рёбер и CODE_GAP — `docs/tr/architecture.md` (не дублировать таблицу здесь). Core — фундамент; прикладные модули зависят от Core, не наоборот. `Core/Engine` не импортирует `Core/UI`. Rule не импортирует Space: `spaceId` / ревизия — проп, роут или inject-ключ, объявленный в Rule; Space только `provide`. Chat-хост не импортирует Roleplay; донор зовёт `register*` и может брать Dto сегмента чипа. Доменный справочник живёт в модуле-хозяине (формы типа урона — Rule, не Character).
- **Без дублирования**: готовая логика и компоненты переиспользуются; копирование — сигнал вынести в общее место.
- **Мутации глубоких объектов** — через функции-апдейтеры модуля, не inline-присваиваниями в компоненте: изменения трассируются и тестируются.
- **Статичные справочники** (опции селектов, конфиги, константы, манифесты) — в подпапку `Constant/` модуля, отдельными файлами; не в `<script setup>` и не в `Interface/`/`Dto/`. Внутри `Constant/` — подпапки по логической группировке при необходимости (например, `Constant/Ability/`, `Constant/Item/`).
- **Производные данные** — через `computed`, без пересчёта в шаблонах и методах.
- **Async-операции** — с состояниями загрузки/ошибки/повтора (паттерн F17); тихих провалов нет.
- **YAGNI**: не абстрагировать сверх текущей потребности.

## 3. Реактивность и TypeScript

- `props` не деструктурировать; при необходимости — только через `toRefs(props)`.
- **Pinia-сторы**: доступ к state/getters — через `store.xxx` (в шаблонах и computed) или `useStore()` в setup; это реактивно. Прямую деструктуризацию (`const { x } = store`) не использовать — теряется реактивность; если она нужна (локальные переменные в setup) — через `storeToRefs`.
- Типы импортировать явно: `import type { ... }`.
- Импорты — строго через алиас `@/`; относительные пути `../../` запрещены.
- **Запрет `any` / `as any`** в production-коде.
- **Типизация — слои по назначению**: контракты сервисов — `Interface/` (только контракты сервисов); контракты данных (интерфейсы-формы и дискриминированные юнионы) — `Dto/` модуля; перечисления — `Enum/` (**string-literal union, не настоящие TS-enum** — номинальная типизация ломает JSON-контракт). Каждый тип — отдельный файл (эталон: `Core/UI/Dto/ColumnDefinition.ts`), без свалок в `types.ts`; внутри `Dto/`/`Interface/`/`Enum/` — подпапки по назначению, не плоская куча. В этих папках — только типы, без констант и функций: справочные константы — в `Constant/` модуля, поведение — в классах `Service/`. **Именованные типы объявляются только в `Dto/`/`Interface/`/`Enum/`**; в файлах с кодом (`Service/`, `Value/`, `Composables/`, `Component/`, `.vue`) их не объявляем — нужен тип, он сразу живёт в типовом слое. Тривиальная одноразовая форма (объект-параметр/результат одного вызова) — inline в сигнатуре, без именованного типа.
- **Именование — человекопонятное, по доменному смыслу и терминологии бэка**: строка-код сервиса — `serviceCode`, а не `key`. Изобретённые сокращения запрещены (`sl` вместо `serviceLocator`); общепринятые аббревиатуры (`api`, `http`, `url`, `id`, `config`) допустимы. Generic-имена (`key`, `value`, `data`, `item`, `obj`, `tmp`, `map`, `arr`) — только если понятие действительно родовое, иначе — доменное имя. Локальные переменные и параметры именуются так же осмысленно, как публичные. Булевы — предикаты (`is*`/`has*`/`can*`), функции — действие + объект. Однобуквенные имена — только в локальных математических/цикловых контекстах (`i`, `n`).
- **Моки = контракт**: моки типизированы теми же Interface-типами, что и бэк-контракты; замена транспорта (`main.ts`, `VITE_API_MODE`) не меняет потребителей.
- Глубокие объекты в дочерние компоненты передавать через `v-model` / именованные `v-model:propName`.
- Клонирование — `structuredClone()`, не `JSON.parse(JSON.stringify())`.
- **Реактивность**: reactive state (`ref`/Pinia) хранит plain-данные (`Dto/`), не class-инстансы — приватные поля не отслеживаются Proxy, `structuredClone`/сериализация теряют методы. Классы-сервисы — статeless, вне reactive state, вызываются `service.method(data)`.
- **Классы-сервисы**: поля-члены, не переприсваиваемые после инициализации (инжектированные зависимости, константные настройки), — `private readonly`; переприсваиваемые поля (состояние) — обычные `private`.
- **Документация (JSDoc).** Обязателен краткий JSDoc на русском у объявления `class` (включая неэкспортированный): зачем класс существует. У функций и методов **вне** `.vue` — по возможности; это не quality-гейт и не повод документировать весь фронт сейчас. В `.vue` (включая функции в `<script setup>`) JSDoc не требуется. Уже написанный JSDoc не удаляем.
- **Инлайн-комментарии — только «почему»**: нетривиальные инварианты и причины (например, почему метод намеренно пуст, алгоритм переноса размера в `DimensionalNumber.modify`), `TODO` с обоснованием. «Что» и «как» не комментируем — это выражается осмысленными именами и кодом; предпочтение — именованию, а не комментарию.
- **Механика закреплена линтером**: `any`/`as any`, `import type`, `readonly`, `!`-assertions, `@ts-ignore`, порядок тегов SFC, пустая строка перед `return`, unused — гарантирует ESLint (`npm run lint`); форматирование (2 пробела, `semi`, `singleQuote`, `trailingComma`, ширина 120) — Prettier (`npm run format`). Детали — в `eslint.config.js`/`.prettierrc.json`, в правилах не дублируем.

## 4. Шаблоны

- В шаблоне — простые выражения и одиночные вызовы методов. Простые лямбды вида `(v) => patch('x', v)` допустимы.
- Инлайн-логика (условия, вычисления, цепочки вызовов) — в методы или `computed`.
- UI строится на Vuetify; дизайн макеты не копировать.

## 5. Тесты

- Unit-тесты — исторические верификаторы (стратегия F8): пишутся на критичную логику (валидация, права, арифметика с инвариантами), а не на каждый вынесенный файл. Расположение — один `__tests__/` в корне модуля с папками, повторяющими структуру модуля (например, `Rule/__tests__/Service/ruleValidation.test.ts`).
- UI-mount-тесты с Vuetify не требуются (см. стратегию F8).

## 6. Верификация

- Проект всегда держим целиком в порядке; файлов-исключений нет.
- Отладка бага: только лёгкая неблокирующая часть — `npm run format` + `npm run lint` (оба автофиксят, на чистом коде молчат). Вердикт: если баг пойман тестом — `npx vitest run <файл>`, устранён, когда тест зелёный; если баг указал разработчик — устранён, когда разработчик подтвердил.
- Завершение бага/задачи (один гейт): `npm run format` → `npm run lint` → `npx vue-tsc --noEmit` → `npm run test`. Весь проект чист.
- Сборка (`vite build`) — веха релиза, делает пользователь.

## 7. Слои, нагрузка, безопасность

Ревью и повседневная работа смотрят на это так же, как на §§1–6. Чужие внутренности модулей закрывает `powerscale/no-foreign-module-internals`; остальное ревью.

- **Слои внутри модуля:** `.vue` — UI; домен — `Service/`/`Value/`; транспорт — `*Api` через locator; стор — состояние, не расчёты. Не прыгать через слой (страница не ходит в чужой внутренний Utils).
- **DOM:** не строить тысячи узлов в одном шаблоне (длинные списки — виртуализация, уже принятый паттерн чата). Тяжёлую работу не делать в рендере; слушатели/таймеры снимать в `onUnmounted`.
- **Бэк и запросы:** нет лишнего fetch/полла; debounce поиска; не перезапрашивать каталог в цикле/`watch` без нужды; пагинация там, где список может расти; тихих провалов нет (F17).
- **Уязвимости:** без `v-html` на непроверенном контенте (сообщения чата — через свой рендер/санитар); секреты и токены не в моках/логах/`localStorage`; вход с бэка валидировать по контракту Dto.
