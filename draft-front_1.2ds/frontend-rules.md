# Правила разработки фронтенда (Vue 3 + TS + Vuetify)

Правила целевого стандарта для `draft-front_1.2ds`. Применяются при любой работе с фронтом. При конфликте с текущим кодом код приводится к правилам (рефакторинг).

## 1. Структура SFC

- **Порядок тегов**: строго `<script setup lang="ts">` → `<template>` → `<style scoped>`.
- **Одна задача на файл**. Если в компоненте появилась вторая независимая задача (в форме — редактор списка, в карточке — диалог, в таблице — фильтры) или сложная вложенная разметка (панели в панелях, табы в табах, матрицы чекбоксов) — выделять дочерний компонент в подпапку рядом.
- Длина файла сама по себе не критерий: файл, делающий одну задачу, резать «по счётчику» нельзя. ~250 строк — сигнал перепроверить декомпозицию по задачам.

## 2. Разделение ответственности

- **Компонент** — только UI: состояние отображения (флаги модалок, `expandedPanels`), привязка данных, эвенты.
- **Логика вне компонента**: расчёты, валидация, работа со справочниками, вотчеры синхронизации, мутации глубоких объектов (`spec`) — выносить из `.vue`.
- Извлечённая логика живёт в подпапках своего модуля (`Service/`, `Dto/`, `Utils/`, `Constant/`, ...) или в модулях ядра (`Core/Engine`, `Core/UI`) в естественной для неё форме:
  - **доменная логика — класс-сервис в `Service/` модуля** (пример: `RuleValidationService`); файлов функций в `Service/` нет;
  - **generic-хелпер без состояния — функция в `Utils/` своего модуля** (группировка подпапками внутри); по возможности такие хелперы не писать (YAGNI);
  - **value-класс — `Core/Engine/Value/`** (пример: `DateTime`, `DimensionalNumber`);
  - мелочь без роста — приватный метод сервиса-потребителя, не отдельный файл.
- **Спеки — классы-сервисы в `Service/` модуля** (подпапка по домену, напр. `Service/Spec/`): `*SpecService`, создающий и подготавливающий объекты спека (`createEmpty*`, `prune*`, `resolve*`). Конфигурация (манифесты полей, справочники типов) инъектируется в конструктор — тестируемость и подменяемость. Все константы конфигурации лежат в `Constant/` модуля и инъектируются в конструктор; приватных констант в Service-файлах не держим. Производные справочники (универсумы полей, выводимые из манифестов) живут в `Constant/` как обычные константы, но вычисляются из источника-манифеста, а не дублируются копией.
- **В корне модуля из файлов — только точки сборки**: `init.ts` и `routes.ts`; всё остальное — подпапки. **Папки — в единственном числе.** Если файлу не находится осмысленное место — это сигнал, что он неуместен в текущем виде.
- **Анатомия модуля**: иерархия `src/modules/{Группа}/{Модуль}/`. Группа объединяет модули по предметной области (Messages: Chat, Notifications; Roleplay: Rule, Space, Character, Game). Подпапки: `Interface/` (контракты сервисов), `Dto/` (контракты данных), `Enum/` (перечисления — string-literal union), `Service/` (классы), `Constant/` (справочники), `Component/` (Vue-компоненты), `Mock/` (моки), `Utils/` (generic-хелперы, с подпапками), `Store/`, `Page/`, `Composables/`, `__tests__/`. **Папки — в единственном числе.** Внутри любой подпапки допустимы подпапки по логической группировке. `init.ts` — если модуль отдаёт наружу сервисы/доменную логику, `routes.ts` — если есть страницы; минимальный модуль — Page + routes. Модули лежат внутри групп; на уровне группы — только сами модули (агрегирующий `routes.ts` группы допустим, пример: Roleplay). **Core — группа фундамента**: её модули Engine (инфраструктура и логика) и UI (переиспользуемые Vue-компоненты и UI-утилиты) доступны из любого модуля напрямую. **Разделение Engine/UI**: всё, что касается отображения (Vue-компоненты, UI-утилиты — напр. `debounce`), — в `Core/UI`; логика/инфраструктура — в `Core/Engine`. **Общий UI проекта живёт в `Core/UI`, а не в `Core/Engine`.** `Core/Engine` не импортирует `Core/UI` (ни типы, ни утилиты): зависимость направлена только UI → Engine. `Core/Engine` — обычный модуль с анатомией (`Dto/`, `Service/`, `Interface/`, `Mock/`, `Value/`, `Composables/`); value-классы — в `Core/Engine/Value/`. Generic-логика и generic-компоненты — это подпапки модулей Engine/UI, а не отдельные папки на уровне группы; появление новых модулей в Core (и других группах) — обычная практика. Перечень подпапок анатомии не закрыт — введение новой подпапки/паттерна это осознанное решение, применяется согласованно в модулях.
- **Композаблы — в корневой `Composables/` модуля**, с подпапками по логической группировке; в `Component/` композаблов не держим (там только Vue-компоненты). Композабл — для stateful-логики с реактивностью и/или жизненным циклом; stateless-хелпер — функция в `Utils/` или приватная функция (YAGNI), композабл не ради паттерна. Кросс-модульные композаблы: отображение — в `Core/UI/Composables/`, инфраструктура — в `Core/Engine/Composables/`.
- **Сервисы через ServiceLocator**: API-сервисы модуля регистрируются в ServiceLocator через `init.ts` (`register`/`get`); доступ — только через фасады `getXxxApi()`, даже к своим. Импорт Service-реализации обходит централизованную подмену mock/real.
- **Межмодульный доступ** — через публичные точки модуля: `init.ts` (API-сервисы и ре-экспорт доменной логики), `useXxxStore()` (сторы — публичное состояние), `Interface/`/`Dto/`/`Enum/` (типы). Внутренние файлы чужого прикладного модуля не импортируем. **Исключение — группа Core**: модули Engine и UI доступны напрямую — это публичный API фундамента. Импорт mock-данных между модулями допустим (фикстуры, не потребители). Сервисы Core/Auth и Core/User — как у всех: `init.ts` + `useXxxStore()`.
- **Плагинные точки** (пример: Chat, профиль пользователя) — когда чужой прикладной модуль должен встроить в модуль-хост свой UI/логику, хост объявляет generic-контракт (`Interface/`) и реестр в `init.ts` (`register`/`get`), а донор регистрирует вкладку через публичную точку хоста (вызов `register*` из своего `init.ts`); композиция — в `main.ts`. Компоненты донора при этом не импортируются хостом напрямую.
- **Моки — в `Mock/` модуля**: фикстуры и mock-API-имплементации — это in-memory источник данных / фейк-бэк, не сервисы; в `Service/` их не кладём.
- **Направление зависимостей**: Core — фундамент; прикладные модули (Messages, Roleplay) зависят от Core, не наоборот.
- **Без дублирования**: готовая логика и компоненты переиспользуются; копирование — сигнал вынести в общее место.
- **Мутации глубоких объектов** — через функции-апдейтеры модуля, не inline-присваиваниями в компоненте: изменения трассируются и тестируются.
- **Статичные справочники** (опции селектов, конфиги, константы, манифесты) — в подпапку `Constant/` модуля, отдельными файлами; не в `<script setup>` и не в `Interface/`/`Dto/`. Внутри `Constant/` — подпапки по логической группировке при необходимости (например, `Constant/Ability/`, `Constant/Item/`).
- **Производные данные** — через `computed`, без пересчёта в шаблонах и методах.
- **Async-операции** — с состояниями загрузки/ошибки/повтора (паттерн F17); тихих провалов нет.
- **YAGNI**: не абстрагировать сверх текущей потребности.

## 3. Реактивность и TypeScript

- `props` не деструктурировать; при необходимости — только через `toRefs(props)`.
- **Pinia-сторы**: доступ к state/getters — через `store.xxx` (в шаблонах и computed) или `useStore()` в setup; это реактивно. Прямую деструктуризацию (`const { x } = store`) не использовать — теряется реактивность; если она нужна (локальные переменные в setup) — через `storeToRefs`.
- Типы импортировать явно: `import type { ... }`.
- Импорты — строго через алиас `@/`; относительные пути `../../` запрещены.
- **Запрет `any` / `as any`** в production-коде.
- **Типизация — слои по назначению**: контракты сервисов — `Interface/` (только контракты сервисов); контракты данных (интерфейсы-формы и дискриминированные юнионы) — `Dto/` модуля; перечисления — `Enum/` (**string-literal union, не настоящие TS-enum** — номинальная типизация ломает JSON-контракт). Каждый тип — отдельный файл (эталон: `Core/UI/Dto/ColumnDefinition.ts`), без свалок в `types.ts`; внутри `Dto/`/`Interface/`/`Enum/` — подпапки по назначению, не плоская куча. В этих папках — только типы, без констант и функций: справочные константы — в `Constant/` модуля, поведение — в классах `Service/`. **Именованные типы объявляются только в `Dto/`/`Interface/`/`Enum/`**; в файлах с кодом (`Service/`, `Value/`, `Composables/`, `Component/`, `.vue`) их не объявляем — нужен тип, он сразу живёт в типовом слое. Тривиальная одноразовая форма (объект-параметр/результат одного вызова) — inline в сигнатуре, без именованного типа.
- **Именование — человекопонятное, по доменному смыслу и терминологии бэка**: строка-код сервиса — `serviceCode`, а не `key`. Изобретённые сокращения запрещены (`sl` вместо `serviceLocator`); общепринятые аббревиатуры (`api`, `http`, `url`, `id`, `config`) допустимы. Generic-имена (`key`, `value`, `data`, `item`, `obj`, `tmp`, `map`, `arr`) — только если понятие действительно родовое, иначе — доменное имя. Локальные переменные и параметры именуются так же осмысленно, как публичные. Булевы — предикаты (`is*`/`has*`/`can*`), функции — действие + объект. Однобуквенные имена — только в локальных математических/цикловых контекстах (`i`, `n`).
- **Моки = контракт**: моки типизированы теми же Interface-типами, что и бэк-контракты; замена транспорта (`main.ts`, `VITE_API_MODE`) не меняет потребителей.
- Глубокие объекты в дочерние компоненты передавать через `v-model` / именованные `v-model:propName`.
- Клонирование — `structuredClone()`, не `JSON.parse(JSON.stringify())`.
- **Реактивность**: reactive state (`ref`/Pinia) хранит plain-данные (`Dto/`), не class-инстансы — приватные поля не отслеживаются Proxy, `structuredClone`/сериализация теряют методы. Классы-сервисы — статeless, вне reactive state, вызываются `service.method(data)`.
- **Классы-сервисы**: поля-члены, не переприсваиваемые после инициализации (инжектированные зависимости, константные настройки), — `private readonly`; переприсваиваемые поля (состояние) — обычные `private`.
- **Комментарии — только «почему»**: нетривиальные инварианты и причины (например, почему метод намеренно пуст, алгоритм переноса размера в `DimensionalNumber.modify`), `TODO` с обоснованием. «Что» и «как» не комментируем — это выражается осмысленными именами и кодом; предпочтение — именованию, а не комментарию.
- **Механика закреплена линтером**: `any`/`as any`, `import type`, `readonly`, `!`-assertions, `@ts-ignore`, порядок тегов SFC, пустая строка перед `return`, unused — гарантирует ESLint (`npm run lint`); форматирование (2 пробела, `semi`, `singleQuote`, `trailingComma`, ширина 120) — Prettier (`npm run format`). Детали — в `eslint.config.js`/`.prettierrc.json`, в правилах не дублируем.

## 4. Шаблоны

- В шаблоне — простые выражения и одиночные вызовы методов. Простые лямбды вида `(v) => patch('x', v)` допустимы.
- Инлайн-логика (условия, вычисления, цепочки вызовов) — в методы или `computed`.
- UI строится на Vuetify; дизайн макеты не копировать.

## 5. Тесты

- Unit-тесты — исторические верификаторы (стратегия F8): пишутся на критичную логику (валидация, права, арифметика с инвариантами), а не на каждый вынесенный файл. Расположение — один `__tests__/` в корне модуля с папками, повторяющими структуру модуля (например, `Rule/__tests__/Service/ruleValidation.test.ts`).
- UI-mount-тесты с Vuetify не требуются (см. стратегию F8).

## 6. Верификация

- После изменений — `vue-tsc --noEmit`, `vitest run`, `npm run lint` и `npm run format:check`. Сборка (`vite build`) — веха релиза, делает пользователь.
