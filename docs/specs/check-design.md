# Тип правила «Проверка»

> Дата: 2026-08-22. Согласовано в обсуждении модели. Статус: **спека + тип в каталоге + запуск соло/pairwise + попадание ББ 1v1**.
> Дальний бой, захват, толчок, урон в оверлей, таблица увечий в UI — позже.

## 1. Зачем

Бросок (`RollEngine`, правило `roll`) считает кубы. Проверка — **именованное действие** над броском: identity (`code`), чтобы гранты и моды цеплялись («преимущество на попадание», «на общение»), плюс слой **сложности → РУ**.

Эффективность грани ≠ сложность проверки. В UI броска `efficiency` ошибочно подписан `сл:` — это порог грани.

## 2. Три слоя

1. **Бросок** — пул, преимущества/помехи, эффективность (дефолт 3; у попадания атакующего — точность оружия). Скаляр успехов. Правило `roll` — дефолты пула, не скоринг «6 и 1».
2. **Размер успехов** — размер источника пула (`dieSize`). Сила `{4|1}` → успехи `{n|1}`.
3. **Проверка** — сравнение со сложностью (размерное число) → успех/провал и **РУ**. Правила броска («6 и 1», преимущества) объявлены на **простой проверке** списком кодов карточек (`attached_rule_codes`) и наследуются потомкам; увечье задаёт свой набор.

РУ: обе стороны к **меньшему** размеру (шаг ×2 вниз, база целая), затем `РУ = база успехов − база сложности`. Проход, если успехи ≥ сложности (`DimensionalNumber.compare`). Нельзя считать в большем размере: 1↓ против 5 дало бы −4.5; верно 1↓ против 10↓ → −9.

Пример: проверка на Силу, сложность `{2|1}`, преимущество от обстоятельств, сила `{4|1}` → 5 кубов, после drop и 6-и-1 скаляр 3 → `{3|1}` ≥ `{2|1}` → успех, РУ 1.

Голый `/roll` в чате — **простая проверка vs `{0|0}`** (механики `check-simple`, РУ). Не отсутствие проверки.

Совместная: чужой размерный итог = сложность стороны; РУ обеих сторон противоположны (±N в одном размере). Попадание: размер успехов атаки приводится к размеру успехов защиты тем же правилом (меньший размер). Одна карточка правила — соло или joint (флаг запуска). Увечье может запретить joint.

## 3. Дерево

Наследование (`parent_check_code`) задаёт правила броска (`attached_rule_codes`) и матчинг грантов (код запуска или предок). Навыки позже добавляют механики поверх, не ломая дерево.

Увечье — **отдельный корень** (свой скоринг; в этом заходе `attached_rule_codes` без «6 и 1»).

```
простая проверка (check-simple)
  ├─ на попадание (check-hit)
  ├─ на истощение (check-exhaustion)
  ├─ на инициативу (check-initiative)
  ├─ на каждую характеристику (check-strength, …) кроме ветки общения
  └─ на общение (check-communication) → обман, убеждение, запугивание, обольщение, торговля
проверка на увечье (check-injury)
```

- Каждая характеристика — своё правило `check-*`.
- Общение: пул по умолчанию с Красноречия и у листьев; на запуске редко подменяют характеристику; identity (обман) не меняется.
- Инициатива — ребёнок простой проверки; характеристику называет мастер.
  **Запуск** всегда `check-initiative` (гранты «на инициативу»). **Механики броска** (`attached_rule_codes`) —
  с проверки **выбранной** характеристики (`check-perception` по умолчанию, `check-attention` / другая, если мастер
  подменил); свободный бросок — с `check-initiative`. Грант «на восприятие» не вешается на чужую инициативу со
  скрытностью, грант «на инициативу» — на любой запуск шкалы.
  Порядок шкалы — `DimensionalNumber.compare` по убыванию (3↓ < 2), не скаляр успехов.
- Грант на общение действует на обман. Грант на `check-simple` — на все обычные проверки, не на увечье.

Коды листьев общения (`intimidation` …) совпадают со старым словарём домена `communication-check` (D116).

## 4. Спека (`CheckSpec`)

```ts
type CheckAllowedModes = 'solo' | 'joint' | 'both'

type CheckDifficultyInput =
  | { kind: 'ask' }                         // мастер; быстро — vs {0|0}
  | { kind: 'from_state'; state_code: string } // истощение
  | { kind: 'none' }                        // порядок (инициатива): сложность = чужие итоги

interface CheckSpec {
  type: 'check'
  parent_check_code?: string | null
  characteristic_code?: string | null      // дефолт пула; иначе у предка
  allow_characteristic_override?: boolean  // общение, инициатива
  default_efficiency?: number | null       // иначе предки, затем правило roll
  difficulty_input: CheckDifficultyInput
  allowed_modes: CheckAllowedModes
  attached_rule_codes?: string[] | null    // коды правил (rule-6-and-1); задано (в т.ч. []) — не наследовать
}
```

Не в карточке правила: полный бой попадания, таблица увечий. Запуск соло и pairwise — §6.

## 5. Код

- Тип `RuleType = 'check'`. Каталог: `mockChecks.ts`.
- Резолв предков / `attached_rule_codes` / характеристика: `Rule/Utils/checkResolution.ts`.
- РУ: `Rule/Utils/checkSuccessRating.ts`.
- `RollEngine.roll(..., extraRuleCodes, [])` — проверка подставляет **коды правил** (у простой: `rule-6-and-1`, `advantages`). Правило `roll` держит дефолты пула; его `sub_mechanics` — только для голого броска без проверки.
- Редактор проверки: «Свой набор правил броска» + мультиселект карточек с механикой.
- Чат `/roll` / форма броска: `rollSimpleCheckZero` (`check-simple` vs `{0|0}`).
- Инициатива: `initiativeRoll.rollInitiative` — identity запуска `check-initiative`; `attached_rule_codes` с
  `resolveCheckCodeForCharacteristic` выбранной характеристики (свободный бросок — с `check-initiative`).
- Карточка в чате (`DiceRollResult.vue`): шапка «название · РУ» (зелёный/красный по успеху/провалу), кубы; параметры и механики — во всплывашке по иконке info.
- Домен «Манера общения»: дети `check-communication` в ревизии.
- Запуск: `CheckLaunchDialog`, `checkRoll.rollNamedCheck` / `rollJointCheck`, мок `mockCheckOffers`.
- Попадание ББ: `hitRoll.rollMeleeHit`, процедура `strike-procedure` → `strike@version`, UI `HitLaunchDialog`.

## 6. Роды запуска

Общий слой РУ: чужой размерный итог = сложность стороны. Процедуры разные.

### Инициатива (`group_gm`)

Уже есть: `InitiativeDialog`. Мастер назначает участников и метод. Identity запуска `check-initiative`. **Не** handshake и не переписывать.

Группы простых проверок с одним победителем / спецправила — отложены.

### Соло

Один участник, без оферты. Сложность: `{0|0}` (игрок, ask), поле ведущего (ask), или `from_state` (характеристика пула против состояния на листе: Сила воли против Истощения). `/roll` — `check-simple` vs `{0|0}`. Кубик боевой карточки — мгновенно vs `{0|0}` + слой `check`.

### Pairwise (простая совместная)

Одно окно на обе стороны. Инициатор заполняет себе и оппоненту (вторая характеристика = первая по умолчанию) → оферта. Оппонент принимает или правит и возвращает (`waitingOn` меняется). Кубы — только после `accept`: два пула, взаимный РУ, два вложения в чат.

Транспорт живой игры — SSE. Сейчас мок API (`createCheckOffer` / `revise` / `accept` / `cancel`) + полл вкладки чата при смене «от лица кого».

UI: кнопка «Проверка» в чате игры. В списке нет `check-initiative` / `check-injury` / `check-hit`.

### Попадание (удар) — v1, модель A

Процедура удара живёт в коде (`hitRoll` + `StrikeProcedure` `code@version`). Срез ревизии держит карточку `strike-procedure` → mechanic `strike@1.0.0`. Две игры на одном сайте (ревизии 4.5 и 5) резолвят разные хендлеры из одного бандла. JSON полной процедуры в карточке нет.

Запуск: тайл атаки на боевой карточке → `HitLaunchDialog` (атакующий: цель + преим. атаки) → оферта `check-hit` с `hit.reaction = null` → защитник выбирает игнор/уклон/блок. Ведущий (`canEdit`) отвечает за ожидающую сторону без смены спикера; полл `getCheckOffersForGame`. Игрок-защитник — «от лица» цели или кнопка «Проверка».

- Эффективность атаки и защиты — **размерное число**, база 3–5. Скаляр 2 = `{4|-1}`. Грань пула = `efficiency.base`; `dieSize = mastery.size + efficiency.size` (размер эффективности на успехи, как размер куба).
- Атакующий: пул = мастерство оружия, эффективность = точность профиля целиком (не только `.base`).
- Игнор: соло vs РУ защиты **0↓** (`{0|-1}`).
- Уклон: joint; пул — лучшее мастерство ББ экипированного оружия; **−N к мастерству** (`CharacteristicNumber.modifyWith`) за размеры Ловкость/Восприятие ниже среднего, не помеха к пулу; эффективность задаёт защитник.
- Блок: joint; профиль с экипированного щита/оружия с `block_profile`; эффективность с профиля, правится вручную, не ниже `minBlockEfficiency` процедуры (`{4|-1}`).
- Выстрел/бросок, фланги, урон, 1v2 — не в v1.

**Клик-атака** (в коде, 2026-08-23): клик по боевому профилю открывает окно атаки (тот же handshake попадания). Атакующий выбирает **действие-атаку** из доступных персонажу. По умолчанию у каждого есть автоматические способности «Простая атака (ближний бой)» и «Простая атака (дальний бой)» (`zones.os.kind = automatic`, признак `attack`, трата ОД в `action_components`). Защитник выбирает реакцию: игнор / уклон / блок — тоже действия (уклон 1 ОД, блок 2 ОД). После броска: оплата X РУ против надёжности (если у типа фаза `attack`), урон `(оружие − сопротивление) × оставшееся РУ`; **защита складывается в сопротивление**, если у типа нет галочки `defense_ignored`. Чат: действие → удар → броски → результат с кнопкой расчёта. ОД списываются с оверлея, истощение пишется состоянием на лист. Увечье по-прежнему отдельной кнопкой.

Увечье: процедура `injury@version` (как удар). Identity — `check-injury` (соло, преимущества, без 6 и 1). Тип урона **опционален**: без типа — базовый скоринг; с типом — фаза `injury` его хуков. Пул = max(floor(повреждения / Стойкость), floor(рана / 2), истощение≥6 → истощение−5). Взрыв 6, пока падают; убрать грани ниже порога (обычно 1–2). Исход: Увечье:X + постоянное/временное + смертельное + обезображивающее; у временного — бросок срока −1. Степпер карточки не бросает; кнопка «Увечье» → чат. На лист не пишем. Спека типов: `docs/specs/damage-type-design.md`.
