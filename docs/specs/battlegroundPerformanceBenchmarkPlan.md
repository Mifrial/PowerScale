# План ориентировочного performance-теста battleground

**Статус:** черновой план эксперимента, 2026-09-20.  
**Назначение:** проверить вычислительную и memory feasibility серверной модели
battleground до реализации PHP persistence и backend API.

Канон предметной области: [`battlegroundLockedDecisions.md`](battlegroundLockedDecisions.md).  
Канон требований: [`../tr/battleground-system.md`](../tr/battleground-system.md).

Этот план не предлагает реализовывать battleground. Тестовый скрипт должен
генерировать синтетические данные и выполнять отдельные операции, похожие на
будущую серверную нагрузку.

## 1. Цель и границы

Нужно получить ориентировочный ответ на вопросы:

- подходит ли PHP для расчётов LOS, дистанции и проверки движения;
- подходит ли occupancy в виде packed binary string;
- насколько дорога обработка одного байта/столбика в горячем цикле;
- сколько памяти занимают сцены и проекции;
- какие операции можно выполнять на каждый запрос, а какие требуют cache или
  предварительного расчёта;
- не требует ли модель упрощения до начала PHP-реализации.

В тест не входят:

- frontend, WebGL и браузерный renderer;
- реализация доменных классов battleground;
- реальный HTTP API, Auth, SSE и MySQL на первом этапе;
- доказательство производительности для всех будущих PHP deployment-конфигураций;
- утверждение о точном количестве поддерживаемых одновременных игроков.

Первый этап измеряет алгоритмическое ядро в PHP CLI. HTTP/FPM, база и
конкурентные запросы проверяются отдельным этапом после появления server Core.

## 2. Среда и воспроизводимость

Скрипт запускается на PHP 8.2, поскольку эта версия является минимальной для
будущего PHP-проекта.

Каждый прогон обязан записывать:

- версию PHP;
- включён ли JIT и основные настройки memory limit;
- ОС и число доступных CPU;
- размер и тип сцены;
- seed генератора данных;
- количество итераций и прогревочных итераций;
- представление occupancy;
- результаты и пиковую память.

Измерение времени выполнять монотонным `hrtime(true)`. Для каждого сценария
отдельно измерять генерацию fixture, прогрев и основной прогон. Результаты
сохранять в машиночитаемом JSON и печатать краткий человекочитаемый итог.

## 3. Build contract and reproducibility

Первый билд является автономным PHP CLI-инструментом и не требует
production-классов battleground, базы данных, HTTP-сервера или frontend.
Предполагаемый путь:

```text
www/mifrial/tools/battleground-model-benchmark.php
```

Запуск полного набора:

```bash
php tools/battleground-model-benchmark.php --suite=all --json=var/benchmark.json
```

Запуск одного сравнения:

```bash
php tools/battleground-model-benchmark.php \
  --scenario=los_single \
  --scene=stress \
  --representation=packed \
  --seed=20260920 \
  --warmup=3 \
  --repeats=7 \
  --iterations=10000 \
  --json=var/los-stress-packed.json
```

Путь `tools/...` в примерах считается относительно `www/mifrial`. Результат
`var/` — артефакт эксперимента, не production-данные.

### 3.1. Параметры по умолчанию

Если параметр не задан, используются:

- `seed=20260920`;
- `warmup=3`;
- `repeats=7`;
- `iterations=10000` для точечных операций;
- `iterations=1000` для `projection`, `path_query` и других дорогих операций;
- `scene=small`;
- `representation=packed`.

`suite=all` обязан прогонять все сценарии на `small` и `stress`, а
`max-grid` — только для `occupancy_read`, `los_single` и memory-проверки.
Полный suite не должен случайно занимать часы: длительность каждого сценария
должна записываться в итог.

### 3.2. Фиксированные fixture-параметры

Если сценарий не переопределяет параметры явно:

- `small` — 40×40 ипари, 200 токенов, 4 000 деревьев;
- `stress` — 200×200 ипари, 200 токенов, 40 000 деревьев, двухэтажный дом
  (`Enclosure`) с окнами, дверьми, телепортами и крышей;
- `max-grid` — occupancy 1024×1024 клеток, без обязательного полного набора
  деревьев и токенов;
- `SceneResolution` — 1/64 ипари для точных координат движения;
- `occupancyCell` — 1/4 ипари для LOS, illumination и portal id;
- portal depth — 0, 1, 2 и 4 перехода в отдельных поднаборах;
- длина LOS — короткая 4, средняя 40 и длинная 160 ипари;
- маршрут — 4, 16 и 64 сегмента;
- token footprints — circle, ellipse и rectangle;
- плотность препятствий — `sparse`, `typical`, `dense`.

В `stress` дом должен включать минимум два отдельных пространства этажей,
опору крыши на родительском пространстве, обычные открывающиеся двери и окна,
а также free/bidirectional и направленные телепортные связи. 40 000 деревьев
хранятся как compact instances; их runtime-обработка выполняется через
подготовленные occupancy/navmesh, а не проходом по всем деревьям на каждый
запрос.

`SceneResolution` и `occupancyCell` нельзя смешивать. Точность движения,
координаты полилинии и footprint collision — 1/64 ипари; occupancy используется
только для своих задач и имеет точность 1/4 ипари. Числа являются параметрами
benchmark, а не новыми требованиями battleground. Их изменение должно
отражаться в JSON-результате.

### 3.3. Correctness oracle

До performance-прогона fixture и каждая реализация обязаны пройти одинаковые
маленькие deterministic cases. Для LOS и чтения occupancy нужен независимый
reference-путь, намеренно простой и медленный; он не должен повторно
использовать код оптимизируемой реализации.

Минимальный oracle проверяет:

- пустой столбик;
- оба opaque-интервала;
- canopy и illumination;
- открытый и закрытый проём;
- portal id;
- границы и отрицательное направление луча;
- высоты с обычным и укрупнённым `zQuantum`;
- illumination=255, затемнённая клетка и sense, игнорирующая свет;
- несколько пространств;
- blocked и clear path;
- точность координат 1/64 ипари независимо от occupancy 1/4 ипари;
- одинаковый результат для всех occupancy-представлений.

Если correctness oracle не пройден, performance-результат не считается
валидным и не попадает в сравнительный вывод.

### 3.4. Протокол измерения

Для каждого сочетания `scenario × scene × representation × density`:

1. создать fixture с одним и тем же seed;
2. проверить fixture oracle;
3. выполнить `warmup`;
4. выполнить `repeats` независимых серий;
5. в каждой серии выполнить `iterations`;
6. записать время каждой операции либо достаточно мелкие batch-выборки для
   расчёта p50/p95/p99;
7. отбросить только явно отмеченные ошибки, а не неудобные медленные серии.

Генерацию fixture, подготовку индексов, измеряемую операцию и сериализацию
результата измерять раздельно. Результаты не смешивать между представлениями:
один процесс или отдельный процесс на вариант должен быть указан в отчёте.

### 3.5. Формат результата

JSON содержит как минимум:

```json
{
  "schemaVersion": 1,
  "status": "ok",
  "run": {
    "phpVersion": "...",
    "jit": false,
    "os": "...",
    "cpuCount": 0,
    "seed": 20260920
  },
  "case": {
    "scenario": "los_single",
    "scene": "stress",
    "representation": "packed",
    "density": "typical",
    "profile": "single-game-normal",
    "workers": 1,
    "durationSec": 60,
    "memoryBudgetBytes": 0,
    "sceneResolution": "1/64 ipari",
    "occupancyCell": "1/4 ipari",
    "iterations": 10000,
    "warmup": 3,
    "repeats": 7
  },
  "correctness": {
    "passed": true
  },
  "metrics": {
    "fixtureBytes": 0,
    "peakMemoryBytes": 0,
    "totalMs": 0,
    "meanUs": 0,
    "p50Us": 0,
    "p95Us": 0,
    "p99Us": 0,
    "opsPerSecond": 0,
    "workerRssBytes": 0,
    "cpuSaturation": 0
  },
  "error": null
}
```

Числа `0` в примере означают типы полей, а не допустимые результаты для
реального прогона. Успешный результат имеет `status=ok` и `error=null`.
Ошибка запуска должна быть отдельным результатом со статусом `failed` и
текстом ошибки в `error`, а не пустым успешным измерением.

### 3.6. Правила сравнения

До получения первых чисел не вводить произвольный продуктовый SLA. Для первого
отчёта использовать такие правила:

- сравнивать только одинаковые fixture, seed и сценарий;
- отдельно сравнивать время и память;
- считать вариант регрессией, если он медленнее или прожорливее baseline,
  но не скрывать trade-off одной метрикой;
- считать результат подозрительным при расхождении correctness или при
  существенной нестабильности повторов;
- отдельно маркировать `exploratory`, `control-negative` и `canonical-baseline`;
- не переносить CLI-результаты напрямую на PHP-FPM/MySQL.

### 3.7. Целевой сервер и capacity-профили

Целевой минимальный профиль для первого эксперимента:

```text
CPU: 2 logical CPUs
RAM: 4 GiB total
PHP: 8.2
Games: 1–2
Players per game: <= 5
```

Память считать для всей машины, а не только для PHP. В отчёте отдельно
указывать пиковую память benchmark workers и оставлять место для ОС, web
server, MySQL и прочих обязательных процессов. Точный memory budget приложения
задаётся параметром, а не подразумевается равным 4 GiB.

До появления backend capacity-тест остаётся синтетическим и запускает несколько
изолированных PHP CLI workers. Минимальная матрица:

- 1 worker: baseline одной игры;
- 2 workers: две игры или две параллельные группы операций;
- 4 workers: контрольный oversubscription-прогон для 2 CPU.

Минимальные профили нагрузки:

```text
single-game-normal: 1 игра, до 5 игроков, 1 command/sec суммарно
single-game-burst:  1 игра, до 5 игроков, 5 command/sec в течение 10 секунд
two-games-normal:   2 игры, до 5 игроков в каждой, 1 command/sec на игру
two-games-burst:    2 игры, до 5 игроков в каждой, 5 command/sec на игру
```

Частоты — стартовые параметры эксперимента, не утверждение о реальном
поведении игроков. Они должны переопределяться через CLI и записываться в
JSON. `projectionRefresh` и серверный `map_visibility` задаются отдельно и не
включаются автоматически в каждый `move`.

Capacity-прогон длится минимум 60 секунд после 10 секунд прогрева. Он должен
показывать throughput, p50/p95/p99, ошибки, суммарный RSS workers, пик памяти
и CPU saturation. Главный результат — максимальный устойчивый профиль до
роста p95, ошибок, нехватки памяти или насыщения CPU.

## 4. Синтетические fixture

### 4.1. Размеры сцен

Минимальный набор:

- `small`: 40×40 ипари;
- `stress`: 200×200 ипари;
- `max-grid`: occupancy 1024×1024 клеток как проверка верхней границы.

Для `occupancyCell = 1/4` ипари это соответственно 160×160, 800×800 и
1024×1024 occupancy-клеток. Размер сцены и размер occupancy-сетки не смешивать.

### 4.2. Содержимое

Генератор создаёт:

- occupancy-столбики с двумя opaque-интервалами, canopy-интервалом,
  illumination и portal id;
- прямоугольные стены и препятствия;
- несколько открытых и закрытых проёмов;
- 200 токенов с координатами, высотой, facing и footprint;
- до 40 000 деревьев как instances;
- несколько SceneSpace и порталов между ними;
- набор маршрутов разной длины;
- набор пар атакующих и целей.

В `stress` fixture обязательно добавить двухэтажный `Enclosure` на родительском
пространстве: два интерьерных `SceneSpace`, крышу как `SupportSurface`,
открывающиеся двери и окна, а также free/bidirectional и направленные
телепортные связи. Минимум один маршрут и одна атака должны проходить через
эту композицию.

Генератор должен иметь режимы плотности препятствий: `sparse`, `typical`,
`dense`. Данные должны быть детерминированы seed, чтобы сравнение вариантов
было честным.

## 5. Варианты представления occupancy

Сравнить минимум следующие варианты.

### A. Packed binary string — канонический baseline

Один бинарный blob на пространство: header и 8 байт на клетку, как в каноне.
Benchmark может отдельно показывать размер header и payload, но не должен
подменять ими контракт.

Нужно измерить как минимум:

- чтение байта через offset и `ord`;
- извлечение нескольких байтов через `unpack()` с заранее выбранным размером
  блока;
- строковые побитовые операции над одинаковыми бинарными масками, если они
  действительно применимы к выбранной операции;
- чтение последовательного участка;
- чтение столбика, необходимого одной LOS-трассе;
- локальный патч двери с copy-on-write.

### B. Packed rows/chunks — экспериментальный вариант

Отдельная бинарная строка на ряд или на небольшой chunk. Вариант нужен для
сравнения локальных патчей и кэширования областей. Он не отменяет принятого
контракта «один blob на пространство» и не может считаться изменением канона
без отдельного решения.

### C. PHP arrays — контрольный негативный вариант

Массивы чисел или структур по клеткам использовать только как контрольный
вариант. Он нужен, чтобы зафиксировать стоимость удобного, но потенциально
дорогого представления по памяти и времени.

Дополнительно можно проверить `unpack`, но не использовать его внутри каждой
ячейки горячего цикла без отдельной фиксации результата.

Критерий эксперимента: формат нельзя оценивать только по размеру blob. Нужно
сравнить стоимость хранения, случайного чтения, последовательного чтения,
локального обновления, полного прохода и побитовой/блочной обработки.

## 6. Сценарии нагрузки

### 6.1. `occupancy_read`

Случайное и последовательное чтение occupancy-столбиков для заранее
известного набора координат. Проверяет overhead представления данных отдельно
от LOS и геометрии.

### 6.2. `los_single`

Проверка LOS между двумя точками/высотами через occupancy-столбики:

- короткий луч;
- длинный луч;
- луч через плотную геометрию;
- луч через открытый portal;
- луч, остановленный opaque-интервалом.
- луч в темноте с обычным LOS-сенсом;
- тот же луч с sense, игнорирующим illumination;
- лучи на разных высотах и через разные `zQuantum`.

### 6.3. `map_visibility`

Отдельный редкий серверный refresh видимости для одного персонажа в пределах
его лучшего LOS-сенса. Это не обычная операция каждого движения: в штатном
сценарии JS обновляет клиентскую видимость по данным начала/конца движения и
имеющемуся occupancy/knowledge.

Сравнить серверный refresh:

- последовательный проход клеток;
- трассировку лучей к границе области;
- повторный расчёт при том же положении;
- расчёт после небольшого изменения двери.

Полный проход карты здесь является контрольным негативным вариантом. Основной
результат — стоимость редкого refresh и возможность быстро его выполнить, а не
стоимость fog на каждый запрос.

Постоянный JS-расчёт fog не входит в этот PHP benchmark. Его нужно будет
проверить отдельным frontend/JS-тестом на тех же occupancy-данных, с отдельным
бюджетом времени.

### 6.4. `projection`

Построение синтетической `PlayerSceneProjection` для редкого серверного
обновления или выдачи после изменения состояния:

- разрешённые данные пространств и occupancy, без серверной rasterization fog;
- фильтрация 200 токенов;
- состояния `visible`, `explored`, `unknown`;
- несколько пространств и ограниченный проход через порталы.

Полную скрытую сцену в результат не включать: тест должен отражать правило,
что сервер фильтрует данные до выдачи игроку.

### 6.5. `move_validate`

Проверка заранее сгенерированной полилинии движения:

- проверка границ и препятствий;
- проверка footprint;
- точная арифметика координат с разрешением 1/64 ипари;
- точная circle/ellipse/rectangle collision, а не проверка по occupancy-клеткам;
- смена support или проход через opening;
- типичные и длинные маршруты.

Occupancy не использовать как замену movement geometry. Если для отдельной
проверки нужна связь с LOS или portal id, измерять её отдельным подпроцессом.
Основной baseline — проверка уже найденной сервером полилинии.

### 6.6. `path_query`

Запрос маршрута по navmesh, построенному заранее:

- короткий маршрут на одной опоре;
- маршрут через несколько support edge;
- маршрут с `squeeze`;
- недоступный маршрут;
- типичная и плотная геометрия.

Координаты результата и funneling хранить с точностью 1/64 ипари. Occupancy
1/4 ипари не является сеткой pathfinding.

Замерить отдельно построение navmesh при сохранении сцены и запрос маршрута
во время игры. Нельзя смешивать стоимость save-time bake со стоимостью каждого
движения.

### 6.7. `attack_context`

Для пар атакующий/цель вычислить:

- точную евклидову дистанцию;
- пересечение LOS;
- открытая дверь/окно с прямым 3D-отрезком в укладке enclosure;
- несколько vis-переходов через порталы;
- телепорт с суммой расстояний до двух проёмов;
- закрытый проём;
- facing и `flank`;
- несколько последовательных атак в одной сцене.

Не моделировать правила броска, урон и остальную механику Game: измеряется
только spatial context.

### 6.8. `door_patch`

Изменить состояние одной двери:

- обновить локальные occupancy-столбики;
- обновить связанные данные прохода;
- подготовить новую scene version;
- выполнить несколько последующих LOS-проверок.

Сравнить локальный патч с полной пересборкой occupancy. Полная пересборка
нужна как baseline, но не должна считаться обязательной реализацией.

### 6.9. `mixed`

Смешанный профиль одной активной сцены:

- 60% `los_single`;
- 15% `attack_context`;
- 15% `projection`;
- 8% `move_validate`;
- 3% `path_query`;
- 1% `door_patch`.

Доли являются стартовой гипотезой и должны быть явно изменяемыми параметрами.
Отдельно прогнать профиль с несколькими игроками, читающими одну сцену.

## 7. Метрики

Для каждого сценария собирать:

- общее время;
- операции в секунду;
- среднее время операции;
- p50, p95 и p99;
- пиковую память процесса;
- размер fixture;
- число обработанных occupancy-клеток;
- число проверенных столбиков и токенов;
- число переходов через portal;
- число обработанных сегментов маршрута и navmesh-полигонов;
- количество аллокаций, если доступен надёжный способ измерения.

Не скрывать подготовительную работу: отдельно публиковать время генерации,
индексации, расчёта и сериализации результата.

Для тестов с памятью отдельно проверить:

- один загруженный blob;
- несколько одновременных сцен;
- повторное использование одной сцены;
- копирование и copy-on-write после патча.

Для леса отдельно записывать:

- время stamp occupancy и построения navmesh на save;
- размер compact instance representation;
- стоимость наивного прохода по 40 000 деревьям как контрольного негативного
  варианта;
- стоимость runtime LOS по уже подготовленной occupancy без прохода по
  instance layer.

Для серверной visibility отдельно записывать частоту вызова как параметр
профиля, а не включать refresh в каждое движение. Базовый профиль движения
использует клиентское обновление fog; серверные операции ограничиваются
projection, авторизацией, проверкой движения и LOS/контекстом атаки.

## 8. Этапы

### Этап 1. Самостоятельный CLI benchmark

Создать отдельный скрипт, например
`www/mifrial/tools/battleground-model-benchmark.php`, без production
autoload-зависимостей battleground.

Добавить параметры:

- `--scenario`;
- `--suite`;
- `--scene`;
- `--representation`;
- `--iterations`;
- `--warmup`;
- `--repeats`;
- `--seed`;
- `--profile`;
- `--workers`;
- `--duration`;
- `--memory-budget`;
- `--json`.

### Этап 2. Проверка корректности fixture

До замеров добавить маленькие deterministic cases:

- пустой луч;
- стена между точками;
- открытая и закрытая дверь;
- canopy;
- портал в другое пространство;
- граница карты;
- пустой occupancy slot.

Бенчмарк не должен превращаться в production-тест, но неправильный LOS делает
результаты бесполезными.

### Этап 3. Сравнение представлений

Прогнать одинаковые seed и операции для binary string, rows/chunks и arrays.
Сначала сравнить корректность результатов, затем время и память.

### Этап 4. Сравнение алгоритмических стратегий

Проверить как минимум:

- полное сканирование карты;
- локальный расчёт вокруг персонажа;
- повторное использование неизменившейся projection;
- локальный патч после открытия двери.

Цель — найти не только «быстрый формат байтов», но и недопустимые паттерны
работы.

Полное сканирование карты и `map_visibility` не включать в штатный профиль
каждого движения. Они остаются отдельным серверным refresh/negative-control
сценарием.

Отдельно сравнить канонический путь:

```text
40 000 instances → save-time stamp → occupancy/navmesh → runtime query
```

с негативным вариантом:

```text
40 000 instances → повторная проверка каждого дерева на каждый LOS/query
```

Негативный вариант нужен для измерения цены ошибки, но не является
предлагаемой реализацией.

### Этап 5. Интерпретация

Для каждого сценария зафиксировать:

- приемлемо;
- требует кэша/индекса;
- требует изменения алгоритма;
- не подтверждено без HTTP/FPM/MySQL.

Не подбирать критерии после получения удобных чисел. Пороговые значения
записать перед первым сравнительным прогоном либо пометить как exploratory,
если заранее обоснованный порог невозможен.

### Этап 6. Synthetic capacity до backend Core

На тех же synthetic fixtures запустить capacity-профили из раздела 3.7:

- 1–4 изолированных PHP worker’а;
- одна stress-сцена на worker;
- одна и две параллельные игры;
- normal и burst режимы;
- отдельный редкий `projectionRefresh`/`map_visibility`.

Этот этап отвечает на вопрос о приблизительной ёмкости слабой машины без
реализации backend. Он не моделирует HTTP/FPM точно и потому не заменяет
следующий этап.

### Этап 7. Второй этап после Core

После появления серверного Core добавить отдельный нагрузочный тест:

- PHP-FPM;
- реальные HTTP-команды;
- Auth и сериализация;
- MySQL persistence;
- несколько одновременных игроков;
- SSE-подключения и доставка небольших событий.

Этот этап не должен менять результаты CLI-теста, а только добавлять стоимость
транспорта и инфраструктуры.

## 9. Предварительные гипотезы

Это гипотезы для проверки, не принятые решения:

1. Packed binary string будет приемлем по памяти.
2. Побайтное чтение в PHP может быть приемлемым для локальной LOS-трассы, но
   полный пересчёт большой карты для каждого запроса может стать узким местом.
3. PHP-массив occupancy будет существенно хуже packed string по памяти.
4. Локальный patch двери должен быть значительно дешевле полной пересборки.
5. Кэширование неизменившейся projection может дать больший эффект, чем
   оптимизация одного чтения байта.
6. 40 000 деревьев нельзя включать как 40 000 полноценных PHP-объектов в
   каждый запрос; для benchmark нужен compact instance representation.

## 10. Критерии остановки и решения

Эксперимент считается достаточным для решения о продолжении проектирования,
если:

- есть сравнимые результаты для трёх occupancy-представлений;
- измерены small, stress и max-grid;
- пройдены `los_single`, `map_visibility`, `projection`, `move_validate`,
  `path_query`, `attack_context`, `door_patch` и `mixed`;
- зафиксированы p95 и пиковая память;
- понятно, какие операции являются CPU bottleneck;
- пройдены capacity-профили для 1–2 игр и до 5 игроков на целевом профиле
  2 CPU / 4 GiB;
- отдельно измерены 1, 2 и 4 worker’а;
- отдельно отмечено, что пока не измерено с PHP-FPM/MySQL.

Результат не обязан доказать, что вся система готова к production. Его задача —
выявить архитектурно опасные решения до написания backend и показать, какие
части канона требуют пересмотра.
