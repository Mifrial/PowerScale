# Контекст разработки модуля Roleplay/Character (фронт)

> Живой документ шага разработки. Обновляется по мере продвижения: решение → запись.
> Дата старта: 2026-08-05. Ветка: `dev`.

## 1. Статус модуля (после шагов 2, 2.1, 2.4 и захода 3)

- Список `/characters` — карточки + `FilterBar` + `useFilteredRows` (шаг 1).
- Карточка `/characters/:id` — вкладки Обзор / Описание / Способности / Инвентарь / Обсуждение (шаги 2, 2.4); вкладка «Обзор» переработана на ссылочную модель (шаг 2.1).
- Редактор персонажа (заход 3, 2026-08-06): `/characters/new` (настройка свободного создания) → `/characters/new/editor`; `/characters/:id/edit` (copy-on-write черновик). Расчётное ядро `CharacterEditorService` + `RequirementEvaluator`, черновик `Store/characterDraft`, API `character.create`/`character.update`. Вкладки «Раса» и «Основа» реализованы; Личность/Развитие/Инвентарь — заглушки; «Описание» — простая.
- `init.ts` регистрирует: категорию прав `character` и плагинные тип/вкладку чата `character_discussion` (готово ранее, не трогаем).

## 2. Цель шага 2

**Карточка персонажа `/characters/:id`** по §7/§4 ТР: привязка к ревизии правил пространства (жёсткий инвариант БД §3), вкладки, доступ «свой vs чужой», встраивание обсуждения in-page.

Осознанно НЕ входят в шаг 2 (отдельные последующие шаги):
- `/characters/:id/edit` (редактор: Раса → Основа → Личность → Развитие → Инвентарь)
- `/characters/:id/versions`, `/characters/:id/migrate`, `/characters/:id/deactivate`
- вкладки «Заметки (только владелец)» из целевой таблицы §7; «Способности» — отдельной вкладкой (шаг 2.4), а не display-only в Обзоре
- сессионная модель (черновик в игре → модерация), copy-on-write

## 4.3. Решения шага 2.3 (логика и данные характеристик)

Контекст обсуждения (2026-08-05, переработка карточки): моки каталога приблизительны и не сверены с реальными правилами — наполняем правдоподобный набор для проектирования карточки.

| № | Решение | Дата |
|---|---------|------|
| D16 | Категория характеристики хранится в спеке правила (`CharacteristicSpec.group`: `primary` / `important` / `secondary` / `combat` / `base`) — в разных ревизиях набор характеристик может отличаться (особенно вторичных), группировка не зашита в код. Отсутствие группы → фолбэк `primary`. | 2026-08-05 |
| D17 | Все тайлы характеристик показывают **итоговое** значение; попап раскрывает состав: маленькая база + модификаторы. Производные (Восприятие = min(Внимательность, Реакция), Интеллект = min(Память, Мышление)) — композитный тайл: агрегат + базы рядом; каждая база кликабельна со своим попапом (свои модификаторы). Формула производности берётся из `CharacteristicSpec.formula` (коды парсятся из строки `min(a, b)`). | 2026-08-05 |
| D18 | Мастерство боя — отдельная секция (сейчас только ближний бой): тайл МББ (итог) + тайлы «Мастерство боя {оружие}» (МББ + бонус владения оружием, итог). Модификаторы владения взаимоисключающие, в значение МББ не суммируются. Состав тайла оружия: база + общее мастерство (Ближний бой) + владение инструментом. | 2026-08-05 |
| D19 | Условные модификаторы («+1 к общению для проверок на обман») — поле `scope` у `CharacteristicModifier`; в значение тайла не входят, в попапе помечаются «условно: …». Источник без правила — `sourceLabel` (напр. «Обстоятельства»). | 2026-08-05 |
| D20 | Пустые секции скрываются целиком: если характеристики категории нет — её блок не показывается; «Вторичные» обычно пусто. | 2026-08-05 |
| D21 | Значение характеристики — **размерное число** `{ base, size }` (`DimensionalNumberValue`), база от 3 до 5, а не обычное число: `CharacteristicValue.value` и `CharacteristicOverview.value` типизированы размерным числом; отображение через `DimensionalNumber.toString()` (при `size=0` → «5», иначе «5↑»). В formula-контекст (для формул атак) значение переводится в число `toNumber()`. | 2026-08-05 |
| D22 | Тайл характеристики компактный: имя и значение в **одну строку** (значение — размерное число), подпись-прогресс (для оружия) мелкой строкой ниже. Индикатор наличия модификаторов (стрелки/подсветка) из UI убран — выводим только итоговое значение; состав раскрывается по клику. | 2026-08-05 |
| D23 | Производная характеристика — компактный композитный блок: слева имя+значение агрегата и подпись формулы (человекочитаемая, напр. «Минимальная из Внимательность и Реакция» — имена баз в именительном падеже, склонение не делаем), справа колонка баз (имя + значение). Агрегат и каждая база кликабельны со своим попапом. | 2026-08-05 |
| D24 | Компактность данных: все характеристические значения в фикстурах приведены к базе 3–5; владение мечом снижено до 1 уровня → «Мастерство боя мечом 5» (база 3 + Ближний бой +1 + Владение +1). | 2026-08-05 |
| D25 | Тесты на страницу (`characterOverview.test.ts`, `mockCharacters.test.ts`) **удалены** — написаны преждевременно и тормозят итерации. Правило: тесты только на критичную инфраструктуру и только когда она готова. Остались инфраструктурные: `characterReference`, `formulaEvaluation`, `access`. | 2026-08-05 |
| D26 | Значения с ненулевой размерностью проверяются на данных: в Основных у Торвина Стойкость `{base:3,size:+1}` («3↑») и Магия `{base:4,size:-1}` («4↓») — проверка отрисовки маленькой/большой характеристики. | 2026-08-05 |
| D27 | В «Основных» сначала простые характеристики (по 4 на строку), затем производные (по 2 на строку) — компактнее. | 2026-08-05 |
| D28 | Попап характеристики: лёгкая оконтовка + адаптивная ширина (`width:max-content`, `max-width:420px`) — длинный текст не обрезается. Модификатор в формате «+1 от мастерства | Ближний бой 1»: значение, роль источника (`sourceRole` из типа правила), кликабельное правило с уровнем (`sourceLevel`); связка «→ цель» убрана. | 2026-08-05 |
| D29 | В секции «Мастерство боя → Ближний бой» плашки показывают короткие подписи (`shortName`): «Общее», «Меч», «Кинжал»; полное имя — в попапе и подписи-прогрессе. | 2026-08-05 |

| D31 | Подпись производной — короткое «Минимальная из →» (имена баз не перечисляются — они рядом справа). Подпись находится внутри кликабельной области тайла (проп `caption`), клик открывает попап. | 2026-08-05 |
| D32 | Плашки владения оружием — это тег оружия: label «Меч»/«Кинжал» (shortName), подпись-прогресс «Владение X N из M» убрана (избыточна). Полное имя способности — в попапе. | 2026-08-05 |
| D33 | Модификаторы одного источника (группа по `sourceRole`) **не складываются**: из группы берётся один с наибольшим плюсом и один с наибольшим минусом. Итог источника уточнён в D35: роли «от мастерства» и «от владения оружием» — разные источники и суммируются. | 2026-08-05 |
| D34 | **Переход на расчёт значений**: версия хранит только `base` характеристики (размерное число) и модификаторы; итог считается в карточке (`CharacteristicValue.base` вместо `value`). Моки больше не содержат рукописных итогов — нечего рассинхронизировать. | 2026-08-05 |

| D36 | Попап характеристики показывает заголовок по короткой подписи плашки (тег оружия «Меч», а не «Владение мечом»), строки «Значение» и «База» — размерные числа (напр. «3↑»), при отсутствии модификаторов — «Без модификаторов». | 2026-08-05 |
| D37 | Ресурс «Мана» в каталоге переименован в «Концентрация» (code `concentration`); у персонажей лимит 0 — ресурса нет, не отображается. | 2026-08-05 |
| D38 | Ресурс как характеристика: версия хранит `current` + `base` (базовый лимит) + `bonuses` (бонусы и штрафы лимита, не модификаторы); лимит = база + сумма дельт. Лимит 0 → ресурса у персонажа нет, плашка не рендерится (фильтр в сервисе). | 2026-08-05 |
| D41 | Ресурс размерный как характеристика: `current`/`base`/`max` — `DimensionalNumberValue` (безразмерный ресурс — размер 0). Ци Духа — размерный в «маленьких» (`↓`, размер −1): у Торвина значение `3↓`, лимит `8↓`; отображение и шкала по базам. | 2026-08-05 |
| D42 | Блок «Валюты» заменён на «Разное»: ОС/ОЛ/ОР — «очки», не «валюта» (ТР §6); деньги — монеты (`item.category: money`), не валюта. Состав: ОС (потрачено при создании), ОЛ и ОР (есть + «потрачено X / всего Y»), Деньги (сумма). Оформление — плашки в духе характеристик (имя + значение + подпись), 2 на строку. | 2026-08-05 |
| D43 | Версия хранит `points: CharacterPointsState` (osSpent, olSpent/olTotal, orSpent/orTotal) + `money: number` вместо `currencies`; DTO `Currency*` и справочник `CURRENCY_LABEL_BY_CODE` удалены. | 2026-08-05 |
| D44 | «Постоянная защита» вынесена в шапку карточки «Защита N» (N = сумма максимумов по группам `source_code` защит: защиты одного источника **не суммируются**, разные — суммируются). Каждый доспех — выделенная плашка-итем (как оружие в Атаках), внутри столбец его защит и сопротивлений с источником: «+5 защиты от доспеха · надёжность 3», «+3 защиты от поддоспешника · надёжность 2» (источник — source-правило по `source_code`, имя в нижнем регистре). Щит — отдельная плашка «— блокирование». | 2026-08-05 |
| D45 | Карточки «Защита» и «Атаки» — **на всю ширину, в столбик** (отдельные); итемы внутри каждой карточки — по пол-ширины (2 на строку, `cols="6"`). | 2026-08-05 |
| D46 | Плашка атаки — равномерное распределение слева/справа (3×2), не «подпись | значение»: слева «{оружие}», «{профиль}», «Дистанция {значение}»; справа «{N} точность», «{N} {родительный типа урона} урона», «{N} пробития». «N пробития» — всегда одно и то же слово («пробитие» — это значение/уменьшение защиты, не количество). Клик по плашке — попап с формулами урона и пробития (человекочитаемыми: «Сила», «Сила − 1», «число 5», «уровень {способность}»), плюс точность и дистанция. | 2026-08-05 |
| D47 | Склонение типов урона — константа `Constant/DAMAGE_TYPE_FORMS` (родительный для урона, дательный для сопротивлений; код → формы). | 2026-08-05 |
| D48 | Источники (тип `source`) всегда входят в срез ревизии — на них ссылаются слоты защит/сопротивлений кодом, карточка выводит имя источника. ## 4.10. Миграция персонажа на новую ревизию правил (план, 2026-08-13)

> Согласованный план (детали — ТР §7 «При переходе на новую версию правил», `/characters/:id/migrate`). Реализация по шагам: (А) очки ГМ + смена ревизии игры + модель кастомных предметов (game-спека §7.13), затем (Б) миграция персонажа (этот раздел). Нумерация решений — при реализации.

### Ключевые положения

- **Обе версии персонажа сохраняются.** Для standalone — `CharacterDetail.previousVersion` (последняя пред-миграционная); в игре — `active_version` (старая) и `pending_version` (мигрированная) у членства `game_characters`. Сравнение «до/после» — через общий `Game/Utils/membershipDiff` (diff двух `CharacterVersion`).
- **Инвентарь при миграции не перезакупается**: текущий список предметов и деньги персонажа переносятся как есть; проверка денег на закупку не выполняется (лимит — наличные). 
- **Невалидные предметы → кастомные (по умолчанию, авто-резолв, НЕ конфликт)**: правило отсутствует в новой ревизии → предмет становится «предметом мастера»: `ruleId: null`, `name` (старое имя правила), `description` (старое описание правила); `quantity/equipped/note/durabilityLeft` сохраняются. Полноценный механизм выдачи кастомных предметов мастером — будущий заход, модель закладывается сейчас.
- **Миграция — черновик (resumable)**: отдельный draftKey в `characterDraft` (на новой ревизии); можно прервать и продолжить позже.

### Классификация результата миграции (`CharacterMigrationService`)

| kind | Условие | UI |
|------|---------|----|
| `ok` | Чистый ремап: характеристики/ресурсы/бюджеты неизменны, все правила на месте, требования выполнены | Отчёт «изменений нет» + «Перейти на версию» |
| `resolved` | Отличия авто-резолвятся: значения характеристик/ресурсов пересчитаны, затраченная валюта изменилась (недобор — зелёным), кастомные предметы | Отчёт с подсветкой + «Перейти на версию» |
| `conflicts` | Серьёзные проблемы: удалённое правило (кроме предметов — они кастомные), невыполненные требования, **перерасход сверх реальных лимитов**, удалена раса | «Разрешить конфликт» → редактор на новой ревизии |

- **Перерасход бюджета** — конфликт (нельзя принять невалидную версию). При разрешении пользователь сам сбрасывает лишнее в редакторе.
- **Авто-сброс при конфликте**: способности/предметы/состояния/характеристики с удалённым правилом (предметы — в кастомные), способности с невыполненными требованиями; удалённая раса → сбрасывается (нужно выбрать новую).

- **`InventoryItem`**: `ruleId: string | null` + `name?`, `description?` (кастомный предмет). Рендеры (SheetCard, `CharacterOverviewService.buildInventory`, Editor/InventoryTab) адаптируются на `ruleId: null` (имя из `name`, категория «предмет» без спеки, без ссылки на правило).
- **`CharacterMigrationService`** (чистый, тестируемый):
  - Вход: `{ version, oldRules, newRules, newSpaceId, effectiveLimits }`.
  - Ремап всех ссылок `oldRuleId → code → newRuleId` (code глобально уникален — работает cross-space); предметы с несуществующим правилом → кастомные.
  - Пересчёт через `characterBuildService.fromVersion` + `characterEditorService.build` на новых правилах; **реальные лимиты персонажа** (для игровых = лимит игры + гранты ГМ, см. game-спека §7.13).
  - Выход: `{ kind, version, problems[], diffs[] }`.
- **API (мок)**: `character.migrate(characterId, { toRevision, toSpaceId })` (расчёт, не применяет), `character.applyMigration(characterId)` (обновляет версию + `previousVersion`).
