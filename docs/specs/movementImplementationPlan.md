# План реализации действий движения

## 1. Цель и граница первого этапа

Реализовать движение как открытый контур операций поверх существующих действий
и процессов. Первый этап не реализует:

- координаты и позиции;
- пиксели и фиксированную клетку как игровую единицу;
- facing и абсолютные направления;
- маршруты и геометрию;
- реальные collision;
- видимость battleground.

Первый этап реализует:

1. декларативные операции действий в каталоге правил;
2. permission и request движения;
3. единый агрегированный результат действия;
4. списание ОД в общем исполнителе;
5. сессионный `currentSpeed`;
6. расширяемый статус вынужденного прерывания для будущего battleground.

Основные источники согласования:

- `docs/specs/moveIdeaContext.md`;
- `docs/specs/battlegroundIdeaContext.md`;
- `draft-front_1.2ds/frontend-rules.md`.

При расхождении старых формулировок `moveIdeaContext.md` с этим планом сначала
зафиксировать расхождение и актуализировать контекст, а не реализовывать обе
модели одновременно.

## 2. Архитектурные границы

Перед изменениями изучить:

- `AbilitySpec` и `AbilitySpecBase`;
- `ActionComponent`, `ActionEffect`, `Formula`, `Requirement`;
- `ProcessSpec`, `ProcessStep`, `ProcessTransition`;
- `ActionExecutionService`, `ActionEffectService`;
- `ProcessSession` и `ProcessSessionService`;
- `MechanicEngine` и существующие обработчики;
- `GameApi`, игровые оверлеи и сессионные состояния;
- mock-правила действий и процессов.

Границы ответственности:

- `Rule` хранит типизированные декларации операций, выражений и prerequisites;
- `Character` поставляет актуально собранный профиль и `movementStep`;
- `Game` запускает действие, списывает ОД, агрегирует результат и хранит
  состояние игровой сессии;
- механика `movement_state` обновляет сессионный `currentSpeed` по результату
  целого действия;
- `Core/Engine` предоставляет точные value-операции;
- Vue-компоненты выбирают параметры, вызывают публичные фасады и отображают
  permission/result.

Целевые места реализации:

- `Roleplay/Rule/Dto/Ability/ActionOperation.ts` — открытый union
  `ActionOperation`;
- `Roleplay/Rule/Dto/Ability/MovementOperation.ts` —
  `MovementOperation`, `DistanceConstraint` и компонентные направления;
- `Roleplay/Rule/Dto/Ability/MovementDistanceExpression.ts` — выражения
  размерной дистанции;
- `Roleplay/Game/Dto/ActionResolution.ts` — агрегированный результат с
  горизонтальной и вертикальной дистанциями;
- `Roleplay/Game/Service/ActionExecutionService.ts` и его instance-реализация —
  preflight, списание ОД и единая resolution;
- `Roleplay/Rule/Service/Mechanic/MovementStateMechanic.ts` и регистрация
  обработчика — обновление сессионного `currentSpeed`;
- `Roleplay/Game/Interface/IGameApi.ts`, `GameApi.ts`, `Mock/mockGameApi.ts` —
  чтение и запись сессионного состояния;
- соответствующие `Roleplay/Rule/__tests__/Service`,
  `Roleplay/Game/__tests__/Service` и `Roleplay/Game/__tests__/Mock` —
  unit-тесты контрактов, execution и state mechanic.

Перед созданием файлов проверить фактическую раскладку `Instance` и соглашения
именования. Если публичный фасад и instance-реализация разделены иначе,
сохранить эти границы, изменив только конкретный путь.

Не создавать отдельный исполнитель движения, дублирующий
`ActionExecutionService`. Если текущий исполнитель специализирован под атаки,
сначала выделить общий этап исполнения действий, сохранив существующий
поверхностный API потребителей.

## 3. Открытый ActionOperation

Ввести открытый тип `ActionOperation` в естественном типовом слое Rule после
проверки текущей структуры. Тип не должен содержать конкретные игровые
движения.

Универсальные операции первого этапа:

```text
{ type: 'movement', ... }
{ type: 'turn', ... }
{ type: 'posture', ... }
```

`walk`, `run`, `sprint`, `jump` и `careful` не являются типами движка. Это
конкретные правила каталога, использующие одну или несколько универсальных
операций.

Одно действие и один `ProcessStep` могут содержать несколько операций:

```text
movement + turn
movement + posture
```

Операции резолвятся как части одного действия, но `currentSpeed` вычисляется
один раз по агрегированному результату всего действия.

Проверить, где естественно разместить `operations: ActionOperation[]`:

- в отдельном `ActionSpec`;
- в расширении action-ветки `AbilitySpec`;
- в `ProcessStep`;
- в общем контракте для action и process step.

`ActionComponent` оставить контрактом затрат/компонентов. `ActionEffect` не
перегружать описанием основной операции, если это нарушает его текущую
семантику.

## 4. MovementOperation

Сформировать структурированный контракт движения примерно с такой семантикой:

```text
movement:
  allowedDirections:
    horizontal: [front, flank, rear]
    vertical: [up, down]
  distance:
    horizontal?: DistanceConstraint
    vertical?: DistanceConstraint
  freeTurn:
    maxDegrees: integer
    free: boolean
```

`DistanceConstraint` содержит `min`, `max`, `minInclusive` и `maxInclusive`,
где `min` и `max` имеют тип `MovementDistanceExpression`. Дистанция задаётся
отдельно для каждой выбранной компоненты. Поэтому `front + up` — это одна
movement-операция с двумя независимыми ограничениями и двумя точными
дистанциями, а не неявный вектор и не одна общая длина.

В request передаются `horizontal.distance` и/или `vertical.distance`.
В `ActionResolution` сохраняются соответствующие requested/traversed
значения. Отсутствующая компонента представляется `null` и не участвует в
проверке диапазона; для расчёта скорости она нормализуется в точное нулевое
значение. Минимум и максимум каждой активной компоненты проверяются
независимо. Как минимум одна компонента и её положительная дистанция
обязательны.

Горизонтальные направления — только:

```text
front | flank | rear
```

Вертикальное направление является отдельной компонентой и может сочетаться с
горизонтальным:

```text
up | down
```

В permission хранятся допустимые горизонтальные и вертикальные компоненты. В
request передаются выбранные компоненты и их дистанции, а в агрегированном
результате — фактические компоненты и их дистанции. Чистое вертикальное
движение может иметь
`horizontalDirection = null`; полёт может иметь одновременно
`horizontalDirection = front` и `verticalDirection = up`. Не добавлять на
первом этапе `left/right`, absolute direction, координатные векторы или facing.

`freeTurn` — это только ограничение бесплатного поворота, выполняемого в
рамках данной movement-операции. Отдельная операция `{ type: 'turn', ... }`
остаётся самостоятельной и не должна смешиваться с этим полем.
`freeTurn` не списывает отдельную стоимость и не является причиной сброса
скорости, если в том же агрегированном действии есть положительное движение.
Самостоятельная `turn`-операция имеет собственную стоимость действия и
сбрасывает `currentSpeed`, как и любое действие без положительного движения.

Само действие спринта использует только горизонтальную компоненту движения.
Для prerequisite спринта учитывается горизонтальная компонента предыдущей
скорости; вертикальная компонента ей не мешает. Поэтому движение
`horizontalDirection = front` вместе с `verticalDirection = up` может открыть
спринт, если горизонтальная скорость достаточна. Будущие правила полёта могут
использовать обе компоненты без изменения базового контракта.

`maxStepCount` не должен быть обязательным дублирующим полем, если максимум
полностью выражается через `MovementDistanceExpression`. Если он нужен для
семантического отображения правила, хранить его отдельно от вычисленного
`maxDistance`.

Инварианты:

- выбранные горизонтальная и вертикальная компоненты request входят в
  соответствующие allowed directions;
- каждая активная дистанция точная и размерная;
- нулевая дистанция не является валидным движением;
- min/max сравниваются без `toNumber()`;
- `minDistance > maxDistance` соответствующей компоненты запрещает permission;
- ходьба и осторожное передвижение: `0 < distance <= 1 шаг`;
- бег: `1 шаг <= distance <= runSpeed`;
- спринт: `2 шага <= distance <= sprintSpeed`;
- прыжок вперёд: `horizontalDirection = front`, `0 < distance <= 1 шаг`;
- прыжок во фланг/тыл: `horizontalDirection = flank | rear`,
  `0 < distance <= шаг ↓2`;
- прыжок вверх: `verticalDirection = up`, `0 < distance <= шаг ↓2`.

Минимум ограничивает добровольный request. Будущее collision может завершить
начатое движение на положительной дистанции меньше минимума.

## 5. MovementDistanceExpression

Не расширять текущий общий `Formula` движковыми формулами движения: его текущая
семантика относится к другим доменам.

Создать отдельный узкий тип `MovementDistanceExpression`, который описывает
только необходимые значения:

- целое количество собственных шагов;
- `currentMovementStep × integer`;
- полную разницу размеров между двумя характеристиками;
- умножение разницы размеров на целый коэффициент;
- изменение размерности, включая `step ↓2`;
- сложение необходимых составляющих.

Минимальные выражения:

```text
1 × currentMovementStep
(2 + Δ) × currentMovementStep
(4 + 2 × Δ) × currentMovementStep
currentMovementStep ↓2
```

Коды характеристик Силы и Веса передаются из правила. Вычислитель не должен
знать фиксированные коды конкретных mock-правил.

Не создавать полноценный DSL. Сначала определить минимальное типизированное
дерево выражений, затем расширять его только при появлении реального правила,
которое нельзя описать существующими узлами.

## 6. Размерная арифметика

Изучить `Core/Engine/Value/DimensionalNumber.ts` и существующие тесты.

Пространственные значения:

- не представлять дробным JS `number`;
- не вычислять через `toNumber()`;
- не округлять саму дистанцию;
- не связывать с пикселями или фиксированной клеткой;
- сохранять размерность при сложении, сравнении и изменении размера.

Обязательные проверки:

```text
1↓5 > 0
1↓5 < 1↓
movementStep = 1↓5
боковой прыжок = 1↓7
```

Округление вниз разрешено только при вычислении `currentSpeed` из дистанции,
пройденной за несколько ОД. Оно выполняется в собственных шагах персонажа,
а не над исходной пространственной дистанцией.

## 7. Шаг и производные скорости

`currentMovementStep` — актуальный производный параметр профиля персонажа.
Он может зависеть от расы, возраста, эффектов и других правил. UI не является
доверенным источником шага.

Конкретные коэффициенты скоростей приходят из правил через
`MovementDistanceExpression`:

```text
runSpeed = (2 + Δ) × currentMovementStep
sprintSpeed = (4 + 2 × Δ) × currentMovementStep
```

Ограничения доступности:

- `runSpeed <= 1 шаг` — бег недоступен;
- `sprintSpeed < 2 шага` — спринт недоступен;
- диапазон с min больше max недопустим.

Шаг, физический размер, занимаемая область и досягаемость — независимые
понятия.

## 8. ActionResolution и агрегирование

Обычное действие и каждый `ProcessStep` формируют единый результат:

```text
ActionResolution:
  status
  spentActionPoints
  operationResults
  movement:
    horizontal:
      direction?
      requestedDistance
      traversedDistance
    vertical:
      direction?
      requestedDistance
      traversedDistance
  interruptionReason?
```

Правила агрегации:

- дистанции movement-операций одного действия суммируются отдельно по
  горизонтальной и вертикальной компонентам;
- turn и posture дистанцию не добавляют;
- movement-компоненты одного действия не должны иметь конфликтующих
  направлений на одной оси;
- действие может содержать одну горизонтальную и одну вертикальную компоненту;
- конфликтующие направления на одной оси получают `mixed`;
- `mixed` в горизонтальной компоненте не удовлетворяет prerequisite `front`;
- `currentSpeed` обновляется по результату всего действия, не по операциям.

## 9. Collision-контракт будущего battleground

На первом этапе реальный collision не реализуется, но контракт результата
должен быть готов к подключению battleground:

- collision после положительного перемещения сохраняет положительную
  компонентную `traversedDistance`, даже если она меньше добровольного
  `minDistance` этой компоненты;
- движение завершается вынужденным прерыванием с причиной `collision`;
- collision до начала движения даёт `traversedDistance = 0` в соответствующей
  компоненте прерванного или неуспешного результата;
- нулевой результат не считается движением и не обновляет `currentSpeed`;
- стоимость ОД уже списана и не возвращается;
- collision не превращается в добровольный запрос дистанции меньше минимума.

Для тестов этого контракта использовать внедряемый mock spatial resolver:
реальный battleground и геометрия на первом этапе отсутствуют, но execution
должен уметь получить от resolver частичный положительный результат,
нулевой результат и статус `collision`.

## 10. Сессионный currentSpeed

Не использовать отдельный `lastMovement`. Хранить обязательное актуальное состояние
участника игровой сессии:

```text
currentSpeed:
  horizontal:
    stepsPerActionPoint: integer
    direction: front | flank | rear | null | mixed
  vertical:
    stepsPerActionPoint: integer
    direction: up | down | null | mixed
```

Нулевое состояние — это объект с `horizontal.stepsPerActionPoint = 0`,
`vertical.stepsPerActionPoint = 0` и `null` направлениями, а не специальное
значение, нарушающее форму состояния. Сокращение `currentSpeed = 0` ниже
означает именно этот объект.

Если действие потратило `N` ОД, горизонтальная и вертикальная скорости
вычисляются независимо по соответствующим фактическим дистанциям:

```text
horizontalStepsPerActionPoint =
  floor(exactDimensionalDivision(horizontalDistance, currentMovementStep) / N)

verticalStepsPerActionPoint =
  floor(exactDimensionalDivision(verticalDistance, currentMovementStep) / N)
```

Каждый компонент `currentSpeed` получает своё целое значение. Сначала
соответствующая фактическая дистанция и `currentMovementStep` сравниваются и
делятся как точные размерные значения, затем `floor` применяется только к
итоговому количеству собственных шагов за один ОД. Исходные дистанции остаются
точными в `ActionResolution`. Округление должно быть отдельной операцией, не
через абсолютные пиксели, клетки или `toNumber()`.

Положительное движение меньше одного собственного шага допустимо. В этом
случае соответствующая компонента может получить
`stepsPerActionPoint = 0`, но её положительное направление сохраняется.
Ноль здесь означает «меньше одного полного шага за ОД», а не отсутствие
движения. Такая скорость не удовлетворяет prerequisite спринта.

Инварианты состояния:

- компонент с нулевой фактической дистанцией получает
  `stepsPerActionPoint = 0` и `direction = null`;
- `mixed` допустим только у компоненты с положительной фактической
  дистанцией и конфликтующими направлениями;
- `mixed` не сохраняется в нулевом состоянии.

После любой траты ОД:

1. пройти preflight валидного действия;
2. списать ОД;
3. сбросить `currentSpeed` в 0;
4. зарезолвить всё действие;
5. если агрегированный результат содержит положительное движение, вычислить
   новый `currentSpeed`.

Следствия:

- действие без движения → `currentSpeed = 0`;
- поворот → `currentSpeed = 0`;
- posture → `currentSpeed = 0`;
- атака или проверка → `currentSpeed = 0`;
- движение + поворот/posture → скорость вычисляется по движению;
- collision после положительного движения → соответствующая компонента скорости
  вычисляется по фактически пройденной дистанции;
- collision до начала движения → обе компоненты скорости остаются 0.

## 11. Механика состояния

Отдельное системное правило активирует механику `movement_state`.

Механика:

- получает агрегированный `ActionResolution`;
- обновляет `currentSpeed` один раз за целое действие или `ProcessStep`;
- не знает кодов «Бег», «Спринт», «Прыжок» и других конкретных правил;
- не обрабатывает внутренние операции отдельно;
- сбрасывает скорость, если положительного движения в результате нет.

Проверить интеграцию с существующим `MechanicEngine` и выбрать событие уровня
завершения действия. Не использовать механику для вычисления конкретной
формулы движения: формулы приходят из правил.

## 12. Prerequisite спринта

Условие входа в спринт должно быть декларативным и не ссылаться на код
предыдущего правила:

```text
previous action movement:
  currentSpeed.horizontal.direction === front
  currentSpeed.horizontal.stepsPerActionPoint >= 2
```

Любое будущее движение, включая полёт, сможет удовлетворить условию, если его
агрегированный результат имеет горизонтальное направление `front` и достаточную
горизонтальную скорость. Вертикальная компонента не влияет на это условие.

Если между действиями шаг персонажа изменился, уже сохранённый целочисленный
`currentSpeed` не пересчитывается задним числом: он является результатом
последнего действия. Новый шаг используется при следующем вычислении скорости.
Это решение нужно отразить в `moveIdeaContext.md`.

## 13. Порядок исполнения и ОД

Разделить:

```text
preflight:
  правило
  права
  доступность
  prerequisite
  направление
  диапазон
  наличие ОД

execution:
  списание ОД

resolution:
  выполнение ActionOperation[]
  агрегирование ActionResolution
  movement_state
```

Невалидный запрос не является начавшимся действием и не списывает ОД.
Валидно начавшееся действие сначала списывает ОД, затем резолвится. Collision,
включая столкновение сразу после начала, не возвращает ОД.

## 14. ProcessStep

Расширить `ProcessStep` отдельным типизированным `operations:
ActionOperation[]`, если архитектурный анализ подтвердит, что это естественная
граница.

Каждый шаг процесса:

- имеет собственную стоимость;
- выполняется как одно действие;
- формирует один `ActionResolution`;
- сохраняет существующий normal/emergency interruption contract;
- обновляет `currentSpeed` только после агрегированного результата шага.

Не вводить отдельные типы процесса для бега или спринта. Переход в спринт
описывать декларативным prerequisite результата предыдущего действия.

## 15. Mock-правила

Добавить конкретные правила только в mock-каталог, используя универсальные
операции:

- поворот — `turn`, 1 ОД, не более 180°;
- осторожное передвижение — `movement`, 2 ОД, `0 < distance <= 1 шаг`,
  направления `front/flank/rear`;
- ходьба — `movement`, 1 ОД, `0 < distance <= 1 шаг`, только `front`;
- бег — процесс, части по 1 ОД, `1 шаг <= distance <= runSpeed`;
- спринт — процесс, части по 1 ОД, `2 шага <= distance <= sprintSpeed`,
  prerequisite по `currentSpeed` и `front`;
- прыжок — `movement`, 3 ОД: горизонтальная компонента
  `front` — до 1 шага, `flank | rear` — до `шаг ↓2`, вертикальная компонента
  `up` — до `шаг ↓2`; горизонтальная и вертикальная дистанции передаются
  своими компонентами;
- после бега/спринта дальность прыжка вперёд — до 2 шагов;
- упасть/встать — `posture`, 3 ОД;
- положение лёжа — состояние с ограничениями доступных правил и
  согласованными модификаторами.

Конкретные названия и коды этих правил не должны появляться в движке,
вычислителе expressions или `movement_state`.

## 16. API и состояние Game

Добавить обязательное Game API/mock-хранилище для `currentSpeed` участника:

- получить состояние по `gameId` и `entityKey`;
- сохранить его после целого действия или шага процесса;
- сбрасывать после действия без положительного движения;
- не помещать в `CharacterVersion`;
- регистрировать сервис через существующий ServiceLocator.

Не смешивать `currentSpeed` с `ProcessSession`: процесс хранит текущий шаг
процесса, механика движения — актуальную скорость последнего действия.

## 17. UI

После стабилизации доменных контрактов:

- показывать permission, диапазон и допустимые направления;
- передавать выбранные горизонтальную/вертикальную компоненты направления и
  точную `distance`;
- запрещать нулевой запрос;
- не показывать бег при недоступной скорости;
- не показывать спринт без prerequisite;
- использовать существующий UI процессов;
- отображать размерные значения без преобразования в дробные JS-числа;
- держать расчёты в сервисах и derived state, не в Vue-шаблонах.

## 19. Документация и критерий завершения

После реализации:

- актуализировать `docs/specs/moveIdeaContext.md`;
- при необходимости добавить в `docs/tr/TR.md` ссылку на итоговый контракт;
- не дублировать дизайн в `battlegroundIdeaContext.md`;
- описать будущий адаптер, который заменит абстрактный результат фактическим
  `traversedDistance` и статусом collision.

Первый этап считается завершённым, когда игрок может выполнить валидное
абстрактное действие движения или шаг процесса с точной дистанцией, корректным
списанием ОД, единым `ActionResolution` и обновлением `currentSpeed`, при этом
координаты персонажа не изменяются.
