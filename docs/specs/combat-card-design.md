# Дизайн боевой карточки в чате игры — принятые решения

> Дата: 19.08.2026. Живой документ обсуждения AI + автор. Статус: **реализовано** (ядро 2026-08-19, компактность CD-13
> 2026-08-22).
> Фиксация: ТР §8 (чат игры) и очередь §14 п.6.

## 0. Что это

Боевая карточка — интерактивная сводка персонажа в контексте игрового чата (вкладка «Чат игры»), по образцу
карточки персонажа (все секции обзора; вопрос компактности — отдельный заход). Ключевое отличие — встроенные
действия:

1. **Кубик у каждой характеристики** — мгновенный бросок этой характеристики в игровой чат.
2. **Звёздочка у каждой характеристики** — добавить бросок характеристики на панель быстрых бросков игры
   за конкретно этого персонажа (макрос).
3. **Быстрая правка ресурсов** `+/-` в пределах лимита.
4. **Быстрая правка состояний**: number — попап со значением; dimensional (горение) — размерная сила; отравление — яд, тип урона и сила; флаги — «Убрать»; «добавить любое state-правило ревизии».

Изменения ресурсов/состояний живут в игровом оверлее (домен Game), применяются игрой автоматически, а после
игры уходят на модерацию как изменение персонажа (кроме НПС — применяются сразу).

## 1. Анализ существующего (готовые кирпичи)

- **Просмотр листа в игре**: `SheetCard` (по видимым секциям), view-model `CharacterOverviewService.build(version, rules)`
  (характеристики/ресурсы/состояния/защита/атаки), движковые значения — `characterEditorService.build`
  (паттерн `Utils/initiativeCharacteristic`).
- **Броски**: `RollEngine` + правила ревизии; пул из характеристики — база движкового значения, размерность уходит
  в `dieSize` броска (размерная характеристика `3↓` → 3 куба, итог отдаётся «↓1»); сложность/грани — правило
  «Бросок» ревизии. Отправка броска в чат — паттерн `InitiativeDialog`
  (`chatStore.sendMessage(text, [{type: ROLL_ATTACHMENT_TYPE, payload: result}], chatId, speaker)`;
  процессор вложений идемпотентен — готовый `DiceRollResult` проходит как есть).
- **Модерация**: `GameCharacterMembership` (activeVersion/pendingVersion/hasDraft), `Utils/membershipDiff`
  (поэлементный diff, включая ресурсы и состояния), `moderateCharacter` (approve/reject). Кнопка «Остановить сессию»
  в `GameChatTab` (status → in_process + submit боевых изменений; `completed` — отдельно, селектором в форме игры).
- **Участники боя**: `GameInitiative.participants` (kind character/npc, entityId), approved-персонажи
  (`fetchGameCharacters`) и активные НПС (`getNpcs`). `GameChatTab` уже грузит memberships/npcs/rules/mechanics.

## 3. Модель данных (Game domain)

```ts
// Dto/GameCombatOverlay.ts
type CombatEntityKey = `character:${number}` | `npc:${number}`;

interface GameCombatOverlay {
  gameId: number;
  entityKey: CombatEntityKey;
  kind: "character" | "npc";
  /** Переопределения текущих значений ресурсов (по ruleId) — эффективное current = оверлей ?? версия. */
  resources: { ruleId: string; current: DimensionalNumberValue }[];
  /** Актуальный список состояний в бою (полный). Эффективное states = оверлей.states ?? версия.states. */
  states: CharacterStateValue[];
  updatedAt: string;
}
```

- Оверлей — per game: `mockGameCombatOverlays: Map<gameId, Map<CombatEntityKey, GameCombatOverlay>>` (как `mockGameInitiative`).
- Пустой/отсутствующий оверлей ⇒ игра читает версию как есть. Первая мутация создаёт запись оверлея.
- Для НПС мутации пишут сразу в `npc.version` (без оверлея/модерации) — поведение в моке.

**Быстрые броски:**

```ts
// Dto/GameQuickRoll.ts
interface GameQuickRoll {
  gameId: number;
  entityKey: CombatEntityKey;
  characteristicRuleId: string;
}
// Хранилище: Map<gameId, Map<entityKey, string[]>> (ruleId характеристик, порядок добавления).
```

**API (IGameApi):**

- `getCombatOverlays(gameId)` → `GameCombatOverlay[]` (все approved-персонажи + активные НПС, включая пустые).
- `setCombatResource(gameId, entityKey, ruleId, current)` — правка current (UI вычисляет в пределах лимита);
  валидация: ресурс есть в эффективной версии, `0 ≤ current.base ≤ limit` (лимит = база + Σ бонусов в базовых
  пунктах шкалы ресурса; размерная шкала не сплющивается — `1↓` остаётся `1↓`).
- `addCombatState(gameId, entityKey, state: CharacterStateValue)` / `setCombatStateValue(gameId, entityKey, index, value?)` /
  `replaceCombatState(gameId, entityKey, index, state)` / `removeCombatState(gameId, entityKey, index)` — правка состояний (список повторов, индекс в списке; `replace` — сила DOT / блок яда целиком).
- `getQuickRolls(gameId)` → `Record<CombatEntityKey, string[]>`; `addQuickRoll(gameId, entityKey, ruleId)`;
  `removeQuickRoll(gameId, entityKey, ruleId)`.
- `submitCombatChanges(gameId)` — вызывается при «Остановить сессию» (CD-2), не публичный UI.

**Эффективная view (для карточки/показа):** `Utils/combatEffectiveState` — версия (membership.activeVersion / npc.version)

- оверлей; возвращает ресурсы (current из оверлея) и состояния (states из оверлея). Остальное — из версии.

## 4. Модерация (поток + мерж)

1. Во время игры мутации пишут в оверлей. `hasCombatChanges(character)` = в оверлее есть ресурсы или
   `states` отличается от `version.states`.
2. **«Остановить сессию»** (GameChatTab → `changeStatus('in_process')`): после успешного `updateGame`
   вызывается `submitCombatChanges(gameId)`: для каждого approved-персонажа с изменениями —
   `baseline = clone(activeVersion)`, `proposed = baseline + оверлей` (resources current, states) →
   `membership.pendingVersion = proposed`, `membershipStatus = 'pending'`, `hasDraft = false`.
   Оверлей сохраняется (источник для мержа). Сессия (playing → in_process) не трогает терминальный
   статус игры: `completed` выставляется отдельно (селектор статуса в форме игры).
3. Вкладка «Модерация»: существующий `membershipDiff(active, pending)` — покажет только изменённые поля
   (ресурсы/состояния). Approve/reject — существующие кнопки.
4. **Approve** (`moderateCharacter`): если у членства есть оверлей → **мерж**: применить поля оверлея
   (current ресурсов с клампингом к лимиту актуальной версии, `states` — заменой списка) на `versions[id]`
   (актуальную версию персонажа — standalone-правки других полей сохраняются), `syncCharacterVersion`,
   оверлей очистить, `status='approved'`. Без оверлея (обычная подача/миграция) — существующий overwrite.
5. **Reject**: оверлей очистить, `pendingVersion=null`, `status='rejected'`.

Оговорка мержа: если игрок параллельно правил в standalone-редакторе те же ресурсы/состояния — результат игры
(оверлей) приоритетен для изменённых полей.

## 5. UI — боевая карточка

- **Слайд-овер** (`CombatCardPanel`, v-navigation-drawer temporary справа от чата) по клику на участника.
- Источники открытия: строки шкалы инициативы (InitiativeTrack — кликабельны только при CD-6, `emit('open-card', entityKey)`),
  кнопка у селектора «от лица кого» в поле ввода чата (вместо иконки `mdi-account-voice`).
- Состав (CD-9 + CD-13): шапка + вкладки. **Обзор** — сворачиваемые секции (шеврон у заголовка): характеристики
  (3 колонки, кубик/звезда; Вес в важных), бой, ресурсы (тайлы), состояния, защита/атаки тайлами листа.
  Разное (ОС/ОЛ/ОР) на боевой карточке не показывается. **Способности** — `AbilityTab` (избранное только у персонажа).
  **Инвентарь** — имя, кол-во, моды, экип (`setCombatItemEquipped`: персонаж → `overlay.sheet`, НПС → версия).
- **Права (CD-6)**: карточка, ОД и истощение в шкале — владелец approved-персонажа или ГМ; иначе строка шкалы не открывает лист и не показывает метрики.
- **Ресурсы (CD-12)**: тайлы в сетке (как характеристики, CD-13 — 3 колонки), попап по клику — текущее/максимум/база +
  бонусы лимита; `+/-` по шагу 1 в базовых пунктах, кламп `[0..limit]` (лимит = база + Σ бонусов в шкале ресурса).
  Изменение — `setCombatResource`.
- **Состояния (CD-10)**: outlined-тайл как ресурсы, сетка **2 в ряд**. Одна запись = один тайл (одинаковые типы рядом). Слева иконка + имя + срок (для увечья: интервал −1 × сила, или «пост.»), справа сила. Клик — попап: number — `ClampedNumberField` + «Изменить»; горение — размерная сила; отравление — яд / тип / сила (добавление — диалог, не пустой flag); прочий флаг — «Убрать». 0 / сила ≤ 0 удаляет запись. «Добавить состояние» — пикер (`v-menu` attach, z-index 2200).
- **Кубик (CD-7)**: `Utils/characteristicRoll` — `rollCharacteristic(view, rules, mechanics)` (RollEngine),
  спецификация `characteristicRollSpec`: пул = база движкового значения (минимум 1 куб), faces/efficiency из
  правила «Бросок», размерность значения → `dieSize` броска (итог ролла показывается «в размерности», `3↓` → 3 куба);
  отправка `chatStore.sendMessage(имя характеристики, [pre-computed result], chatId, speaker)`
  — speaker персонажа карточки (`{kind:'character',...}`), для НПС — `{kind:'npc',...}`.

## 6. UI — быстрые броски (звёздочка)

- Блок **«Быстрые броски»** в сайдбаре игрового чата (рядом со шкалой инициативы).
- Показывает записи участника, выбранного **селектором «от лица кого» в чате** (активный источник речи:
  ручной выбор + авто-подстановка активного хода инициативы; отдельного селектора у блока нет).
  Для «Ведущий» (speaker `gm`) сущности нет — блок пуст.
- Запись = характеристика/боевой стат/оружие; клик — бросок (как кубик), иконка «×» — снять звёздочку.
  Звёздочка в карточке — добавить (гейт CD-6). Оружие в блоке помечается секцией «ББ:»/«ДБ:» (одинаковое оружие
  ближнего/дальнего боя различается; ruleId тайла оружия — `combat:{melee|ranged}:{имя}`).
- Резолюция записи: ruleId → характеристика/стат/оружие обзора (`quickRollRecords` + `resolveQuickRollRecords`,
  не-характеристики отбрасываются); бросок — как кубик карточки (speaker персонажа/НПС).
  Карточка выбранного участника — кнопкой у селектора в чате (CD-5).
- Хранилище per (game, entity) — `mockGameQuickRolls` (прототип; модель допускает перенос на бэк).
