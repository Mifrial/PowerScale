# Дизайн типов правил «Раса» и «Вид» — принятые решения

> Дата: 31.07.2026. Живой документ обсуждения AI + автор. Финальные решения зафиксированы
> после полного обсуждения (см. историю чата). Отличается от наброска в ТЗ/ТР — теперь
> источник истины для реализации.

## 1. Иерархия: Вид → Подвид → … → Раса

Цепочка: **Вид → Подвид → … → Раса**. Все узлы, кроме последнего, — «виды» (тип `species`),
последний — «раса» (тип `race`).

- **Вид** — корневой узел дерева, `parent_race_code = null`.
- **Подвид** — узел дерева, `parent_race_code` указывает на родителя (`species`).
- **Раса** — **терминальная** точка цепочки, единственная, из которой генерится персонаж.
  От расы НЕ наследуются (у расы нет детей). Родитель расы — всегда `species`.
- Вид и подвид — **один тип `species`**, различаются только наличием `parent_race_code`.
- Виды/подвиды понадобятся позже для **древовидного выбора расы** в селекторах.

**Что где живёт:**

| Свойство | Вид/Подвид (`species`) | Раса (`race`) |
|----------|------------------------|---------------|
| `parent_race_code` | да (вид: null; подвид: species) | да (всегда species) |
| `cost_os` (стоимость в ОС) | нет | да |
| `characteristics` (характеристики) | нет | да |
| `abilities` (способности) | да (наследуются расами цепочки) | да (свои + наследуемые) |

- Способности вида/подвида **наследуются** расами вниз по цепочке (вид → подвид → раса).
- **Циклы** возможны только среди `species` (A → B → A); раса — лист, в цикле участвовать
  не может. Валидация проверяет цепочку `parent_race_code` видов.

## 2. Общие принципы (наследуются из ability-resource-design.md)

- Все строковые ссылки между правилами — по семантичному `code`, НЕ по внутреннему `id`.
- `Rule`/`RuleVersion` уже содержат `code`; числовые внутренние id (`spaceId`, `tagId`,
  `mechanicId`, `source_id`) не трогаем.
- Модификаторы характеристик и «дать характеристику сразу» (напр. Магия) — **уже покрыты**
  дарами способностей `characteristic_modify` / `characteristic` из `abilityTypes.ts`.
  Раса лишь объявляет **стартовый профиль** характеристик; сами модификаторы — зона
  способностей, отдельно для расы не вводятся.

## 3. Схема SpeciesSpec (тип `species`)

```ts
interface RaceAbilityRef {
  ability_code: string
  automatic: boolean        // true = бесплатная/авто, false = доступная (расовая/видовая)
}

// Вид / подвид — чистый узел дерева
interface SpeciesSpec {
  parent_race_code: string | null   // вид: null; подвид: родитель (type='species')
  abilities: RaceAbilityRef[]       // наследуются расами цепочки
}
```

## 4. Схема RaceSpec (тип `race`)

```ts
type RaceCharacteristicMode = 'fixed' | 'purchased'

interface RacePurchaseLevel {
  cost: number                  // потрачено ОС (1, 2, 3…)
  value: DimensionalNumber      // итоговое значение характеристики
}

interface RaceCharacteristic {
  characteristic_code: string
  mode: RaceCharacteristicMode  // per-characteristic (решение автора)
  base: DimensionalNumber       // fixed: фикс. база; purchased: минимум (значение за 0 ОС)
  purchase?: RacePurchaseLevel[] // только при mode='purchased': лестница «за N ОС → значение»
}

// Раса — играбельная, терминальная точка цепочки
interface RaceSpec {
  parent_race_code: string | null   // всегда type='species'
  cost_os: number                   // стоимость расы в ОС (отрицательная = даёт ОС)
  characteristics: RaceCharacteristic[]
  abilities: RaceAbilityRef[]       // свои + наследуемые от предков (species-цепочки)
}
```

### 4.1 Два режима характеристик

- **`fixed` (новые правила):** раса даёт характеристику с **фиксированным значением**
  (Ловкость 4↑). Дальше значение модифицируют общие Черты дарами `characteristic_modify`
  (+/−, источник); часть черт может сразу «дать» характеристику целиком (`characteristic`-дар).
  `purchase` отсутствует.
- **`purchased` (старые правила):** раса задаёт **базовый минимум** + таблицу закупки
  «за N ОС → значение». Пропуск уровня просто не перечисляется списком (массив пар
  `{cost, value}`, НЕ индексированный — без null-дырок). `0`/отсутствие характеристики
  в профиле расы = характеристики у расы нет.

Пример таблицы закупки Силы:
```
[Сила] [Минимум 3] [за 1 ОС → 4] [] [за 3 ОС → 5]
```
как данные:
```ts
{ code: 'strength', mode: 'purchased', base: { base: 3, size: 0 }, purchase: [
    { cost: 1, value: { base: 4, size: 0 } },   // за 1 ОС → 4
    // cost 2 — пропуск (уровень недоступен)
    { cost: 3, value: { base: 5, size: 0 } },   // за 3 ОС → 5
] }
```

### 4.2 Редактор

Панели `RaceEditor.vue`:
- **Общее** — `RuleEditorBase` (название, описание, механика, признаки).
- **Раса** — родитель (autocomplete по `type='species'`, исключить себя) + стоимость ОС
  (`ClampedNumberField`, допускает отрицательные).
- **Характеристики** — строки: выбор характеристики + переключатель режима `fixed`/`purchased`:
  - `fixed` → `DimensionalNumberInput` (база);
  - `purchased` → `DimensionalNumberInput` (минимум) + список уровней `{cost, value}` с +/−.
- **Способности** — строки: выбор способности + переключатель «бесплатная/доступная»
  (`automatic`).
- **Превью наследования** — если есть родитель (`species`), показать наследуемые способности
  из цепочки предков (обход `parent_race_code` вверх).

Панели `SpeciesEditor.vue`:
- **Общее** — `RuleEditorBase`.
- **Родитель** — autocomplete по `type='species'`, исключить себя.
- **Способности** — как у расы (строки `{ability_code, automatic}`).

### 4.3 Карточки

`RaceCard.vue` (макет `makets/space-rule-view.html`):
- Стоимость ОС («8 ОС» / «+2 ОС»), родитель (`species`).
- Характеристики: `fixed` → «Ловкость 4↑»; `purchased` → «Сила: минимум 3 · за 1 ОС → 4 ·
  за 3 ОС → 5».
- Свои способности — чипсами; наследуемые от предков — отдельным блоком (помечены
  «от предка»).

`SpeciesCard.vue` (минимальная): родитель + способности.

## 5. Манифест блоков и prune

Для `RaceSpec`/`SpeciesSpec` дискриминант — сам тип правила (race/species), поэтому в
прунере нет необходимости: у `race` поля `cost_os`/`characteristics` всегда в наличии,
у `species` их нет вовсе. Общий паттерн «prune на границе эмита» не требуется; пустые
массивы (`characteristics`, `abilities`) на эмите допустимы.

## 6. Валидация ссылок при публикации

- В `ruleValidation.ts` расширяется `collectSpecRefs`/`validateRuleReferences`:
  - `race`: `parent_race_code` → тип `species`; `characteristics[].characteristic_code` →
    тип `characteristic`; `abilities[].ability_code` → тип `ability`.
  - `species`: `parent_race_code` → тип `species`; `abilities[].ability_code` → тип `ability`.
- Новая структурная валидация:
  - `validateRaceStructure`: `cost_os` — число; пустые/дублирующиеся коды характеристик и
    способностей; у `purchased`: `cost > 0` и уникальные `cost`.
  - `validateSpeciesStructure`: пустые/дубли `ability_code`.
  - **Циклы среди `species`** по цепочке `parent_race_code` (A → B → A).
- Вызовы подключаются в `publishDraft` рядом с существующими (`validateRuleReferences`,
  `validateAbilityStructure`).

## 7. Моки

- `species`: «Эльфы» (вид, `parent = null`), «Лесные эльфы» (подвид, `parent = 'elves'`).
- `race`: «Человек» (пример `purchased`-режима), «Эльф» (`fixed`: Ловкость 4↑, Восприятие 3;
  наследует от вида «Эльфы»), «Лесной эльф» (`parent = 'wood-elves'`).
- Способности-моки «Острый слух», «Ночное зрение» (зона `os`, `automatic`) — чтобы
  срез ссылок был консистентным; у вида «Эльфы» — «Острый слух» (наследуемый), у расы «Эльф» —
  «Ночное зрение».

## 8. Отложенное

- **Древовидный селектор рас** при создании персонажа (группировка по видам/подвидам) —
  зона Character, позже.
- **Смесь рас** (future) — `race_mix` в `character_versions.data_json`; на уровне правил
  иерархии `parent_race_code` достаточно.
- Играбельность узла — определяется **типом** (`race` vs `species`), отдельный флаг не нужен.

## 9. Открытые вопросы

- Нужен ли «краткий профиль» вида/подвида (заголовок для селектора) — вероятно, будет
  собираться из способностей; отдельное поле пока не вводим.
