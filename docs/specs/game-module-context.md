В модуле `Roleplay/Game` уже есть (не трогаем):

## 2. Цель захода

Замкнуть группу Roleplay: игры используют **правила** (пространство + ревизия, лимиты ОС/ОР/денег), **персонажей** (roster + модерация), **чат** (game chats), **Core** (права/авторизация).

Текущий заход — **Фаза 1 «Ядро Game»** (объём согласовывается): доменная модель + API + моки + стор; список `/games`; создание `/games/new`; карточка `/games/:id` (шапка + вкладки); гейтинг доступа (route-perm + предикаты per-game). UI — в стиле модуля Character (списки/карточки/табы/попапы), НЕ по макетам `makets/game-*.html`.

Осознанно НЕ входят в Фазу 1 (отдельные заходы):

- roster/модерация персонажей (`/games/:id/members|invitations|characters|moderate`, модель `game_characters` active/pending/draft)
- создание персонажа «через игру» (в Character отложено, ТР §7)
- встроенный чат игры/обсуждение в карточке
- добыча (`game_loot`), НПС, летопись, инициатива

## 6. Гэпы и риски

**Гэпы:**

- Нет доменной части игр (DTO/API/стор); страница — стаб.
- Пер-игровые права (`game.edit`, `game.moderate`, `game.manage`, `game.edit_inventory`) живут на `game_member_permissions` и на фронте требуют учёта роли в игре + индивидуальных прав — это не глобальные `AccessService`-ключи.
- Привязка игры к ревизии правил должна быть согласована с моками Space (инвариант как у персонажей: `(spaceId, spaceCode, rulesRevision)`), иначе ссылки на `/space/{code}/{N}` и лимиты будут «от балды».
- Модель модерации D117 уже зафиксирована (ТР §7.8, спека Character), реализуется в Game — в Фазе 2.

**Риски:**

- Нарушение направления зависимостей (случайный импорт Character/Rule/Chat → Game). Проверять каждый новый импорт.
- Согласованность моков: владельцы/участники игр должны существовать в `mockUsers`; ревизии — в `mockSpaces`; game-чаты (`game`/`game_discussion`) — в `mockChat`.
- Встраивание обсуждения игры (Фаза 3) — не сломать глобальный чат-стор (паттерн D7 Character: openChat/canInChat, очистка activeChatId/stopSync).

## 7.20. «Правила игры» — дизайн (план, 2026-08-16)

> **Статус: анализ согласован; реализация по итогам уточнения НЕ по плану V2, а по решению пользователя — «Уникальные правила» как текстовые записи персонажа (см. §7.21).**
> **Слой 1 (починка резолюции правил из ревизии) реализован 2026-08-21** — `Rule/Utils/ruleRevisionResolver.ts` + проброс `spaceId`/`rulesRevision` через `ChatRulesContext` → `ChatThread`/`ChatMessenger` → `RuleChip` → `RuleSlider`; `CharacterDetailPage` передаёт контекст ревизии в `RuleSlider`. > **Закрытие §7.20 (2026-08-21):** вкладка «Правила» в карточке игры **отклонена** — дублирует браузер ревизии пространства `/space/{code}/{N}` (карточка уже ссылается кнопкой «Правила: {spaceName} v{N}» в Обзоре). V2 (кастомные предметы ГМ) поглощено §7.21 (текстовые записи на персонаже). Спойлер (§7.19) — отложен, не в этом релизе.

**Разведение понятий (три слоя):**

- **Слой 1 — просмотр правил игры**: игра всегда привязана к ревизии и берёт правила из неё. «Правила игры» = вкладка-браузер правил ревизии игры (типы + поиск + карточки → слайдер). Плюс — **починка общих слайдеров/чипов правил**: они должны резолвиться из контекста ревизии (`spaceId` + `rulesRevision`), а не из глобального каталога (сейчас `RuleSlider` грузит `ruleStore.fetchRule(id)` — глобально, поэтому «сломан везде»: показывает не версию ревизии, а каталог).
- **Слой 2 — GM-расширения на ходу**: ГМ придумывает свой item (название+описание достаточно) и добавляет в игру; способности на ходу — тоже полезно, но сложнее.
- **Слой 3 — «документ правил»** (страница с разделами/подразделами, импорт большого дока) — **отложен** (решение пользователя).

**Варианты (слои 1+2):**

- **V1 — только просмотр**: вкладка правил ревизии + слайдеры из ревизии. (+) маленький, закрывает последний пункт Фазы 3, чинит слайдеры/чипы. (−) не даёт ГМ расширять правила.
- **V2 — просмотр + кастомные предметы ГМ (рекомендация)**: V1 + игра несёт свои «предметы мастера» (название+описание), видимые в правилах игры и выдаваемые игрокам (переиспользование D118 «предметы мастера» в инвентаре персонажа). ## 11. «Уникальные правила»: замена материализует итем + синхронизация листа (2026-08-18)

Два бага закрыты (гейт: format+lint+vue-tsc+vitest 831/831).

### Баг A (закрыт): замена кастомного правила на итем не материализовала предмет

- Симптом: «Заменить на правило» давала чип «заменено: …», но предмета нет в инвентаре (ни в сводке игры, ни в листе).
- Причина: `mockCharacters.updateCustomRule` искала тип правила по `ruleCatalog`, а правило из черновика после коммита живёт в overlay `mockSpaces.committedRules` (id `rule-N`, вне `ruleCatalog`) → `type==='item'` не срабатывал.
- Фикс: резолв типа из ревизии версии (`fetchSpaceByCode(version.spaceCode)` → `fetchRevision(space.id, version.rulesRevision)`), fallback на `ruleCatalog`; только `item` → `version.inventory` (quantity 1/инкремент, не экипировано, **без списания денег/бюджета** — выдача ГМ, деньги списываются только при закупке в редакторе).

### Баг B (закрыт): лист и игра показывали разные версии (лист 6 / игра 13)

- Причина: `mockCharacters.details[id].version` — ссылка, зафиксированная при инициализации на старый объект. `moderateCharacter`/`applyMigration` делали `versions[id] = <новый объект>`, но `details[id].version` не перепривязывался → `fetchCharacter` (лист) отдавал старую версию, `activeVersion` в игре — новую.
- Фикс: новый экспорт `mockCharacters.syncCharacterVersion(id)` перепривязывает `details[id].version = versions[id]`; вызывается в `moderateCharacter` approve (mockGameMemberships). `applyMigration` уже перепривязывал `details` сам.

### Тесты

- `mockCharacterApi.test.ts`: замена на итем из черновика (коммит → ревизия) материализует предмет; правило не-итем инвентарь не трогает.
- `mockGameMemberships.test.ts` «миграция + approve»: расширен — `fetchCharacter(3)` после approve видит ревизию 12 и кастом-запись (лист синхронизирован).
