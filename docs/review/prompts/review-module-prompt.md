# Промт для ревью модуля (шаблон)

Переиспользуется для ревью модулей `draft-front_1.2ds` по волнам.
Перед запуском заполняется блок «Специфика модуля».

---

Ты — фронтенд-ревьюер. Проведи ревью модуля `src/modules/{Группа}/{Модуль}` на
соответствие `draft-front_1.2ds/frontend-rules.md` (целевой стандарт, код
приводится к нему) + общее ревью качества. Ревью — READ-ONLY: ничего не менять,
только читать и анализировать. Работаем по одному модулю за волну.

Контекст и границы:
- Код модуля: `draft-front_1.2ds/src/modules/{Группа}/{Модуль}/`.
- Правила: `draft-front_1.2ds/frontend-rules.md` (все разделы).
- Прошлые волны: `docs/review/context-*.md` — учесть принятые решения и НЕ
  дублировать уже известные findings; если пункт остался открытым — пометить
  «осталось с волны N». Ревью фокусируется на текущем состоянии модуля.
- Читай файлы лениво, только по задаче; не сканируй проект на старте. При
  чтении следи за вложенными компонентами, подключаемыми сторами/сервисами и
  кросс-модульными импортами.

Чек-лист ревью:

1. Соответствие frontend-rules.md:
   - Структура SFC: `<script setup>` → `<template>` → `<style scoped>`; одна
     задача на компонент; ~250 строк — сигнал проверить декомпозицию.
   - В .vue только UI (флаги, привязка, эвенты); логика — в Service/ (классы),
     Dto/, Utils/ (только stateless generic), Constant/; мутации глубоких
     объектов — функциями-апдейтерами.
   - Класс-сервисы, не файлы функций; синглтоны — в Service/Instance/
     (не в init.ts и не в файле класса); спеки — *SpecService в Service/Spec/,
     конфиг инъектируется.
   - Анатомия, папки в единственном числе; в корне модуля только
     init.ts/routes.ts.
2. Слои и зависимости:
   - Межмодульные импорты — только через публичные точки: init.ts (getXxxApi),
     useXxxStore(), Interface//Dto//Enum/. Внутренние файлы чужих прикладных
     модулей — нельзя. Исключение — группа Core (Engine/UI напрямую).
   - Допустимые зависимости: только группа Core (Engine, UI, User и т.п.).
     Иные — нарушение. Core/Engine не импортирует Core/UI.
   - API-сервисы — только через ServiceLocator и getXxxApi() (правило 26);
     прямой импорт Service-реализации — нарушение.
   - Плагинные точки (register/get в init.ts) — контракт в Interface/,
     композиция в main.ts; хост не импортирует компоненты донора.
   - Mock/ — фикстуры и mock-API (in-memory источник), не в Service/; моки
     типизированы теми же интерфейсами, что и бэк-контракты.
3. Один экспорт на TS-файл; исключения — только init.ts/routes.ts; баррелей
   index.ts нет; в Mock/ мультиэкспорт допускается (конвенция).
4. Именование: доменное, по терминологии бэка; без изобретённых сокращений;
   булевы-предикаты (is*/has*/can*), функции «действие+объект»; папки/файлы в
   единственном числе; нейминг файлов соответствует анатомии.
5. Типизация: типы только в Dto//Interface//Enum/ (по слоям), каждый тип —
   отдельный файл; string-literal union вместо TS-enum; import type; запрет
   any/as any; без свалок в types.ts; без типов в файлах с кодом.
6. Реактивность: props не деструктурировать (только toRefs); сторы через
   store.xxx / storeToRefs; reactive state хранит plain-данные (Dto/), не
   классы; клонирование — structuredClone.
7. Уязвимости: XSS (v-html, рендер контента сообщений от бэка), утечки данных
   в моках/логах, чувствительные данные в сторах, отсутствие валидации на
   входе.
8. Расширяемость: хардкод вместо контракта/реестра; копипаста вместо общего
   места; решения под один кейс; YAGNI — избыточные абстракции.
9. Нагрузка на бэк: лишние запросы, двойной fetch, отсутствие
   пагинации/дебаунса/кэша, перезапросы в вотчерах, циклическая синхронизация
   (особенно ChatSyncService).
10. Тяжесть для фронта: большие computed/шаблоны, лишние реактивные
    зависимости, тяжёлая работа в рендере, утечки слушателей/таймеров в
    компонентах и композаблах (жизненный цикл).
11. Async-паттерн F17: у асинхронных операций есть состояния
    загрузки/ошибки/повтора; тихих провалов нет.
12. Тесты: __tests__/ в корне модуля, структура повторяет модуль; покрыта
    критичная логика (F8), UI-mount-тесты не нужны.

Специфика модуля {Группа}/{Модуль}:
(здесь — уникальные для модуля контракты, плагинные точки, сервисы
синхронизации, потоки данных и всё, что важно проверить именно здесь)

Формат результата:
1. Находки, отсортированные по критичности: P1 (баги/реальный бэк-контракт),
   P2 (нарушение правил/доменный разрыв), P3 (улучшения). Каждая — файл:строка,
   суть, связь с правилом, предлагаемый фикс.
2. Разбор проблем с вариантами решения: для нетривиальных пунктов — плюсы/
   минусы каждого варианта, рекомендация и обоснование.
3. Подтверждённые сильные стороны (кратко) и что намеренно не блокировало.
4. План работ с разбивкой по шагам.
5. Верификация: vue-tsc --noEmit, vitest run, npm run lint, npm run format:check.
