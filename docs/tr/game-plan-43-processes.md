# План 43 — Процессы как оркестратор действий

**Статус:** ~ЧАСТИЧНО~

**Реализация:** ~PHP~, ~VUE~, ~МОК~ (мок остаётся для комбо и движения)

**Опираться на:** ~PHP~, ~НЕ ОСНОВА~

## Границы

- Процесс — оркестратор действий, а не второй боевой движок. Шаг процесса — это
  обычное действие (в том числе атакующее) со своей стоимостью, долгом ОД,
  ожиданием и прерыванием. Сессия процесса хранит только текущий шаг, счётчики
  и связи между шагами.
- Удар — не отдельная сущность рядом с действием, а исполнение атакующего
  действия (`game_action.kind = strike`). Поэтому «шаг-удар» — это действие,
  чьё исполнение открывает удар.
- Долг ОД — свойство объявленного действия, а не удара. Удар — частный случай
  действия; реакции (уклонение, блок, разворот) долга не получают.
- Работают шаги, стоимости, переходы, `failure`, `interruption`,
  `completion_effects`, счётчики сессии и помехи повтора оружия.
- В срезе 1 шаг-удар — только одиночная цель. Широкий удар (`wide_strike`) как
  шаг процесса отклоняется: у него другой путь закрытия, и сессия процесса
  должна двигаться после всех целей, а не после одной.
- Не входят: операции `movement` (`run`, `sprint`), battleground и координаты,
  поддержание заклинаний, `N → N`, процессы вне боя.
- Frontend `ProcessSessionService` и `ComboProcessService` — мок, не контракт:
  сервер сам считает доступные шаги, стоимости, счётчики и модификаторы удара.

## Модель

```text
процесс = сессия шагов
шаг     = объявленное действие + состояние шага
удар    = исполнение атакующего действия (game_action.kind = strike)
```

Шаг-действие не создаёт `game_action`; строка действия нужна только удару,
потому что его закрытие приходит позже. Состояние шага живёт в `game_process`.

- Отдельной «цены шага» как сущности нет. У шага есть объявленное действие, а
  `steps[].costs` — данные процесса, которые подставляются вместо цены карточки
  действия. В контенте это нужно: у серии вторая часть стоит 2 ОД, хотя карточка
  действия стоит 3 ОД.
- `execution` шага — режим исполнения действия: атака с выбранным профилем
  оружия, неатакующая карточка действия или шаг без действия.
- Объявление шага идёт через тот же путь, что обычное действие: проверки,
  списание, пол долга, открытие удара, ответ защиты, close.
- Сессия процесса не списывает ОД сама. Она задаёт, какое действие объявляется
  и по какой цене, а списание, долг и ожидание выполняет общий боевой путь.
- Долг ОД не привязан к шагу или удару: его получает любое объявленное
  действие, не являющееся реакцией.
- Закрытие удара или действия внутри шага двигает сессию: счётчики, статус
  шага, следующий шаг, `failure`, `completion_effects`.
- Клиент не присылает объект сессии. Он присылает выбор шага и объявление
  действия/удара, сервер возвращает новое состояние.

## Контракт правила

`ProcessSpec` расширяется типизированными полями, без веток под карточку:

```text
process.counters:      [{ code, initial }]                  // состояние сессии
process.target_mode:   "any" | "single"                     // default any
process.steps[].execution:
  type:                "strike" | "action" | "none"
  action_code:         string                               // optional
process.steps[].strike:
  advantage:           Formula                              // помехи/преимущества попадания
  extra_successes:     Formula                              // успехи размера броска
process.steps[].requires_counters: [{ counter_code, min }]   // шаг недоступен ниже порога
process.steps[].counter_on_success: [CounterOp]
process.steps[].counter_on_failure: [CounterOp]

CounterOp = { counter_code, delta } | { counter_code, set }
Formula   = { type: "fixed", value }
          | { type: "counter", counter_code, factor?, divisor?, min_value?, max_value? }
```

- Поля шага живут в `ProcessStep`, поля процесса — в `ProcessSpec`; это DTO,
  не массивы. Парсер — `ProcessSpecs`, рантайм не читает документ напрямую.
- `execution` нужен уже срезу 1; `counters`, `target_mode`, `strike`,
  `requires_counters`, `counter_on_*` — v2 среза 2. Парсер среза 2 читает их с
  умолчаниями, рантайм среза 1 их не использует.
- `execution.type` — как исполняется действие шага, а не второй вид сущности:
  `strike` — атакующее действие с выбранным профилем оружия, `action` —
  неатакующая карточка `action_code`, `none` — шаг учёта без действия (движение
  и продолжение; в срезе 1 не исполняется, шаг отклоняется).
- Код в конверте `game.runAction` — всегда код карточки процесса. Для шага
  сервер сам берёт `execution.action_code`; клиент не подменяет карточку
  процесса карточкой действия.
- `action_code` по умолчанию — код карточки процесса. Для `strike` карточка
  процесса выступает объявлением действия: профиль, проверка и урон берутся из
  оружия. Для `action` `action_code` обязателен и указывает на карточку
  неатакующего действия; для `strike` он тоже может указывать на настоящую
  карточку действия, если шагу нужны её эффекты (например, толчок).
- Доступность проверяется на карточке процесса: уровень, зоны и требования.
  `GameCardAvailability` сейчас принимает только `AbilityActionSpec`; его нужно
  обобщить до `AbilityWithBase`, иначе удар с кодом процесса отвергается как
  «карточка не живая». Если задан `execution.action_code`, дополнительно
  проверяется и карточка действия.
- `execution.type = action` требует неатакующую карточку
  (`assertServerPerformable`). `execution.type = strike` берёт профиль оружия;
  если задан `execution.action_code`, это должна быть атакующая карточка.
- Цена шага (`steps[].costs`) — authoritative стоимость действия в контексте
  процесса. Она не повышается `min_total_action_cost`, глобальным полом удара
  `GameActionFloor::MIN_STRIKE_AP` и минимумом оружия: у серии вторая часть
  дешевле первой по контенту. Модификаторы и хвосты применяются существующим
  путём: `adjustSpends` для удара, `declare` для действия; это не пол, а
  изменение цены.
- Счётчики живут только в сессии процесса, не в листе и не в `states`
  (`rule-content-plan-09-melee-speed.md`).
- `requires_counters` фильтрует доступные шаги. Список доступных шагов и
  готовые модификаторы удара отдаёт сервер; клиент их не вычисляет.
- `strike.advantage` и `strike.extra_successes` считаются на сервере из
  счётчиков и спеки; клиент не присылает числа. `advantage` добавляется к
  преимуществам проверки попадания, `extra_successes` — к успехам размера
  броска; потолки задаются `min_value`/`max_value` формулы.
- `target_mode: single` — цель фиксируется первым ударом процесса; смена цели
  отклоняется. `any` — цель выбирается каждым шагом. Отдельного режима `last`
  нет: подстановка прошлой цели — подсказка клиенту, а не ограничение.
- `counter_on_success` / `counter_on_failure` поддерживают и `delta`, и `set`:
  завершение комбо не «прибавляет 0», а сбрасывает Комбо в 0.
- `repeat_weapon_circumstance` уже разобран `ProcessSpecs`, но рантайма нет.
  Помеха повтора — источник `circumstances`, не `multi_attack`: её не гасит
  навык, снижающий `multi_attack`. Ключ счётчика — экземпляр оружия
  (`id:{itemInventoryId}:{instanceIndex}`), как `AttackActionSourceService.weaponKey`.
  Счётчик растёт на завершённом ударе (попадание или промах), не на объявлении
  и не на отмене. `GameStrikeOpen` записывает `prior` (число прошлых
  использований) в `game_action_strike.repeat_weapon_uses`, close применяет
  `-prior` и после разрешения увеличивает счётчик сессии. Это работа среза 1.
- Старые ревизии без новых полей читаются с умолчаниями:
  - нет `execution`: если ключ `operations` присутствует (даже пустой список) —
    шаг операционный (`none`) и в срезе 1 отклоняется; если ключа нет —
    `strike` с `action_code` = код карточки процесса. Наличие ключа, а не
    непустой список: иначе `run-continue` и `sprint-continue` с
    `operations: []` превратятся в удары. Это совместимость ревизии 27, а не
    общий закон: в v2 `execution` обязателен;
  - нет `start_step_code` или он пустой — стартовый шаг первый в `steps`.
    У `seriya-udarov`, `mnozhestvo-udarov`, `run` и `sprint` поля нет;
  - нет `counters` — счётчиков нет;
  - нет `target_mode` — `any`.

## Контракт сессии

`game_process` получает nullable-поля: строки проверок уже живут в этой
таблице и не имеют процесса, поэтому обязательными они быть не могут.

```text
process_rule_code      string(255) | null   // null — строка проверки
current_step_code      string(128) | null
step_status            pending | completed | null
counters               json | null
weapon_use_counts      json | null
last_target_type       string(16) | null
last_target_id         int | null
```

`game_action` получает nullable-поля (для шага-удара):

```text
process_id             int | null
process_step_code      string(64) | null
```

`game_action_strike` получает поле для повтора оружия:

```text
repeat_weapon_uses     int (default 0)
```

Правила:

- `process_rule_code is null` — строка проверки. Ability-процесс всегда имеет
  код; `current_step_code` и `step_status` у проверки пустые.
- У шага-удара связь с процессом хранится на `game_action`, а не только в слоте
  долга: close получает строку и по `process_id`/`process_step_code` двигает
  сессию и читает цену шага.
- Шаг-действие не создаёт `game_action`: его связь с процессом живёт в слоте
  долга и в команде, а после исполнения сессия двигается в той же команде.
- Один открытый процесс на участника в бою. Второй процесс — `GAME_CONFLICT`;
  повторный шаг того же процесса разрешён. Проверка идёт по открытой строке
  актора, отдельного уникального индекса в БД нет: старт и переход идут через
  CAS версии боя, поэтому гонка двух стартов разрешается конфликтом, а не
  двумя строками.
- Долг ОД — общий: один слот на актора. Слот хранит объявление действия
  (`kind` + payload), а не только удар. Пока шаг ждёт долг, объявить другой
  шаг, действие или `abortProcess` нельзя: сначала `continueAction` или
  `abortAction` (существующий `GameActionDebt::assertFree`).
- `abortProcess` дополнительно отклоняется, если в бою открыт удар или
  неоплаченное действие: сначала нужно закрыть удар или снять действие.
- Процесс несовместим с поддержанием заклинания; это правило включится
  вместе с рантаймом магии, сейчас фиксируется как открытый стык.
- Счётчики не пишутся в Character/NPC; applied effects не откатываются при
  прерывании или очистке.
- Каждая запись строки процесса идёт в одной транзакции с повышением
  `game_battle.state_version`, иначе клиентский CAS по версии боя не увидит
  смену шага. Проверка строки и `replaceTracked` должны быть в одной
  транзакции; иначе два шага могут пройти по одной версии.

## Стоимость, долг ОД и ожидание

- Шаг объявляется через общий путь `game.runAction` (см. «Команды»). Цена шага
  подставляется вместо цены карточки действия до применения модификаторов
  (`adjustSpends` для удара, `declare` для действия). Полы (`MIN_STRIKE_AP`,
  `min_total_action_cost`, минимум оружия) к шагу не применяются; для обычного
  действия они работают как сейчас.
- Цена шага используется не только при списании: close, чат и хвосты
  «до траты N ОД» должны видеть цену шага, а не цену карточки действия. Иначе
  `getActionAp` вернёт 0 для карточки-процесса и эффект «пока не потратят 1 ОД»
  не уменьшится. Источник для шага-удара — `game_action.process_step_code` и
  спека процесса; для шага-действия цена уже в результате объявления.
- Долг ОД — общий слой объявленного действия (`GameActionDebt`), а не часть
  удара. Сейчас он зашит в `GameStrikeSpend`; в срезе 1 выносится на уровень
  `game.runAction`/`GameActionDeclare` и работает для любого объявленного
  действия: `action`, `strike` (включая шаг процесса) и `wound`. Реакции
  (уклонение, блок, разворот) долга не получают — у них отдельный путь
  `resolveReactionResourceSpends` и нет объявления `game_action`.
- `wound` — обычное объявленное действие с долгом, но не шаг процесса:
  `execution.type` его не содержит, процессный контекст к ране не применяется.
- `GameActionDebt::plan` принимает объявление целиком (`kind` + payload), а не
  `$attack` + `$lane`; слот хранит `kind`, объявление, контекст процесса и цену
  (`total`, `remaining`). Для `action` в payload лежит полное тело
  `game.runAction` (актор, карточка, `chosenAmounts`, `followUpTargetKey`), для
  `wound` — тело операции.
- `GameTurns::continueWork` исполняет слот по `kind`:
  - `strike` — `openPaidAction`;
  - `action` — общий сценарий объявления действия (`GameActionDeclare`:
    подготовка, pending, чат, итог), а не голый `GameActionPerform`: иначе
    после долга теряются чат и сборка ответа;
  - `wound` — `GameWoundActions::resume` с сохранённым телом.
  `GameActionPerform`, `GameActionDeclare` и `GameWoundActions` получают
  раздельные `quote`/`execute`: объявление с долгом считает цену, но не пишет
  лист и не применяет эффект.
- Если ОД хватает, действие исполняется сразу, удар открывается.
- Если ОД не хватает, работает общий долг: списывается доступное
  (`min(current, need)`), слот долга хранит объявление вместе с
  `processRuleCode`/`processStepCode`, эффект действия не применяется. Это не
  ошибка команды: команда возвращает `opened: false` и остаток для любого
  действия, не только для удара.
- Исходная команда `action`/`wound` при долге завершается `opened: false` и
  записывается в журнал как таковая. Исполнение после доплаты идёт отдельной
  командой `turn`; второй команды `action`/`wound` нет, повтор исходного
  ключа возвращает `opened: false`.
- Цена-эффекты (`next_action_cost`, `next_action_attack_cost`) уже применены к
  цене на объявлении с долгом. Слот хранит `pending`-снимок цены, и он
  записывается в бой на объявлении: иначе `continueAction` применит эффект
  второй раз. При `abortAction` они не возвращаются: это существующее
  поведение удара, фиксируем его явно. Эффект самого действия не применён.
- `game.continueAction` доплачивает долг; когда `remaining = 0`, действие или
  удар исполняется тем же путём, что и при полной оплате, с той же ценой.
  Через границу долга процесс не теряет шаг. Если исполнение после оплаты
  отвергнуто, слот восстанавливается, а не теряется; повтор не списывает ту же
  цену второй раз.
- `game.abortAction` на неоплаченном действии или шаге снимает слот, действие
  не исполняется; если это шаг процесса — процесс переходит в `cancelled`.
  Возврата ОД и цена-эффектов нет.
- Совместимость: старые слоты с `attack`/`lane` читаются как `kind: strike`;
  новые поля добавляются рядом, без миграции живого боя.

## Переходы, failure, прерывание

- Переход считается по `transition` из спеки: `chain` (радиус и направление),
  `free`, `custom` (рёбра `from → to`).
- Успех шага: применяются `counter_on_success`, шаг получает
  `step_status: completed`, следующий шаг выбирается из доступных. Если шаг
  входит в `exit_step_codes`, процесс сразу `resolved` и применяет
  `completion_effects`.
- Провал шага (`failure`):
  - `end_action` — сессия `cancelled`, шаг не завершён,
    `completion_effects` применяются: процесс закончился, хвост после него
    должен сработать;
  - `restart_from_first` — сессия остаётся открытой, применяются
    `counter_on_failure`, шаг сбрасывается на `start_step_code` со
    `step_status: pending` (иначе повторно объявить стартовый шаг нельзя);
  - на промахе удара внутри шага действует тот же `failure`. Для шага-удара
    успех — успех проверки попадания, а не наличие урона; отменённый толчок
    промахом не считается.
- Если после успеха из текущего шага нет доступных шагов и он не входит в
  `exit_step_codes`, процесс остаётся `open` с пустым списком шагов; выйти
  можно только `abortProcess`. Это осознанное состояние, а не автоматический
  `resolved`.
- `exit_step_codes` — шаги, после успешного завершения которых процесс
  разрешается автоматически (`resolved`) и применяет `completion_effects`.
  Пустой список — автоматического выхода нет: процесс продолжается до провала
  или явного прерывания. Мок `ProcessSessionService::canExit` считает
  отсутствие списка разрешением с любого шага — это не контракт.
  `transition.exits` парсится, но рантаймом не читается; канон — только
  `exit_step_codes`.
- `interruption`:
  - `normal` — `game.abortProcess` разрешён, применяются
    `completion_effects` процесса;
  - `emergency` — только при непустых `effects` шага, применяются они;
  - `game.abortProcess` отклоняется при открытом ударе или долге;
  - `game.abortAction` на неоплаченном действии или шаге — действие не
    исполняется; шаг процесса переходит в `cancelled`, эффектов нет;
  - очистка на `endBattle`/`stopSession`/`leave` эффектов не применяет.
- `completion_effects` процесса сейчас только разобраны в `ProcessSpec`, в
  Game не применяются. Их нужно применять при `resolved`, `normal`
  прерывании и `failure: end_action`; механизм `pending_action_effects` уже
  есть, но `complete` читает эффекты карточки действия и не умеет добавлять
  чужие. Нужен публичный вход для готового списка эффектов процесса.

## Команды

```text
game.runAction          объявление действия или шага: обычный конверт
                        action/strike + context.processRuleCode,
                        context.processStepCode
game.abortProcess       normal | emergency
game.abortAction        снятие неоплаченного действия или шага
game.continueAction     доплата долга действия или шага
game.getBattleSheets    сессии процессов, доступные шаги, стоимости,
                        счётчики, готовые модификаторы удара, слот долга
game.get / getRoster    краткая сводка для карточки и состава
```

- Отдельных `startProcess` / `continueProcess` нет. Шаг — это действие, а
  процесс — его контекст. Сервер сам различает старт (открытой сессии нет) и
  продолжение (сессия есть) по `processRuleCode` и проверяет доступность шага.
- `context.processRuleCode` и `context.processStepCode` добавляются в конверт
  `action` и `strike` (`GameRunActionBody`) как optional-поля: обычное действие
  без процесса их не присылает. Клиент не присылает объект сессии.
  - старт: `processRuleCode` задан, открытой сессии у актора нет;
    `processStepCode` необязателен и должен совпасть со стартовым шагом;
  - продолжение: `processRuleCode` должен совпасть с открытой сессией,
    `processStepCode` обязателен и должен быть доступным шагом.
- `code` конверта — код карточки процесса, не `execution.action_code`.
- Шаг с `execution: none` (движение и продолжение) в срезе 1 не объявляется;
  отдельного второго пути списания ОД не вводим. Для `run`/`sprint` сервер
  явно отклоняет шаг с операцией `movement`.
- Удар внутри шага хранит `processId` и `processStepCode` на `game_action`:
  open проверяет шаг, цель и доступность, close двигает сессию. Шаг-удар с
  несколькими целями (`wide_strike`) в срезе 1 отклоняется; широкий удар
  определяется по `execution.action_code`/профилю, не по коду процесса.
- `expectedVersion` и идемпотентность — как у остальных боевых команд;
  изменение строки процесса входит в версию боя.
- `game.abortProcess` — писатель боя или владелец актора, `expectedVersion`
  как у остальных боевых команд.
- Итог объявления с долгом: `opened: false`, `debt: true`, `remaining` и
  частично списанный `spent`; действие не исполнено, цена-эффекты учтены. Для
  удара это существующий результат, для `action` — новый; клиент показывает
  долг по слоту, а не по мнимому успеху действия.
- Панель боя читает `game.getBattleSheets`; `game.get`/`getRoster` не содержат
  листов боя и не годятся как единственный источник сессии процесса.

## Чат

- Процесс не пишет служебных строк: ни «начинает/продолжает процесс», ни
  «шаг «…»», ни «прерывает/завершает», ни «сорван». Чат — история
  произошедшего, а не лог состояний процесса.
- Шаг-действие пишется обычной строкой `GameActionChat`:
  «X совершает действие [[rule:…]] за N ОД», где N — цена шага, а не цена
  карточки процесса.
- Шаг-удар пишется обычной нарративной строкой `GameStrikeSingleChat`.
  Повтор оружия и помехи к попаданию остаются в той же строке/эффектах.
- Состояние процесса показывают плитка боевой карточки и всплывающее
  уведомление (`ProcessNoticeService`): выполненный шаг («шаг «…» выполнен» +
  «Продолжить») и прерывание («процесс прерван»). Уведомление закрывается
  крестиком до таймаута.
- Завершение и провал отдельной строкой в чат не пишутся: итог виден по
  `completion_effects` и по ответу действия.
- Ожидание и доплата остаются строками `continueAction`: это долг ОД, а не
  процессная мета.

## Срезы

1. **Оркестратор и боевые процессы без счётчиков** — `seriya-udarov`,
   `mnozhestvo-udarov`: поля `game_process`/`game_action`/`game_action_strike`,
   контекст шага в `game.runAction`, `abortProcess`, `getBattleSheets`, общий
   путь объявления и списания, **вынос долга ОД на уровень объявленного
   действия** (action, strike, wound; реакции — нет), долг шага через
   `continueAction`/`abortAction`, переходы, `failure`, `completion_effects`,
   помехи повтора оружия, очистка, чат без процессной меты, MySQL-тесты,
   реальный API на фронте.
   Контент не меняется; совместимость ревизии 27 — пустой `start_step_code` =
   первый шаг и `operations` по наличию ключа. Широкий удар как шаг отклоняется.
2. **Комбо** — `ProcessSpec` v2 (`counters`, `target_mode`, `strike`,
   `requires_counters`, `counter_on_*` с `delta`/`set`), парсер и
   редактор, ревизия 28, рантайм счётчиков и одной цели, серверные
   модификаторы удара, снятие жёстких констант `ComboProcessService`.
   В ревизии 28 у `combo-finish` появляется `exit_step_codes: ["combo-finish"]`:
   у шага нет исходящих рёбер, и без выхода процесс останется `open` с пустым
   списком шагов. Отдельно типизировать «Раскрытие»: закрытие комбо другим
   своим атакующим действием по той же цели. Сейчас это зашито в
   `ComboProcessService` (`canCloseWithOtherAttack`, `COMBO_CLOSE_CAPS`), в
   `ProcessSpec` поля нет. Черновик формы:
   `process.close_with_other_attack: { min_counter, min_value, allow_wide }`
   плюс проверка owned-способности с `parent_ability_code` процесса; точную
   форму фиксируем в срезе 2 до реализации.
3. **Движение** — `run`/`sprint` после контракта движения; здесь только явный
   отказ на операции `movement`, чтобы карточки не запускались молча.

## Состояние среза 1

Сделано в PHP:

- `ProcessExecution` и умолчания `ProcessSpecs`: пустой `start_step_code` — первый
  шаг, `operations` различается по наличию ключа;
- `GameCardAvailability` принимает `AbilityWithBase`, удар с карточкой процесса
  проходит;
- поля `game_process`, `game_action`, `game_action_strike` и чтение/запись
  сессии;
- `GameProcessRules` (переходы, цена шага) и `GameProcessFlow` (старт,
  завершение, провал, прерывание, повтор оружия);
- шаг через `game.runAction` для удара и действия, цена шага вместо цены
  карточки;
- общий долг ОД для `action`/`strike`/`wound`, `resume` после доплаты без
  повторного списания;
- `game.abortProcess`, `game.getBattleSheets` отдаёт сессии процессов и слот
  долга;
- служебных строк процесса в чате нет: шаг пишется обычной строкой
  действия/удара с ценой шага.

Сделано во фронтенде:

- `game.getBattleSheets` читается в `GameApi.getProcessSessions`: серверные
  сессии процесса переводятся в `ProcessSession` (`ProcessSessionSourceService`);
- объявление шага-удара отправляет `processRuleCode` и `processStepCode` в
  контексте `game.runAction`, шаг-действие — там же;
- «Продолжить» на плитке процесса открывает боевой диалог на следующем шаге;
- «Оборвать» вызывает `game.abortProcess`, а не мок `setProcessSession`;
- ход процесса не пишется служебным сообщением в чат: выполненный шаг и
  прерывание показываются всплывающим уведомлением (`ProcessNoticeService`),
  а «Продолжить» из уведомления открывает диалог следующего шага; уведомление
  закрывается крестиком до истечения таймаута;
- прерывание из любого диалога поднимает `process-aborted`, а `GameChatTab`
  подписан на `overlay-changed` `AttackLaunchDialog`: сессия чистится локально
  и перечитывается из `game.getBattleSheets`, поэтому плитка процесса исчезает
  сразу, без перезагрузки;
- действующие эффекты (`after_action_until_resource_spent_check_modifier`,
  стоимость/точность следующей атаки) показываются в блоке эффектов запуска
  атаки вместе с эффектами самой карточки;
- счётчики/комбо и движение по-прежнему на моке.

Осталось:

- счётчики и комбо — срез 2;
- движение — срез 3;
- отрицательная проверка, что чат не содержит процессной меты (сейчас её нет);
- полный `bash tools/test-full.sh` после ручной проверки.

## Тесты

- Unit: `ProcessRules` — переходы (`chain`/`free`/`custom`), `exit`,
  `failure`, стоимости шага, формулы счётчиков, `delta`/`set`; парсер
  `ProcessSpec` v2 и умолчания старых ревизий (в том числе `execution` по
  умолчанию для `seriya`/`mnozhestvo`), пустой `start_step_code` = первый шаг,
  `operations: []` — операционный шаг, а не удар.
- Unit: цена шага не поднимается `MIN_STRIKE_AP`/`min_total_action_cost`, но
  `adjustSpends` её меняет.
- Unit/Game: удар с кодом карточки процесса проходит проверку доступности;
  `GameCardAvailability` принимает `AbilityProcessSpec`, а не только
  `AbilityActionSpec`.
- Game MySQL: старт/продолжение/прерывание шага, полная оплата, долг действия
  и удара (`opened: false`), долг раны, доплата через `continueAction`,
  `abortAction`, второй процесс, шаг-удар (успех/промах), шаг-действие с
  долгом, счётчики и цель комбо, повторы оружия (ключ экземпляра, источник
  `circumstances`, рост на завершённом ударе), `completion_effects` на
  выходе/провале/нормальном прерывании, отсутствие эффектов при очистке, связь
  `game_action.process_id`, идемпотентность, CAS, строка действия с ценой шага
  и без процессной меты,
  `game.getBattleSheets` с открытой сессией, `game.abortProcess` без
  turn order.
- Game MySQL: неатакующее действие при нехватке ОД частично списывает,
  возвращает `opened: false` и исполняется после `continueAction`; при
  `abortAction` цена-эффекты не возвращаются; реакция при нехватке ОД
  по-прежнему отвергается. Широкий удар как шаг процесса отвергается.
- Game MySQL: запись шага процесса повышает `game_battle.state_version`;
  устаревшая версия боя даёт конфликт, а не второй шаг.
- Frontend: `ProcessSessionSourceService` переводит серверные сессии в
  `ProcessSession`; `game.getBattleSheets` отдаёт сессию и долг; диалог атаки

  блоке запуска атаки; прерывание чистит сессию и перечитывает
  `game.getBattleSheets`; мок остаётся для комбо и движения;
  `npx vitest run` по затронутым файлам.
- Полный `bash tools/test-full.sh` — после ручной проверки.

## Риски

- Цена шага и полы `MIN_STRIKE_AP`/`min_total_action_cost`: если пол применить
  к шагу, вторая часть серии подорожает и контент развалится. Пол обходится
  только для шага, не глобально.
- Подмена цены: если `execution.action_code` — настоящая карточка, её
  `resolveResourceSpends` вернёт цену карточки и минимум оружия. Для шага их
  нельзя складывать с `steps[].costs`; цена шага заменяет трату ОД, а не
  дополняет её. Иначе вторая часть серии станет 3+2 ОД.
- Долг шага пересекается с `continueAction`/`abortAction`; без явного
  контекста процесса в слоте долга replay исполнит шаг как обычное действие.
- Долг сейчас зашит в `GameStrikeSpend`. Вынос на уровень объявления —
  изменение общего пути действия: легко получить двойное списание или replay
  действия без слота. `GameTurns::continueWork` должен исполнять слот по
  `kind`, а не всегда открывать удар.
- Реакции не должны попасть в слот долга: у них нет `game_action` и
  `continueAction`; при нехватке ОД реакция отвергается, как сейчас.
- Связь `process_id` только в слоте долга недостаточна для шага-удара: после
  `continueAction` close уже не увидит слот. Нужны поля на `game_action`.
- `completion_effects` процесса сейчас не применяются; легко оставить их
  только на «успешном» конце, хотя провал `end_action` тоже конец процесса.
- Спека v2 и старые ревизии: без умолчаний `process` перестанет читаться.
  Умолчание `strike` для шага без `operations` — совместимость среза 1, а не
  общий закон для будущих небоевых процессов. Наличие ключа `operations`, а не
  его непустота: иначе `run-continue`/`sprint-continue` станут ударами.
- Пустой `start_step_code` у `seriya`/`mnozhestvo`/`run`/`sprint`; без
  fallback на первый шаг процесс не стартует.
- Счётчики легко утащить в `states` или лист — это ломает канон сессии.
- Очистка процесса на `endTurn` не делается: конец хода процесс не рвёт,
  диалог «Продолжить/Бросить» — начало своего хода.
- `movement`-шаги отклоняются явно; иначе `run`/`sprint` спишут ОД без эффекта.
- Карточка процесса — `AbilityProcessSpec`, а не `AbilityActionSpec`. Удар с
  `actionRuleCode` процесса **не проходит** текущий `GameCardAvailability`:
  он требует `AbilityActionSpec` и бросает «карточка не живая». Нужно обобщить
  проверку доступности до `AbilityWithBase` и проверять карточку процесса;
  `actionBase`/`resolveResourceSpends` для процесса по-прежнему пусты, поэтому
  толчок и эффекты карточки действия требуют `execution.action_code`.
- `GameProcesses` уже используется проверками; новые поля `game_process`
  обязаны быть nullable, иначе `game.check` перестанет открывать строки.
- Долг на объявлении с долгом уже применяет цена-эффекты; `abortAction` их не
  возвращает. Это надо зафиксировать в тестах, иначе легко пообещать возврат.
- Исполнение действия после долга нельзя вести голым `GameActionPerform`:
  чат, pending и сборка ответа живут в `GameActionDeclare`; нужен общий
  `quote`/`execute`, иначе после `continueAction` действие исполнится молча.
- Широкий удар как шаг процесса не поддержан: его закрытие идёт по другому
  пути, и сессия процесса не сдвинется после одной цели. В срезе 1 — явный
  отказ.
- `combo-finish` без исходящих рёбер и без `exit_step_codes` оставит процесс
  открытым; в ревизии 28 выход обязателен.
