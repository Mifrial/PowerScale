# План 43 — Процессы как тип действия

**Статус:** ~ПЛАН~

**Реализация:** ~PHP~, ~VUE~, ~МОК~

**Опираться на:** ~PHP~, ~НЕ ОСНОВА~

## Границы

- Процесс — оркестратор действий, а не второй боевой движок. Шаг процесса — это
  обычное действие или удар со своей стоимостью, долгом ОД, ожиданием и
  прерыванием. Сессия процесса хранит только шаг, счётчики и связи между
  шагами.
- Работают шаги, стоимости, переходы, `failure`, `interruption`,
  `completion_effects`, счётчики сессии и помехи повтора оружия.
- Не входят: операции `movement` (`run`, `sprint`), battleground и координаты,
  поддержание заклинаний, `N → N`.
- Frontend `ProcessSessionService` и `ComboProcessService` — мок, не контракт:
  сервер сам считает доступные шаги, стоимости, счётчики и модификаторы удара.

## Модель

```text
процесс = сессия шагов
шаг     = действие или удар + цена шага + счётчики + переход
```

- Объявление шага идёт через тот же путь, что обычное действие или удар:
  проверки, списание, пол долга, открытие удара, ответ защиты, close.
- Сессия процесса не списывает ОД сама. Она задаёт цену шага и контекст, а
  списание, долг и ожидание выполняет общий боевой путь.
- Закрытие удара или действия внутри шага двигает сессию: счётчики, статус
  шага, следующий шаг, `failure`, `completion_effects`.
- Клиент не присылает объект сессии. Он присылает выбор шага и объявление
  действия/удара, сервер возвращает новое состояние.

## Контракт правила

`ProcessSpec` расширяется типизированными полями, без веток под карточку:

```text
process.counters:      [{ code, initial }]                  // состояние сессии
process.target_mode:   "any" | "single" | "last"            // default any
process.steps[].execution:
  type:                "strike" | "action" | "none"
  action_code:         string                               // только для action
process.steps[].strike:
  advantage:           Formula                              // к помехам/преимуществам попадания
  extra_successes:     Formula                              // успехи размера броска
process.steps[].requires_counters: [{ counter_code, min }]   // шаг недоступен ниже порога
process.steps[].counter_on_success: [{ counter_code, delta }]
process.steps[].counter_on_failure: [{ counter_code, delta }]

Formula = { type: "fixed", value }
        | { type: "counter", counter_code, factor?, divisor?, cap?, floor? }
```

- `execution` делает шаг конструктором: `strike` — любой выбранный профиль
  оружия, `action` — конкретная карточка действия, `none` — шаг учёта без
  действия (движение и продолжение).
- Цена шага (`steps[].costs`) — authoritative стоимость шага. Она не
  повышается полом `min_total_action_cost` и минимумом оружия: у серии вторая
  часть дешевле первой по контенту. Модификаторы действия и хвосты
  (`GamePendingActionCosts::adjustSpends`) применяются как у обычного действия.
- Счётчики живут только в сессии процесса, не в листе и не в `states`
  (`rule-content-plan-09-melee-speed.md`).
- `requires_counters` фильтрует доступные шаги. Список доступных шагов и
  готовые модификаторы удара отдаёт сервер; клиент их не вычисляет.
- `target_mode: single` — цель фиксируется первым ударом процесса; смена цели
  отклоняется.
- `repeat_weapon_circumstance` уже типизирован: счётчики использований оружия
  ведёт сессия, `GameStrikeOpen` получает помехи обстоятельств.
- Старые ревизии без новых полей читаются с умолчаниями: нет счётчиков, нет
  `execution`/`strike`, `target_mode: any`.

## Контракт сессии

`game_process` получает поля:

```text
process_rule_code      string(128)
current_step_code      string(64)
step_status            pending | completed
counters               json
weapon_use_counts      json
last_target_type       string(16) | null
last_target_id         int | null
```

Правила:

- Один открытый процесс на участника в бою. Второй шаг другого процесса —
  `GAME_CONFLICT`.
- Долг ОД — общий: один слот на актора. Пока шаг ждёт долг, объявить другой
  шаг или действие нельзя (существующий `GameActionDebt::assertFree`).
- Сессия несовместима с поддержанием заклинания; это правило включится
  вместе с рантаймом магии, сейчас фиксируется как открытый стык.
- Счётчики не пишутся в Character/NPC; applied effects не откатываются при
  прерывании или очистке.

## Стоимость, долг ОД и ожидание

- `startProcess` / `continueProcess` объявляют шаг и передают его в общий путь
  действия/удара. Цена шага подставляется вместо цены карточки действия.
- Если ОД хватает, шаг исполняется сразу: действие закрывается, удар
  открывается.
- Если ОД не хватает, работает обычный долг: списывается доступное
  (`min(current, need)`), слот долга хранит объявление вместе с контекстом
  процесса, эффект шага не применяется.
- `game.continueAction` доплачивает долг; когда `remaining = 0`, шаг
  исполняется тем же путём, что и при полной оплате. Через границу долга
  процесс не теряет шаг.
- `game.abortAction` на неоплаченном шаге снимает слот, шаг не исполняется,
  процесс переходит в `cancelled`. Возврата ОД нет.
- Нехватка ОД не является ошибкой команды: команда возвращает `opened: false`
  и остаток, как обычное действие.

## Переходы, failure, прерывание

- Переход считается по `transition` из спеки: `chain` (радиус и направление),
  `free`, `custom` (рёбра `from → to`).
- Успех шага: применяются `counter_on_success`, шаг получает
  `step_status: completed`, следующий шаг выбирается из доступных.
- Провал шага (`failure`):
  - `end_action` — сессия `cancelled`, шаг не завершён;
  - `restart_from_first` — сессия остаётся открытой, шаг сбрасывается на
    `start_step_code`;
  - на промахе удара внутри шага действует тот же `failure`.
- `exit_step_codes` — завершённый шаг из списка переводит сессию в
  `resolved` и применяет `completion_effects`.
- `interruption`:
  - `normal` — `game.abortProcess` разрешён, применяются
    `completion_effects` процесса;
  - `emergency` — только при непустых `effects` шага, применяются они;
  - `game.abortAction` на неоплаченном шаге — `cancelled` без эффектов;
  - очистка на `endBattle`/`stopSession`/`leave` эффектов не применяет.
- `completion_effects` серии
  (`after_action_until_resource_spent_check_modifier`) уже поддержаны
  `pending_action_effects`; нужно применить их при `resolved`/`normal`
  прерывании процесса, а не только после удара.

## Команды

```text
game.getProcesses       чтение: сессии по участникам, шаги, стоимости,
                        счётчики, готовые модификаторы удара
game.startProcess       объявление первого шага (payload действия/удара)
game.continueProcess    объявление следующего шага (payload действия/удара)
game.abortProcess       normal | emergency
```

- `startProcess`/`continueProcess` — не отдельное списание, а объявление шага
  через общий путь `game.runAction`; сессию создаёт и двигает сервер.
- Шаг с `execution: none` объявляется `continueProcess` без payload удара и
  списывает цену шага напрямую; в срезе 1 такие шаги не используются.
- Удар внутри шага хранит `processId` и `processStepCode` в объявлении; open
  проверяет шаг, цель и доступность, close двигает сессию.
- `expectedVersion` и идемпотентность — как у остальных боевых команд;
  изменение строки процесса входит в версию боя.
- `game.get`/`game.getRoster` отдают сессию процесса, чтобы панель и чат не
  собирали её из мока.

## Чат

- Старт: «X начинает процесс «…», шаг «…» — N ОД».
- Шаг оплачен и исполнен: строка с ценой шага.
- Ожидание долга и доплата — существующие строки `continueAction`.
- Провал: «… процесс «…» сорван» с причиной (`failure`).
- Прерывание: «… прерывает процесс «…»».
- Завершение: «… завершает процесс «…»» с эффектами завершения.

- Game MySQL: старт/продолжение/прерывание шага, полная оплата, долг

## Риски

- Цена шага и пол `min_total_action_cost`: если пол применить к шагу, вторая
  часть серии подорожает и контент развалится.
- Долг шага пересекается с `continueAction`/`abortAction`; без явного
  контекста процесса в слоте долга replay может исполнить шаг как обычное
  действие.
- Спека v2 и старые ревизии: без умолчаний `process` перестанет читаться.
- Счётчики легко утащить в `states` или лист — это ломает канон сессии.
- `completion_effects` серии — `pending_action_effects`; проверить, что хвост
  срабатывает после завершения процесса, а не только после удара.
- Очистка процесса на `endTurn` не делается: конец хода процесс не рвёт,
  диалог «Продолжить/Бросить» — начало своего хода.
- `movement`-шаги отклоняются явно; иначе `run`/`sprint` спишут ОД без эффекта.
