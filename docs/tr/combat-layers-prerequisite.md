# Prerequisite — список боевых слоёв и срез надёжности

**Статус:** prerequisite-контракты разложены, 2026-10-07. Базовые
Character/Mechanic/Rule prerequisites и resistance path Game реализованы, но
полный P1 и `game-plan-28` закрыты только частично. [`rule-plan-07.md`](rule-plan-07.md)
остаётся стопом для отдельного Rule-расчёта слоёв: текущая семантика отбора
живет в Game. Этот файл не создаёт следующий Game plan.

Поведение не привязывается к конкретным кодам правил и механик. Разрешено получить внешний идентификатор из входных данных или из живой ревизии, найти live Rule или каталожную механику и прочитать typed spec или semantic marker. Запрещены сравнение с литералом кода, поиск карточки по заранее известной строке и fallback на frontend-коды или константы.

Frontend `HitRollService`, `AttackDamageService` и `BlockHitService` — источник требований. Их константы порога, подстановка кода предмета и сравнение с кодом механики контрактом не становятся.

## Модель блока

Блок — реакция с числовым эффектом. Отсутствие автопровала атакующего блок успешным не делает.

```text
реакция block
→ проверка попадания с результатом атакующего
  и результатом блокирующего
→ автопровал атакующего {0|-1}
  → полный промах, блок не применяется
→ проверка блокирующего провалена
  → обычное попадание
→ проверка блокирующего успешна
  → успешный блок:
     success = 1
     добавляется защита блокирования
     добавляются сопротивления блокирования
```

`BlockProfile.defense` — дополнительная защита блокирования. Защита даёт сопротивление всем типам, кроме `defense_ignored`. В ударе 1 → N результат проверки блокирующего независим для каждой цели. При провале блока сопротивления блокирования не добавляются. При автопровале атакующего блокирующая ветка не выполняется.

## 1. Проверка попадания: атакующий и защитник

**Решение.** Отдельной карточки и отдельного marker нет. Одна живая проверка с `hit_check`. У неё две роли, не «первый» и «второй» участник: атакующий и защитник. Защита принадлежит защитнику.

Роли подтверждены. Так же устроен frontend `HitRollService`: `rollHit` бросает обе роли одной карточки; `rollWideHit` бросает атакующего один раз и каждого защитника отдельно. PHP сейчас бросает только атакующего (`throwHit` / `rateHit`).

| | |
| --- | --- |
| Где живёт marker | `CheckSpec`, JSON-ключ `hit_check`, геттер `isHitCheck()`. Уже разбирает `RootSpecs` |
| Чем это не является | Spec выбранного действия, компонент `ActionComponents`, отдельный typed action contract, вторая карточка |
| Как выбирается ровно одна | Тот же обход, что `GameCheckRoll::findHitCode`: живые правила ревизии игры, битый spec пропускается, остаётся ровно одна `CheckSpec` с marker. Код карточки наружу — данные найденной строки, не литерал в коде |
| Нет карточки или их несколько | `GameInvalidException`, удар не закрывается. Подстановка первой карточки запрещена |
| Чужие признаки на той же карточке | Как сейчас у `hitSpec`: жетон концентрации, воля, неустойчивость и сложность `from_state` делают карточку негодной для попадания |
| 1 → 1 | Атакующий и защитник бросают одну карточку каждый по своему листу. Режим карточки должен допускать joint |
| 1 → N | Атакующий бросает один раз. Каждый защитник бросает один раз по той же карточке. РУ против каждого защитника считается отдельно. Защита и слои каждого защитника свои |
| Реакция не block | Бросок защитника для блока не выполняется. `ignore` и `dodge` этот контракт не расширяет |
| Автопровал атакующего `{0\|-1}` | Рейтинг атакующего против этого защитника. При этих значениях слои блока этого защитника не читаются |
| Успех защитника в блоке | Его `CheckRating` пройден. `success` против него становится `1` |
| Провал защитника в блоке | Обычное попадание: рейтинг атакующего против него сохраняется, его `BlockProfile` в котёл не входит |

Новый marker и новый код проверки не вводятся. Пример двух блокирующих целей: один бросок атакующего, два броска защитников, два независимых РУ, две независимые защиты.

**Тесты Game, когда шаг удара начнётся.** Rule-тесты marker уже есть; их не дублировать ради блока.

| Случай | Ожидание |
| --- | --- |
| Нет живой проверки с marker | Отказ удара |
| Две живые проверки с marker | Отказ удара |
| Битый spec с marker и одна живая | Берётся живая |
| Реакция block, 1 → 1 | Два результата одной карточки |
| Реакция block, две цели | Один бросок атакующего, два независимых броска блокирующих |
| Автопровал атакующего | Полный промах, защита и сопротивления блока не читаются |
| Блокирующий провален | Обычный рейтинг атакующего, слои блока не входят |
| Блокирующий успешен | `success = 1`, защита и сопротивления блока входят |

## 2. Reliability cut

**В PHP authoritative контракта нет.** Это не закрывается заглушкой в Game.

Что уже проверено:

- `DamageTypeSpec` хранит формы, `defense_ignored`, флаг сложности заклинания и потолок рейтинга. Признака среза нет.
- `WeaponProfile` хранит формулу `penetration`. Это не признак среза и не сравнение с именем механики.
- Компоненты действия — ресурс, речь, жест, материал. Признака среза нет.
- `IMechanicEngine` резолвит binding `code@version` и вызывает событие. Capability среза у хендлера нет.
- Frontend включает срез, если среди хуков типа урона есть хендлер с заранее известным кодом механики и фазой атаки. Это требование «срез приходит от механики типа урона», не контракт PHP. Код механики в Game и Rule не копируется.

Capability-инфраструктура [`mechanic-plan-07.md`](mechanic-plan-07.md) сделана,
но production handler/content для реального среза ещё не подтверждены. Это
остаётся частью незакрытого P1.

Цепочка, которую он фиксирует:

```text
профиль атаки → код типа урона (данные)
→ живое правило damage_type этой ревизии
→ привязанные механики правила
→ каталог Mechanic (code, version) → хендлер
→ semantic capability хендлера
```

Game спрашивает порт Mechanic, есть ли среди уже резолвленных механик эта capability. Game не сравнивает код механики, не читает boolean клиента и не выводит срез из типа урона. Пока порт не существует, удар среза не делает.

## 3. Проекция слоёв цели

**Владелец:** Character. Контракт — [`character-plan-12.md`](character-plan-12.md). Rule не читает Character и Game. Game не обходит способности и не хранит список.

Вход — пара документов `sheet` и `choices` игрока или версии NPC. `equippedModifiers` даёт коды надетого, не слоты. Коды модификаторов экземпляра — `choices.inventory[].modifiers`. Отдельного NPC-разборщика нет.

Выход — typed DTO, живущий только на стеке вызова. В бой и в лист он не пишется.

Слои на лету:

- надетая броня: коды из `equippedModifiers`, слоты из живого `ItemSpec` ревизии;
- выбранный предмет блока: только если код есть среди надетых и у предмета есть `BlockProfile`, включая сопротивления этого профиля и модификаторов предмета;
- сопротивление способностей листа, в том числе постоянное сопротивление тела, если оно лежит грантом способности на листе; значение-формула считается `FormulaContext` этой ревизии;
- врождённый флаг предмета сам по себе слоем не является. Отдельный обход каталога расы не нужен: способность тела уже выбрана на листе тестового персонажа, и её грант входит в проекцию.

Постоянного списка слоёв и второго листа нет. Значения слотов остаются в spec ревизии.

**Граница транзакции.** Проекция — чтение внутри уже открытого закрытия удара, после проверки версии листа и до записи исхода. Порт лист не меняет. Конфликт версии по-прежнему на mutation port / CAS NPC. Отказ проекции одной цели 1 → N — отказ этой цели; сбой порта или транзакции откатывает закрытие целиком, как сейчас отказ расчёта сопротивления.

## 4. Durability и source

### Durability

Подтверждено кодом и этим prerequisite:

- `durability` — optional threshold слоя, не прочность предмета и не шанс блока. У щита и оружия отдельное optional поле прочности предмета (`WeaponBlock` / `ShieldBlock`) к слою не относится.
- `BlockProfile.defense` поля `durability` не имеет (`BlockProfile`). Эта защита в срез не входит.
- Срез, если capability его включила, действует на общий котёл и только на слои, у которых threshold задан.
- Слой без threshold абсолютно применим: в котёл входит, срезом не снимается.
- Сопротивления блокирования используют тот же `ResistanceSlot`. Если в spec нет `durability`, их применимость абсолютна — после того, как канон разрешит отсутствие значения.
- Пороги frontend (константа 99 и максимальное безопасное число) в spec не переносятся.

**Подтверждено.** Отсутствие `durability` — абсолютная применимость. Имя поля в spec остаётся `durability`: это порог надёжности, РУ, нужный чтобы проигнорировать слой, не прочность предмета. Явной отметки «надёжность полная» отдельным ключом не заводим.

[`rule-system.md`](rule-system.md) теперь трактует `durability` как optional.
Парсер `ItemSpecs` и DTO принимают отсутствие ключа как `null`; фронт всё ещё
шлёт целое. Полный P1 всё ещё блокируют block check, penetration,
action-point eligibility/spend и production reliability handler.

### Source

Термин — `source`, не отдельный provenance.

Общий механизм сложения один, его не копировать в удар отдельной формулой. Он уже есть во frontend `AggregateSourceDeltasService` и назван в [`rule-system.md`](rule-system.md):

- у указанного source берутся самый сильный бонус и самый сильный штраф;
- если source не указан, запись считается уникальным источником: такие бонусы и штрафы не схлопываются между собой и применяются все.

Блокирование — частный случай до этого механизма, не ветка внутри него. К моменту расчёта у слоя блока source уже есть. Если в слоте профиля указан свой `source_code`, сохраняется он. Если не указан, слой приезжает в расчёт с source блокирования «От блокирования». Код предмета блока в source не подставляется. Агрегатор про блокирование ничего не знает: он видит обычный указанный source.

Явный source брони и гранта способности сохраняется как данные. Сопротивление тела и сопротивление предмета блока оба входят в список до этого сложения.

## Что блокирует game-plan-28

1. Production handler/content для capability среза по [`mechanic-plan-07.md`](mechanic-plan-07.md).
2. Полная Game-ветка блока: проверка защитника, автопровал атакующего,
   обычное попадание при провале блока и `success = 1` при успехе.
3. Подключение penetration к Game-расчёту и закрытие eligibility/spend ОД.
4. E2E-проверка полного P1 на реальном контенте.

Роли атакующего и защитника, source блокирования и состав проекции подтверждены ниже. Отдельного списка вопросов нет.

## Подтверждённые решения

1. Проверка с `hit_check` бросается ролями атакующего и защитника. Новый marker не заводится. В 1 → N атакующий бросает один раз, каждый защитник — один раз, РУ и защита считаются на защитника.
2. Нет ключа `durability` — абсолютная применимость. Отдельный флаг «полная надёжность» не вводится.
3. Пустой source слоя блока до расчёта заполняется source «От блокирования», если свой `source_code` не задан. Дальше работает общий механизм source: указанный source схлопывается до сильнейшего бонуса и сильнейшего штрафа; отсутствующий source уникален и не схлопывается.
4. В проекцию входят сопротивление способностей листа, включая постоянное сопротивление тела, и сопротивления предмета, которым выполняется блок. Игнорировать их нельзя. Отдельный обход каталога расы не нужен, потому что способность уже на листе.

## Приёмка будущего шага

Базовый path уже принят частично. Полный P1 принимается только если:

- надетый код брони даёт слоты из живой spec, не из копии на листе;
- ненадетый инвентарь в проекцию не входит;
- персонаж и NPC читаются из своих листов одним портом проекции;
- список слоёв строится на лету; бой после чтения не содержит полного листа и постоянного списка слоёв;
- грант `resistance` входит в проекцию игрока и NPC;
- проверка попадания — одна карточка с `hit_check`; роли — атакующий и защитник;
- нет карточки или их несколько — отказ, не первая попавшаяся;
- автопровал атакующего `{0|-1}` даёт полный промах, и блокирующая ветка не выполняется;
- в 1 → N успех каждого защитника независим, ставит его `success = 1` и добавляет его защиту и сопротивления блока;
- провал блокирующего оставляет обычное попадание;
- защита блокирования даёт сопротивление всем типам, кроме `defense_ignored`, и не имеет `durability`;
- срез включается только capability механики типа урона и только у слоёв с заданным threshold;
- слои без threshold остаются абсолютно применимыми;
- явный `source_code` сохраняется; пустой source блока до расчёта становится «От блокирования» и дальше идёт в общее сложение source;
- сопротивление тела с листа и сопротивление предмета блока входят в проекцию;
- production mechanic handler действительно сообщает capability среза;
- penetration реально уменьшает защиту в Game;
- проверены право на действие и списание ОД;
- E2E подтверждает цепочку на нескольких пользователях.

## Не хардкодить

- сравнение `ruleCode` или кода механики с литералом;
- готовый boolean среза во входе клиента;
- порог 99 и максимальное безопасное целое;
- код предмета как запасной source;
- порядок формулы из `AttackDamageService`, пока канон её не принял отдельно от этого prerequisite.
