# План Character 11 — остаток повреждений и дельта истощения

**Статус:** PHP сделан. Канон — [`character-plan-10.md`](character-plan-10.md) (`putState`), [`character-system.md`](character-system.md) (повреждения и истощение — разные состояния), [`rule-system.md`](rule-system.md) («Экземпляр может отсутствовать»). Нарезка — [`character-roadmap.md`](character-roadmap.md): этот документ шаг туда не вписывает и C11 не закрывает. G22 не начинается. Стандарты — [`php-coding-standards.md`](php-coding-standards.md).

Сверка кода до плана. `ICharacterActualMutations` принимает `setInventoryQuantity`, `putInventoryQuantity`, `setMoney` и `putState`. `CharacterActualStateRows::append` на `putState` дописывает новую строку в `sheet.states` и `StateSpec` читает только как `value_type` (`flag`, `number`, `dimensional`). Флаги `isDamageRemainder()` и `isDamageExhaustion()` порт не вызывает. Kind, который заменяет значение одной строки состояния и прибавляет целое к другой, в каталоге нет.

Цель: тот же порт получает один kind. Операция несёт уже посчитанные остаток `{base, size}` и целое частное. Деление порт не делает, `DimensionalNumber` не меняется. Остаток пишется в единственную живую карточку с `isDamageRemainder()`. Частное прибавляется к единственной живой карточке с `isDamageExhaustion()`. Код карточки не зашивается. Game, удар, стойкость, увечье, конец хода, DOT и каст не входят. Character Game не импортирует.

## Зафиксировано

- Kind явно: `putDamageSplit`. Набор ключей ровно `kind`, `remainder`, `quotient`. Других ключей нет. `remainder` — массив с ключами `base` и `size`, оба int, в том числе отрицательные: проверка как у `value` числового `putState` (`is_int`), не как у `setMoney`. `quotient` — такой же int. Поле листа — список `sheet.states`. Новая или заменённая строка — как у числового и размерного `putState`: ровно `{ stateRuleCode, value }`. Другие ключи лежащей строки в замену не переносятся. Коды карточек в kind не передаются.
- Живые карточки ищутся по `getLiveRules` среза ревизии листа. Тип `state`, `getSpec()` — `StateSpec`. Остаток — единственная карточка, у которой `isDamageRemainder()` истинно. Истощение — единственная, у которой `isDamageExhaustion()` истинно. Это разные карточки: одна с обоими флагами считается и там, и там и даёт отказ. Нет карточки или их две и больше — `CHARACTER_INVALID`, лист не пишется. Tombstone в live не входит. Код вроде имени состояния не зашивается.
- `value_type` карточки остатка — `dimensional`. Карточки истощения — `number`. Иначе `CHARACTER_INVALID`, лист не пишется. Форма операции проверяется до среза.
- Уже лежащая строка с `stateRuleCode` этой карточки заменяется новым `value` на том же индексе. Остальные строки списка и их порядок не двигаются. Второй строки тот же kind не дописывает. Строк с этим кодом две и больше — `CHARACTER_INVALID`, лист не пишется. Строка без этого `stateRuleCode` не считается. Строки остатка не было — создаётся одна в конце списка. `value` остатка — переданный `{base, size}`, в том числе нули. Частное `0` строку истощения не меняет и не создаёт; карточка истощения при этом всё равно обязана быть одна и с `value_type` `number`. Частное не ноль прибавляется к лежащему int; строки не было — в конец пишется само частное. Обеих строк не было — сначала остаток, затем истощение. Лежащий `value` истощения не int — `CHARACTER_INVALID`.
- `putState` не меняется по поведению: ветка по-прежнему дописывает строку и флаги остатка и истощения не читает. `accept` по-прежнему проверяет только форму `putState` и чужой kind пропускает молча, поэтому `putDamageSplit` в `accept` не передаётся. Сейчас без своей ветки в `applyOperation` это уже `CHARACTER_INVALID`. Сборка строки `putState` — приватный `appendOne`, снаружи её не вызвать. Поэтому оба kind идут одним циклом по списку операций там же, где сейчас `append` перебирает только `putState`: ветка `putState` остаётся дописыванием, `putDamageSplit` — соседняя ветка того же цикла. Второй проход после всего `append` и копия сборки строки `putState` не делаются. Иначе `putState` того же кода допишет вторую строку раньше замены. `choices` этот kind не меняет. Колонки и миграции нет: `states` остаётся ключом JSON `sheet`. `apply` по-прежнему собирает девять ключей и кладёт в строку список `states` после разбора, если ключ есть. Проверка владельца в `CharacterActualPatch` не меняется. Вход `operations` биндер по kind не режет.
- Прежние kind остаются. Полный лист, `replaceSection`, смена `equipped`, деньги и количество этим kind не пишутся. Деление размерного числа, удар, стойкость, увечье, конец хода, DOT и каст в операцию не входят.
- Фасад прежний: `ICharacterActualMutations::apply` и `applyToDocument`. Нового метода и нового HTTP нет. Владелец по уже существующему `character.applyActualPatch` передаёт тот же массив операций; отдельного фильтра kind нет.
- Game поле не выбирает и `putDamageSplit` не заводит. Код Game и Rule не меняется. Хендлеры `injury_efficiency`, `exhaustion_wound` и `state_write` в Mechanic не ставятся.

## Не закрыто

- C9: decay, периодичность, DOT и каст.
- C11 в [`character-roadmap.md`](character-roadmap.md) этим документом не вписывается и не закрывается. G22 не начинается.
- Удар, стойкость, увечье, конец хода. Деление `DimensionalNumber`. Объединение повторов по `aggregation`. Вложенные поля раны, увечья и отравления.

## Ошибки

- Пустой список операций, чужой `kind`, лишний ключ, `remainder` не `{base, size}` из int, `quotient` не int — `CHARACTER_INVALID`, лист прежний.
- Нет живой карточки остатка или истощения, карточек больше одной, одна карточка с обоими флагами, тип не `state`, spec не `StateSpec`, `value_type` не `dimensional` у остатка или не `number` у истощения, две строки одного `stateRuleCode`, лежащее истощение не int, ключ `states` есть и это не список — `CHARACTER_INVALID`. Нет ревизии — `CHARACTER_NOT_FOUND`, как у среза. Нет строки персонажа — `CHARACTER_NOT_FOUND` из `ICharacters::get`. Чужой владелец на HTTP — по-прежнему `CHARACTER_NOT_FOUND` из `CharacterActualPatch`, порт владельца не проверяет.
- Устаревшая `actual_version` — `CHARACTER_CONFLICT` до разбора операций, строка не меняется.
- `validate` по-прежнему может вернуть `CharacterSaveRejectedException` на `apply`. Отказ `putDamageSplit` до записи до этого не доходит.

## Тест

Suite `character`. Документ: остаток заменяет единственную строку карточки `isDamageRemainder()` значением `{base, size}`, в том числе нулём, на том же индексе, соседние строки не двигаются; частное прибавляется к единственной строке карточки `isDamageExhaustion()`; частное `0` эту строку не меняет и не создаёт; обеих строк не было — сначала остаток, затем частное; повтор кода на листе — `CHARACTER_INVALID`, второй строки нет. В одном списке `putState` того же кода до `putDamageSplit` даёт две строки и `CHARACTER_INVALID`; после — замена уже лежит, и `putState` дописывает ещё одну. `putState` по-прежнему дописывает строку и флаги не читает. Нет карточки, две карточки одного флага, карточка с обоими флагами, чужой `value_type`, битая форма — `CHARACTER_INVALID`, документ прежний. Чужой `kind` по-прежнему отказ. MySQL: `apply` пишет замену и сумму и поднимает `actual_version`; устаревшая версия строку не меняет; нет строки — `CHARACTER_NOT_FOUND`. Карточки в тесте — фикстуры типа `state` с флагами, не именованный код правила. Деление `DimensionalNumber` не вызывается. Код Game и реестр Mechanic не вызываются.
