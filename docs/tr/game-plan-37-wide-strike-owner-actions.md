# План 37 — общая модель действий и ответы владельцев целей

**Статус:** ~СДЕЛАНО~

**Реализация:** ~PHP~, ~VUE~

**Опираться на:** ~PHP~

## Согласованные границы

- Общая модель хранения для ударов `1 → 1` и `1 → N`: `game_action` и `game_action_target` вместо `game_strike`, `game_wide_strike`, `game_wide_strike_target`.
- Ответы накапливаются по целям. Последний необходимый ответ автоматически запускает атомарное разрешение. Отдельного подтверждения ведущим нет.
- Ведущий видит ожидание по целям и может ответить за любую из них («Взять на себя»); NPC обслуживает только писатель.
- Один пользователь может владеть атакующим и другим персонажем-целью. Сам атакующий целью собственного удара не становится.
- Старые данные являются результатом ручных тестов: пользователь разрешил их удалить. Перенос данных не требуется. Удаление старых таблиц — отдельный ограниченный шаг, не неявное действие обычной установки схемы.
- Проверки, экономика и `game_process` в этот заход не мигрируют. Расчёт ударов не превращается в универсальный движок правил.
- Поведение и публичный API готового `1 → 1` сохраняются, кроме согласованного общего запрета второго открытого удара в том же бою. Изменения его репозитория обусловлены общей моделью хранения.

## 1. Общая модель хранения

`game_action`: `id`, `kind` (`strike` / `wide_strike`), `battle_id`, `session_id`, `attacker_kind`, `attacker_id`, `action_rule_code`, `item_inventory_id`, `item_rule_code`, `profile_type`, `profile_index`, `open`.

`game_action_target`: `id`, `action_id`, `target_type`, `target_id`, nullable `reaction`, `block_item_inventory_id`, `block_item_profile_index`, `block_item_rule_code`, `expected_sheet_version`.

Уникальность цели: `(action_id, target_type, target_id)`. Порядок целей стабилен и сохраняет порядок объявления. Связь с сессией и порядок очистки согласуются с существующими SmartTable-контрактами. Итоги остаются в `game_command.result`.

Общие репозитории знают физические таблицы. Адаптеры старых репозиториев сохраняют привычные формы строк (`defender_*`) и разделяют действия по `kind`: закрытие через API одного вида не должно закрыть действие другого вида. Проверка наличия любого открытого удара общая. Один только SELECT не обеспечивает этот инвариант при конкурентном объявлении: проверить и закрепить его транзакцией/CAS боя и конкурентным тестом.

Обновить setup, schema, фикстуры и очистку сессии. Сначала удаляются цели, затем действия; команды и бои очищаются в существующем порядке. Старые таблицы не удалять до явного выполнения согласованного шага очистки.

## 2. Права

Писатель: владелец игры, роль `gm` или `game.edit_all`. Per-game `game.edit` этих прав не даёт.

| Действие | Кто вправе |
| --- | --- |
| Объявить широкий удар персонажем | Писатель или владелец активного персонажа-атакующего |
| Объявить широкий удар NPC | Только писатель |
| Ответить за персонажа-цель | Писатель или владелец активного персонажа-цели |
| Ответить за NPC-цель | Только писатель |
| Отправить несколько ответов | Право проверяется для каждой строки; чужая строка отменяет всю команду |
| Разрешить удар | Автоматически после полного набора ответов |

Проверки широкого удара вынести в `GameWideStrikeAccess` вместо writer-only помощника. Проверки доступа готового `1 → 1` не ослаблять.

## 3. Ответы и атомарное разрешение

`game.resolveWideStrike` сохраняет имя, но принимает непустой `defenses[]` с явной целью в каждой строке:

```json
{
  "gameId": 1,
  "battleId": 2,
  "idempotencyKey": "example",
  "expectedVersion": 5,
  "defenses": [
    {
      "target": {"type": "character", "id": 10},
      "reaction": "dodge",
      "expectedSheetVersion": 3
    }
  ]
}
```

Поля блока остаются прежними. Старый позиционный формат без `target`, повторы целей и цели вне действия отвергаются. Запрос писателя на все цели сразу сохраняет прежний пользовательский сценарий.

Ответ: `battleId`, `strikeId`, `version`, `closed`, `pendingTargets`, `targetResults`. До разрешения `closed=false`, `targetResults=[]`, версия боя не меняется. При закрытии `closed=true`, список ожидания пуст, версия боя увеличивается один раз.

Транзакция ответа блокирует строку действия через текущий SmartTable conditional-порт, читает текущее состояние целей блокирующим чтением, проверяет права и версии, сохраняет ответы. Если ответы полны — выполняет существующий расчёт и закрытие в этой же транзакции. Обычный snapshot SELECT после ожидания блокировки не использовать как источник актуального состояния ответов.

Каждый ответ сохраняет ожидаемую версию листа; при закрытии сверяются версии всех целей повторно. Конфликт любой цели отменяет всю текущую транзакцию, включая последний ответ и все эффекты; ранее подтверждённые отдельными командами ответы сохраняются. Игрок обновляет лист и отправляет новый ответ с новым ключом. Пока удар открыт, авторизованный актор может заменить ответ своей цели; писатель — любой цели. После закрытия замена невозможна. Идемпотентный повтор прежней команды возвращает её сохранённый снимок, а не заново вычисленное состояние.

Один бросок атакующего, один CAS версии боя, один полный итог и атомарная запись урона/ран. Неполные ответы не применяют никаких эффектов и не снимают запрет `endTurn`. Ошибки принятия ответа возвращаются ошибками команды; существующие non-CAS отказы расчёта по целям сохраняются в `targetResults`.

## 4. Доставка и чтение

Каждый принятый ответ записывает `game_command` с `source=wide_strike` и вызывает существующую доставку `strike` после commit. Сохранить catch-up после реконнекта и существующий механизм идемпотентности; новый outbox не нужен.

`game.getBattleSheets` получает nullable `openWideStrike` с идентификатором, атакующим и упорядоченными целями. Все допустимые читатели видят `answered`; реакцию и детали ответа — только владелец соответствующей цели и писатель. Проекция не должна раскрывать скрытых NPC в обход существующих правил видимости.

После reload/reconnect состояние восстанавливается с сервера, а не из локального диалога. SSE служит сигналом перечитать состояние, не единственным хранилищем ответа.

## 5. Фронтенд

- Новый `GameWideDefenseService`: доступ к ответу по цели, ожидание, выбор доступных строк.
- `GameApi` и `GamePhpBattleContext`: новая проекция, per-target тело и ответ `closed/pendingTargets`.
- `HitLaunchDialog`: ожидание у атакующего, свои цели у владельца, список ожидания и «Взять на себя» у ведущего. У пользователя может быть несколько собственных целей.
- `GameChatTab`: обновление по `strike`, предложение ответа владельцу неответившей цели, обновление/закрытие открытого диалога по серверному состоянию. Не перекрывать другой диалог безусловно.
- Готовые `GameStrikeDefenseService` и `GameAccessService.canWriteStrike` не менять без отдельной необходимости.
- Dev-сервер запускает пользователь.

## 6. Проверки и порядок работы

1. Повторить PHP baseline после фикстурного коммита. При красном результате остановить функциональную работу и установить причину.
2. Общая схема, репозитории и минимально необходимые адаптации тестов: старые сценарии `1 → 1` и `1 → N`, replay, CAS, cleanup и результаты сохраняются. Отдельный тест общего запрета открытого удара в обе стороны, включая конкурентное объявление.
3. Права и накопление ответов; отдельный коммит новых сценарных тестов.
4. Фронтенд и его тесты.
5. Документация и генерируемые карты.

Бэкенд-тесты: владельцы атакующего и разных целей; чужие строки и смешанная пачка; NPC только писатель; частичный ответ без эффектов; последний ответ; ответ писателя за всех; повтор и изменение тела ключа; замена ответа до закрытия; устаревший лист при ответе и при финальном расчёте; откат последнего ответа и эффектов; два конкурентных ответа разных целей без зависания и двойного разрешения; несколько целей одного владельца; endTurn; stop; видимость проекции и реконнект/catch-up.

Фронт-тесты: доступ по каждой цели, несколько своих целей, ведущий и takeover, ожидание, новый формат запроса, частичный/полный результат, восстановление проекции и отсутствие окна у постороннего.

Финально: PHP-тесты `GameWideStrike` и `GameStrike`, затронутые проверки Game/доставки/конца хода; vitest по Game; проверки стиля изменённых файлов; `composer maps`, `composer maps-check`, `composer docs-check` из `www/mifrial`.

Не ослаблять продакшн-валидацию или ассерты ради зелёных тестов. Не откатывать чужие изменения. Удаление тестовых данных не означает разрешение удалять другие данные Game.

## 7. Документация и приёмка

Обновить ссылки на хранение в планах 13/19, устаревшее writer-only ограничение в плане 36, актуальный контракт `game-system.md`. Исторические решения отмечать как заменённые этим планом, не выдавать их за текущий контракт. Карты обновлять генератором.

Готово, когда оба вида ударов используют общие таблицы; `1 → 1` проходит регрессию; владельцы независимо отвечают за цели широкого удара; последний ответ ровно один раз атомарно разрешает действие; состояние доступно после перезагрузки; писатель способен завершить ожидание за игроков и NPC; все обязательные проверки зелёные.
