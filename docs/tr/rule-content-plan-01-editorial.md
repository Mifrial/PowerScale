# План C1 — редакционный проход каталога

**Статус:** `DONE` (пачки 1–23 и очередь runtime собраны). Не закрыто редакцией и **не текущая работа:** дальний бой 382–393, оружейные навыки, расы. Родитель — [`rule-content-roadmap.md`](rule-content-roadmap.md). Очередь — [`rule-content-queue.md`](rule-content-queue.md). Канон — [`rule-system.md`](rule-system.md). UI — `/space/{code}/{ctx}` + FilterBar «Редакционный статус».

## Цель

Пройти выгруженные правила пачками по **10**, не открывая новые оси spec и не подгоняя Game под дамп.

После пачки: у десяти карточек честный `contentStatus` / `contentNote`; то, что ждёт движок, попало в очередь.

## Как работать одну пачку

1. Каталог, фильтр `Нуждается в работе` (плюс вкладка типа, если удобно).
2. Открыть правило. Читать описание, spec **и секцию каталога**. Не верить моку по умолчанию.
3. Исход пачки в чате: имя, секция (`catalogSection` + путь), описание, логика spec. Секцию правим здесь же, если она неверная.
4. Статус:
   - текст и spec согласованы, игроку можно показывать → `ready`;
   - дыры, но карточка не врёт опасно → `needs_work` + комментарий, что осталось (редко оставлять в той же пачке повторно);
   - spec/текст вредят → `broken` + `contentNote`;
   - нужен runtime или чужое правило → статус по вреду карточки, строка в очередь, в комментарии — почему.
5. Не ставить `ready`, если Game «уже как-то работает», а текст врёт.
6. Не ставить `broken` только потому, что каста нет.

Простые правки описания/очевидного spec — в той же пачке. Тяжёлые группы — очередь, не растягивать пачку.

## Что не делать в C1

- Импорт новой выгрузки и кристалл/мана «про запас».
- Поле `runtime-support` в DTO.
- Массовый reset статусов.
- PHP, кроме уже лежащего `content_note` в снимке версии.
- Закрывать C2 внутри этой пачки.

## Гейт пачки

Десять кодов с итоговым статусом; очередь обновлена, если были пропуски; черновик пространства сохранён, если менялись карточки.

Первая пачка — любые десять `needs_work` с открытого каталога; приоритет листов — в C2.
