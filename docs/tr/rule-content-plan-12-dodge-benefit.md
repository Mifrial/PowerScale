# C2 — Польза уклонения в профилях оружия

**Статус:** план, 2026-09-19.  
**Родитель:** [`rule-content-plan-11-melee-accuracy.md`](rule-content-plan-11-melee-accuracy.md).  
**Очередь:** [`rule-content-queue.md`](rule-content-queue.md).

Цель: заменить зашитый `Ловкость.modify(−3)` на редакционное число профиля
`dodge_benefit` и провести его через текущий боевой расчёт.

`dodge_benefit` — не временный бонус, не эффект действия и не runtime-баф.
Это постоянное целое в `WeaponProfile`. Таблица ниже — **только шпаргалка
для первой простановки в каталог**. Код таблицы не знает и по ней ничего
не выводит.

Этот план **снимает S0** из плана-11 §2.1.

## 1. Принятый канон

### 1.1. Расчёт

```text
модификатор = dodge_benefit профиля, иначе fallback −3
S = Ловкость.modify(модификатор)
повреждение = max(0, (урон оружия − сопротивление) × РУ − S)
```

Сопротивление до РУ, Смягчение после. Карты (Направленный, Стремительный)
режут уже это `S`, не кубы уклона. `ignore` и `block` — без слоя.

Ловкость как источник Смягчения и fallback `−3` в этом срезе остаются
в коде Game (как сейчас зашито `−3`). Вынести «какая характеристика» и
«какой fallback» в спеку характеристики или mechanic ловкости — **не этот
срез**; механика ещё может смениться.

При отсутствии `dodge_benefit`: тот же расчёт с `−3`, `console.warn` с
кодом предмета/индексом профиля; на dev-сервере — ещё `alert`. В unit-
тестах (`import.meta.env.MODE === 'test'`) alert не звать: vitest часто
с `DEV=true`, иначе каждый тест фолбэка встанет на диалоге. Не
подставлять `0`: `0` — валидная польза (`[Сила]`), не «поле пусто».

### 1.2. Шпаргалка расстановки (не runtime)

Для профилей `actionCharacteristic` по Силе, включая бросок/выстрел с той
же формулой:

| Формула урона | `dodge_benefit` |
| --- | ---: |
| `[Сила − 4]` и слабее | `−6` |
| `[Сила − 3]` | `−4` |
| `[Сила − 2]` | `−3` |
| `[Сила − 1]` | `−1` |
| `[Сила]` | `0` |
| `[Сила + x]` | `+x` |

Фиксированный урон:

| Формула | `dodge_benefit` |
| --- | ---: |
| `[1]` | `−6` |
| `[2]` | `−4` |
| `[3]` | `−4` |
| `[6]` | `−4` |

После первой простановки профили правятся вручную, если на игре цифры
не зашли. Калибровка думалась на `{Сила 4|1}` / `{Ловкость 4|1}`;
`action_characteristics` (сила выстрела ≠ Сила персонажа) не повод
отклоняться от шпаргалки. Модификаторы предмета дельтят урон, не
`dodge_benefit` — пока так задумано.

Размерный ряд `FormulaEvaluationService` при `{4|1}` (справка, не код):

| Формула | Результат |
| --- | ---: |
| `[Сила − 4]` | `{3|0}` |
| `[Сила − 3]` | `{4|0}` |
| `[Сила − 2]` | `{5|0}` |
| `[Сила − 1]` | `{3|1}` |
| `[Сила]` | `{4|1}` |

`{4|1}.modify(-2)` в текущем `DimensionalNumber` = `{5|0}`. Менять шкалу
в этом плане не надо.

## 2. Границы

### Входит

1. Опциональное поле `dodge_benefit` на `WeaponProfile`.
2. Простановка по шпаргалке во всех профилях **каталога и выгрузки**:
   оружие, щиты с атакующим профилем, врождённое (`ruka` / `noga`).
   Без поля — только узкая синтетика теста fallback; в мок/выгрузку
   такое не класть.
3. Редактор: поле «Польза уклонения», тип профиля — DTO, не локальный
   дубль.
4. Overview → soak только на `dodge`.
5. Fallback `−3` + warn / dev alert, если поля нет.
6. Тесты soak/cuts; overview тащит число; отсутствие поля даёт `−3`.

### Не входит

- формула урона, сопротивление, пробитие, РУ;
- поле на `WeaponBlock` вместо профиля;
- новые action-эффекты;
- код, который по формуле урона считает `dodge_benefit`;
- валидатор «не меньше −6» / обязательное поле;
- пересчёт soak от модов предмета, хвата, дистанции;
- спека характеристики / mechanic «для смягчения» (открыто на потом);
- PHP.

## 3. Этап A — поле и каталог

### A1. Контракт

`Roleplay/Rule/Dto/Item/WeaponProfile.ts`:

```ts
dodge_benefit?: number;
```

Snake_case, как остальные поля спека. Не required: правила ещё могут
смениться, жёстко сажать механику в типы нельзя.

Новый профиль в `addWeaponProfile` **может не ставить** поле — сработает
fallback. Не заставлять автора «перезаписать дефолт».

### A2. Простановка

Пройти все `weapon_profiles` у `weapon` и `shield`:

- `mockItemImport.ts` (включая `ruka`, `noga` и щиты);
- предметы в других моках, которые попадают в выгрузку.

Значение — по шпаргалке §1.2. Синтетика unit-тестов: профили «как в
каталоге» — тоже проставить; без поля — только фикстура, которая
проверяет fallback (не импорт каталога).

### A3. Редактор

`WeaponProfileEditor.vue` сейчас объявляет **локальный** `interface WeaponProfile`
(урезанный: нет `falloff`, `action_characteristics`). Это нарушение
frontend-rules (именованный тип только в `Dto/`) и расхождение с
`Rule/Dto/Item/WeaponProfile.ts`. Родитель (`WeaponEditor`) уже отдаёт
полный DTO через `WeaponBlock.weapon_profiles`.

В этом срезе: удалить локальный интерфейс, `import type { WeaponProfile }`
из DTO, добавить числовое поле «Польза уклонения». Пустое поле в UI —
`undefined` / ключ отсутствует, **не** `0`. Ноль оставлять только если
автор явно ввёл `0`. `RuleViewLabelService` / `WeaponProfileView` —
показать число, если оно есть.

Spread `{ ...modelValue }` поля рантайма не режет, но локальный тип врёт
автору редактора и провоцирует собрать объект «только из известных ключей».

### A4. Валидация

Не требовать поле. Не ограничивать снизу `−6`. Если значение задано —
целое число. `ItemModifierService` поле не трогает (клонируется со
спеком профиля).

## 4. Этап B — Game

### B1. AttackOverview

Спек профиля — `dodge_benefit` (snake_case). В `AttackOverview` поле
вертикали листа — `dodgeBenefit`, как `damageTypeCode` / `itemRuleCode`.
Перенос 1:1, не считать из формулы.

### B2. DodgeSoakService

`baseSoakValue(dexterity, dodgeBenefit)`: `Ловкость.modify(число)`.
Нет числа → `−3` + warn (+ alert только живой dev, не test). Чтобы warn
назвал предмет, в `amount()` нужен контекст (`itemRuleCode`,
`profileIndex`) — сейчас сигнатура его не имеет. Дальше текущий
`applyCuts`: `sizeDelta` → `subtract` Реакции → `ignoreAtSr` →
`max(0, toNumber)`.

### B3. HitLaunch

В `amount()` передать `resolvedAttack.dodgeBenefit`. Не считать из
формулы урона. `AttackDamageService` по-прежнему получает готовый
`dodgeSoak`.

`attackFromOffer` не обязан класть поле в proposal: `resolvedAttack`
пересобирает профиль через `attackAtDistance`. Если overview нет —
fallback `−3` и warn.

### B4. Прочие applyAttackDamage

DOT / заклинания / толчок / рывок soak профиля не берут. Нет реакции
`dodge` — слоя нет.

## 5. Тесты

Не импортировать шпаргалку §1.2 в сервисы и не искать коды каталога.

- `DodgeSoakService`: заданный модификатор; нет модификатора → как `−3`;
  не dodge → 0; cuts после базы.
- Overview: `dodgeBenefit` с `profile.dodge_benefit`; два профиля одного
  предмета — разные числа.
- Каталог и выгружаемые моки — поле есть.
- Без поля — только отдельный тест fallback, не данные выгрузки.

Не mount `HitLaunchDialog`.

## 6. Гейт

- поле опционально в DTO;
- каталог, щиты, врождённое проставлены (`[3]`/`[6]` → `−4`);
  в выгрузку профили без поля не попадают;
- редактор на DTO, есть ввод пользы;
- soak = `Ловкость.modify(dodge_benefit | −3)` только на dodge;
- нет поля → warn / dev alert, не `0`;
- план-11 S0 считается снятым.
