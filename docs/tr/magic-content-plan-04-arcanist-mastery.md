# План реализации магии 04 — мастерство Арканиста

**Статус:** `READY`, 2026-09-26.
**Дизайн:** [`magic-content-design-03-arcanist-mastery.md`](magic-content-design-03-arcanist-mastery.md).
**Состав:** `magic-structure-construction`,
`magic-structure-interaction`.

План не включает третью способность высшего образования: в текущем каталоге и
релизном срезе её нет.

## 1. Результат

Добавить две карточки высшего образования Арканиста и провести их эффекты
через существующие контуры:

1. **Конструирование магических структур**
   - стоимость `2 ОР`;
   - требования: `magic-structure-overview`, `fizika`,
     `basic-element-properties`;
   - два гранта `magic_study` для `arcanist`;
   - потолок стоимости каждого гранта равен текущему целому значению
     Интеллекта;
   - изученные способности сохраняются при снижении Интеллекта, но теряют
     доступность применения до восстановления нужного значения.
2. **Взаимодействие структур волшебства**
   - стоимость `3 ОР`;
   - требование: `magic-structure-construction` и `40` опыта пути Арканиста;
   - постоянный модификатор `+2` к эффективности `check-spell-cast`;
   - источник модификатора — `mastery`;
   - с бонусом `+1` от `basic-element-properties` применяется больший
     модификатор, а не сумма.

## 2. Контент Rule

### 2.0. Важное ограничение текущего кода

`MagicStudyUnlockService` сейчас получает сырые `Grant` и напрямую сравнивает
`grant.max_cost` с числом стоимости. `EditorMagicPathViewsService` строит
сводку из `CharacterBuild`, в котором нет вычисленного значения
характеристики. Поэтому нельзя просто заменить тип `max_cost` и оставить
остальные вызовы без контекста.

Нужно разделить:

1. **сырой контентный grant** — хранит формулу;
2. **разрешённый grant** — содержит вычисленный числовой `maxCost` для
   конкретного snapshot/build;
3. **показ UI** — получает разрешённое значение либо безопасную подпись
   формулы, но не вычисляет правило в компоненте.

`RuleViewLabelService` не должен самостоятельно вычислять лимит: у него нет
CharacterSnapshot. Он может форматировать формулу, а числовое ограничение
должно приходить из Character/editor-сервиса.

### 2.1. Карточки

Файл: `Roleplay/Rule/Mock/mockSpellImport.ts`.

Добавить константу:

```ts
const ARCANIST_HIGH_SECTION =
  'abilities-acquired-magic-paths-arcanist-education-high';
```

Добавить две локальные `rule()`-карточки:

- `magic-structure-construction`;
- `magic-structure-interaction`.

Для обеих:

- `type: 'ability'`;
- `spec.type: 'skill'`;
- секция `ARCANIST_HIGH_SECTION`;
- признаки `SKILL_KEYWORD`, `MAGIC_KEYWORD`,
  `METHOD_INTELLECT_KEYWORD`, `MAGIC_PATH_KEYWORD`, `ARCANIST_KEYWORD`;
- `parent_ability_code: null`;
- без `contentNote`, если заявленная механика полностью поддерживается;
- описания и подсказки копировать из design-документа.

### 2.2. Декларативный потолок изучения

Текущий `Grant` задаёт `magic_study.max_cost` как `number`, а
`MagicStudyUnlockService` сравнивает его напрямую с каталоговой стоимостью.
Для Конструирования нужен version-aware потолок.

Предпочтительный контракт:

```ts
type MagicStudyMaxCost = number | Formula;
```

Гранты карточки:

```ts
{
  type: 'magic_study',
  scope: 'spell',
  max_cost: { type: 'characteristic', characteristic_code: 'intellect', modifier: 0 },
  path_code: 'arcanist',
}
{
  type: 'magic_study',
  scope: 'non_spell',
  max_cost: { type: 'characteristic', characteristic_code: 'intellect', modifier: 0 },
  path_code: 'arcanist',
}
```

Если существующий `Formula` не подходит для семантики «целое значение
размерной характеристики», добавить отдельный явно названный вариант, а не
использовать строковую арифметику. Вычисление должно применять
`DimensionalNumber.from(value).toNumber()`.

Не дублировать грант отдельными spell/non-spell хардкодами в
`MagicStudyUnlockService`.

### 2.3. Модификатор эффективности

В текущем контракте способности с постоянным runtime-эффектом могут иметь
`grants: []`; эффект определяется наличием способности и доменным сервисом.
Для `magic-structure-interaction` не добавлять фиктивный `characteristic_modify`:

- модификатор не изменяет характеристику;
- он действует только на проверку `check-spell-cast`;
- его источник — `mastery`;
- он должен пройти общий агрегатор источников.

## 3. Character: динамическая доступность

### 3.1. Вычисление потолка

Проверить и расширить:

- `Rule/Dto/Ability/Grant.ts`;
- `Character/Service/MagicStudyUnlockService.ts`;
- `Character/Service/EditorMagicPathViewsService.ts`;
- `Rule/Service/RuleViewLabelService.ts`;
- `Rule/Service/Spec/AbilitySpecService.ts`;
- `Rule/Component/Editors/GrantEditor.vue`.

Доменный слой должен:

1. принимать числовой и формульный `max_cost`;
2. получать актуальный `CharacterSnapshot`/overview отдельным аргументом;
3. вычислять формулу и строить разрешённый grant;
4. сравнивать вычисленный лимит с базовой стоимостью способности.

`EditorMagicPathViewsService.build` нужно либо расширить контекстом
характеристик/overview, либо передавать ему уже разрешённые unlocks. Нельзя
получать текущий Интеллект из одного только `CharacterBuild`.

UI должен показывать вычисленный лимит, не сохраняя его как постоянное число.

Если редактор пока не умеет редактировать формульный `max_cost`, добавить
поддержку минимально необходимого варианта характеристики и не расширять
редактор произвольным языком формул.

### 3.2. Потеря доступности после снижения Интеллекта

Изученный экземпляр способности не удалять и уровень не обнулять.

Ввести единый доменный предикат доступности применения:

```text
ability is learned
  AND every active magic-study constraint for its path/scope is satisfied
```

Предикат должен использоваться до:

- выбора способности в действии;
- запуска заклинания;
- применения spell upgrade;
- runtime-проверки связанных заклинаний.

При недоступности возвращать обычную доменную ошибку/предупреждение, а не
молча удалять способность из `CharacterVersion`.

Точный UX текста ошибки и отображения не должен менять факт хранения
изученной способности.

## 4. Game: бонус Мастерства

### 4.1. Общий расчёт

Расширить существующий `SpellCastEfficiencyService`:

1. проверить наличие `magic-structure-interaction` у заклинателя;
2. добавить `{ sourceCode: 'mastery', delta: 2 }`;
3. сохранить существующий `{ sourceCode: 'mastery', delta: 1 }` для
   `basic-element-properties`;
4. передать оба через общий `aggregateSourceDeltasService`;
5. получить один итоговый бонус `+2`, а не `+3`;
6. применять только к `check-spell-cast`, не к другим проверкам.

Не читать признак/описание из Vue и не добавлять бонус в `SpellSpec`.

### 4.2. Недоступность способности

До формирования `SpellCastExecutionInput` проверить доменную доступность
способности. Если Интеллект ниже лимита изученного навыка или связанного
заклинания, каст/применение должен быть отклонён тем же контуром, который
проверяет доступность изучения.

Сопротивление, цели, ОД и содержание броска не менять в рамках этого плана.

## 5. Тесты

### 5.1. Контент

`Rule/__tests__/Mock/mockSpellImport.test.ts`:

- обе карточки существуют;
- секция — `...arcanist-education-high`;
- признаки совпадают;
- стоимости `2` и `3`;
- требования и отсутствие структурных грантов корректны;
- два `magic_study` имеют `scope`, `path_code: arcanist` и формульный
  потолок Интеллекта;
- описание содержит `+2` и подсказку про несложение одного источника.

### 5.2. Magic study

`Character/__tests__/Service/magicStudyUnlock.test.ts` и новый точечный
тест при необходимости:

- Интеллект `{3|0}` открывает стоимость `3`;
- Интеллект `{4|0}` открывает стоимость `4`;
- размерное значение вычисляется через `DimensionalNumber`;
- spell и non-spell используют одинаковый лимит;
- path `arcanist` не открывает способности другого пути;
- изменение Интеллекта не удаляет изученный экземпляр;
- при недостаточном Интеллекте экземпляр становится недоступен для
  применения и снова доступен после восстановления значения.

### 5.3. Efficiency

`Game/__tests__/Service/spellCastEfficiency.test.ts`:

- только `basic-element-properties` → `+1`;
- только `magic-structure-interaction` → `+2`;
- обе способности → `+2`, не `+3`;
- другие источники не меняют правило агрегации;
- бонус применяется только к `check-spell-cast`.

## 6. Порядок реализации

1. Расширить тип и вычисление формульного `magic_study.max_cost`.
2. Покрыть динамический лимит тестами.
3. Добавить карточку Конструирования и проверить доступность изучения.
4. Добавить единый предикат runtime-доступности изученных magic-study
   способностей.
5. Добавить карточку Взаимодействия.
6. Подключить `+2 mastery` к `SpellCastEfficiencyService`.
7. Обновить каталог и точечные тесты.
8. Запустить форматирование, lint и целевые Vitest-тесты.
9. После пользовательского smoke-теста обновить roadmap/status.

## 7. Не входит в план

- третья способность высшего образования;
- новые правила анализа структур;
- накопление времени исследования;
- магические кристаллы, мана и проводники;
- backend Rule contract;
- полная ревизия всех уже изученных способностей вне магического пути.

## 8. Гейт

- две карточки доступны в правильной секции;
- требования и признаки проходят validation;
- динамический лимит рассчитывается из текущего Интеллекта;
- изученные способности не исчезают при снижении Интеллекта;
- недоступность применения корректно блокируется;
- `mastery +2` не складывается с `mastery +1`;
- существующие spell-flow и проверки не регрессировали;
- точечные тесты и lint зелёные.
