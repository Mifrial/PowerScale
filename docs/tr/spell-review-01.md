# Review 01 — вопросы по терминам и пропускам магии

**Статус:** ожидает уточнений автора, 2026-09-07. Inventory — [`spell-inventory-01.md`](spell-inventory-01.md). План — [`spell-plan-01-inventory.md`](spell-plan-01-inventory.md).

Это очередь вопросов, а не список решений. Ответ можно дать прямо в таблице: коротко подтвердить вариант, исправить предложенный термин, добавить пропущенный фрагмент или написать `defer`.

## Как читать

- `Наблюдение` — что реально есть в выгрузке.
- `Проблема` — почему этого недостаточно для единого контракта.
- `Гипотеза` — рабочий вариант, не принятое решение.
- `Влияние` — что сломается или появится при выборе.
- Пока `Ответ` пуст, соответствующая сущность имеет `needs_decision`/`defer`.

## 4. Предлагаемые ранние решения

Это не принятые решения, а варианты для ускорения review:

1. Для M2 взять один source (`magic-core`) и один path (`arcanist`), а crystal/psionic/shaman оставить content-only до уточнения.
2. Развести `required_power`, `required_control`, `casting_time` и `action_costs`; не использовать одну `difficulty` как хранилище всех четырёх смыслов.
3. Считать текущий `SpellDuration` черновым UI-контрактом, не ограничением предметной модели.
4. До определения РУ, ипари и опыта школы оставить связанные эффекты в `description`/`text_only`.
5. Не импортировать в M2 path-specific скидки и сложные lifecycle-механики как runtime, пока не подтверждены их единицы и границы.

| SR-145 | Дистанции в системе являются размерными величинами; конкретная геометрия расстояний откладывается вместе с Battleground. |
| SR-146 | Battleground, вероятно, не входит в первый релиз; магический runtime не должен преждевременно зависеть от конкретной тактической геометрии. |
| SR-147 | Даже при одном source (`magic-core`) и одном path (`arcanist`) representative slice обязан показать формы выбора источника и пути. Упрощение набора данных не означает отсутствие этих вариантов в UI-контракте. |
| SR-148 | В M2 сразу входят cast fail, Арканный урон и Магическое отклонение. Их можно реализовать без Battleground; геометрия и полноценная тактическая обработка расстояний остаются за пределами первого релиза. |
| SR-149 | Состояние `Шок` нужно для выбранного электрического заклинания и входит в M2 вместе с электрическим уроном и проверкой концентрации, если она требуется действующим контрактом. |
| SR-150 | Canonical name trait-а кристалла — **«Врождённый магический кристалл»**. |
| SR-151 | Для trait/Item-контракта врождённого кристалла зафиксированы поля: `max_power`, `volume`, `recorded_spells`, `mana`, `mana_recovery`, `owner_bound`. |
| SR-152 | `X` — общий выбираемый параметр, но его тип зависит от позиции: в Мощи и Контроле это размерное число с базой 3–5; в других полях, например во Времени сотворения, `X` может быть обычным неразмерным числом. Для каждого параметра отдельно задаются допустимые границы, default и lifecycle-поведение. |
| SR-153 | Для записи вариантов в кристалл: `mana_limit = volume - recorded_spell_volume`; он должен быть не меньше максимальной `mana_cost` среди всех записанных вариантов, где `mana_cost = used_power × creation_in_turns`. Проверяется требуемая Мощь варианта, без произвольного усиления сверх требования; иначе запись запрещена. |
| SR-154 | Точная typed/domain implementation Духовности переносится в M3. В M2 достаточно ссылки на derived characteristic с зафиксированным правилом расчёта. |
| SR-155 | Canonical keyword опыта электромантии — `electromancy`; опыт считается как сумма базовых стоимостей способностей с этим keyword по существующему паттерну derived experience. |
| SR-156 | Formal Game distance contract для `ipari` откладывается до Battleground. До этого расстояние хранится как размерная величина в `ipari`, без метров, клеток и конкретной геометрии. |
| SR-157 | `X` не содержит поле `affects`. Объявление `action_parameters` описывает параметр (`code`, тип, границы, default и lifecycle), а `action_effects` ссылаются на него по `code`; валидатор проверяет наличие ссылки и совместимость типов. |
| SR-158 | Выбор source/path обязателен в UI representative slice, даже если в данных M2 доступно по одному варианту каждого. Это требование уже закрыто решением SR-147. |
| SR-159 | Магический источник в коде — `item` (`innate` + grant `item`). `RuleType.source` — источник модификаторов (`innate`, `armor`, код `spell`) и не используется как ядро/кристалл. |
| SR-160 | Параметры среза — существующий `AbilitySpec.parameters` с `resolution: 'activation'` и `Formula.type = 'parameter'`. Отдельные `action_parameters` / `affects` не вводятся. |
| SR-161 | Заклинание — действие: `action_effects` / атака не вырезаются у `spell`. Текущий union `ActionEffect` узкий (модификаторы удара); его расширяют касание, луч и автопопадение, а урон идёт через существующий attack apply. |
| SR-162 | РУ урона — всегда РУ проверки на попадание. РУ сотворения на урон не подставляется. Автопопадание задаёт фиксированный РУ атаки. Атака — необязательная доставка: типичный эффект — состояние с длительностью (например защита на 10 ходов / 1 минуту) без броска попадания. |
| SR-163 | Компоненты (ОД, соматика, касание) тратятся **до** успешности сотворения. ОД = **max**(ОД заклинания, ОД атаки касания). Касание — выбранная ближняя атака (любое оружие ближнего; «Проводник магии» пока игнорировать). Цель касания (персонаж или воздух) ≠ цель заклинания. Промах / воздух → молоко: сотворение идёт, эффект в пустоту. Сопротивление цели касания сложность не меняет. |
| SR-165 | Цель заклинания увеличивает сложность при сопротивлении магии. Если она обязательна и не выбрана — **автопровал попытки сотворения** (эффекты fail), не молоко. |
| SR-164 | 0 РУ атаки для **самой атаки** остаётся 0 РУ. Для **эффекта касания заклинания** 0 РУ атаки считается успехом с 1 РУ атаки. |
| SR-026 | Источник магии моделируется специальным `Item`: ядро — врождённое и базово неизвлекаемое, кристалл — врождённый при жизни, но извлекаемый после смерти. Мощь ядра X фиксирована и развивается модификаторами; несколько ядер выбираются независимо при cast. |

### SR-025 — форма агрегирования Духовности

После обсуждения буквальное среднее исключено: Шаман развивает три характеристики для одного прокаста, поэтому каждая должна давать собственный вклад, а итог должен расти быстрее среднего.

Рабочий вариант:

- для каждой из трёх характеристик получить вклад относительно `{5|0}`;
- сложить три вклада, чтобы каждая характеристика участвовала отдельно;
- за каждые 2 пункта суммы добавить `+1` к базовой Духовности `{3|1}`;
- пример `7 → +3` сохранить.

Упрощение делать на уровне игрока/UI: показывать три строки вкладов, сумму и итог, например `Общение +3 + Воля +2 + Внимательность +2 = 7 → Духовность {3|2}`. Не просить игрока разбираться с размерной арифметикой.

Подтверждено: характеристика ниже `{5|0}` даёт отрицательный вклад. Все три характеристики участвуют в сумме симметрично — превышение увеличивает Духовность, недобор уменьшает.

## 6. Итог текущего review

Основные спорные правила выгрузки согласованы:

- две характеристики сотворения: Магическая мощь и Контроль магии;
- Мощь/Контроль заклинания — параметры расчёта, не prerequisite изучения;
- источники как специальные `Item`, ядра и кристаллы с разным lifecycle;
- кристалл: trait, Предельная мощь, Объём, записи, мана и простейшее волшебство;
- path-bound изучение, повторная покупка через разные пути и асимметричное исключение Шамана;
- четыре режима длительности, стабильность, дестабилизация и правила продолжения;
- Сложность сотворения, дефицит/превышение Мощи и Контроля;
- failure, Магическое отклонение и Арканный урон;
- сопротивление магии как `arcane` resistance с дополнительным влиянием на cast difficulty;
- Стоимость изучения, скидки пути и правило Арканиста «два за 1 ОР»;
- касание — выбранная ближняя атака до check; ОД = max; молоко = промах/воздух при живом сотворении; нет обязательной цели заклинания = auto-fail; 0 РУ атаки → 1 РУ только для эффекта касания заклинания.
