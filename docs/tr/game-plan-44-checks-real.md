# План 44 — проверки в real-режиме

**Статус:** ~ЧАСТИЧНО~ (соло и оферты работают в real; ручная проверка за
пользователем)

**Реализация:** ~PHP~, ~VUE~

**Опираться на:** ~PHP~, ~НЕ ОСНОВА~

**Родитель:** [`game-roadmap.md`](game-roadmap.md).
**Связанные:** [`game-plan-18.md`](game-plan-18.md) (бэкенд соло и текущий
pairwise), [`rule-content-plan-16-melee-tactics.md`](rule-content-plan-16-melee-tactics.md)
(S2a), [`rule-content-plan-02-concentration.md`](rule-content-plan-02-concentration.md)
(жетоны на проверках).

Цель — перевести `CheckLaunchDialog` в real-режим (`GameApi`, PHP) и довести
pairwise-проверку до двусторонней модели: обе стороны выбирают характеристику
и преимущества, сервер бросает оба пула после согласия и пишет результат в чат.
Мок `CheckOffer` и `CheckLaunchDialog` — не контракт, но их поля удобны как
форма ответа: сервер отдаёт ту же форму, а решения и броски считает сам.

## 1. Границы

Входят:

- соло-проверка через `game.declareCheck` без клиентского броска;
- двустороннее предложение проверки: `propose`, `revise`, `cancel`,
  `answer`, список ожидающих предложений;
- серверный совместный бросок: у каждой стороны свой пул, сложность каждой
  стороны — успехи другой;
- серверное сообщение проверки в чат: объявление, оба броска, исход;
- версии листов обеих сторон и CAS в одной транзакции;
- точки для траты жетонов концентрации в предложении (механика — S2b
  плана-16).

Не входят:

- оферты удара, защиты, Прикрытия и заклинаний — у них свой путь через
  `game.runAction` и `CheckOffer` атаки;
- запись состояний и последствий проверки в лист: список операций пока пуст;
- широкий удар, `N → N`, инициатива, DOT, удержание концентрации;
- новые таблицы.

## 2. Что уже есть

- `game.declareCheck` — соло: участник, карточка, трудность `ask`, бросок и
  рейтинг на сервере, `resolve` process в той же транзакции.
- `game.proposeCheck` / `game.answerCheck` — предложение одной цели и ответ
  `accept | decline`; на `accept` сервер бросает **один** пул проверяемого.
  Это уже не совпадает с двусторонним окном мока.
- `GameChecks::view` отдаёт только `roll.base` / `roll.size`; граней,
  преимуществ и успехов в ответе нет.
- Сервер проверку в чат не пишет.
- `GameApi` методы проверок (`createCheckOffer`, `reviseCheckOffer`,
  `acceptCheckOffer`, `cancelCheckOffer`, `getCheckOffers*`) бросают
  `throwPhpUnsupported`; `CheckLaunchDialog` в соло бросает кубики сам.
- `GameChatTab` уже умеет показывать ожидающие предложения и открывать окно
  проверки с `resumeOffer`; ему нужен реальный источник предложений.

## 3. Контракт

### 3.1 Соло

`game.declareCheck` не меняет вход. Ответ `GameChecks::view` расширяется
деталями броска, которые уже считает `GameCheckRoll::scored`:

```text
faces, adjustedRolls, successes, droppedRolls, dieFaces, advantages,
min_success_size
```

Клиент больше не бросает кубики и не считает успех. `expectedSheetVersion` —
версия листа участника, `idempotencyKey` — ключ команды.

### 3.2 Предложение

Тело предложения повторяет поля мока, чтобы фронт не переписывал окно:

```text
ruleCode
initiator: { type, id }
opponent:  { type, id }
initiatorCharacteristic, opponentCharacteristic
initiatorAdv, opponentAdv
initiatorFree, opponentFree        // { diceCount, dieSize, efficiency }
initiatorSpendConcentration, opponentSpendConcentration
```

Блоки обеих сторон лежат в JSON `proposal` строки `game_check`. `waitingOn`
(`initiator` или `opponent`) и `revision` — там же. Сторона, которая ждёт,
может править только свой блок и принять/отклонить предложение.

Правила:

- инициатор и цель — разные участники игры или боя;
- проверяемая карточка допускает режим `joint` или `both`;
- характеристика каждой стороны принадлежит её листу или заменяется
  свободным пулом; чужая сторона блок не меняет;
- преимущества — целые в допустимом диапазоне;
- `spendConcentration` проверяется на сервере при принятии, а не при
  предложении: до броска жетоны не списываются.

### 3.3 Действия

| Команда | Что делает |
| --- | --- |
| `game.proposeCheck` | создаёт process и `pending`-предложение, броска нет |
| `game.reviseCheck` | меняет блок ждущей стороны, поднимает `revision` |
| `game.cancelCheck` | отменяет `pending`, process → `cancelled` |
| `game.answerCheck` | `decline` — отказ; `accept` — бросок обеих сторон |
| `game.getCheckOffers` | список ожидающих предложений игры или участника |

`game.answerCheck` на `accept` принимает `expectedSheetVersion` принимающей
стороны. Версия второй стороны сохраняется в предложении при `propose` или
`revise`; на принятии обе версии проверяются, иначе `GAME_CONFLICT`.

### 3.4 Совместный бросок

Обе стороны бросают свои пулы. Сложность каждой стороны — успехи другой
стороны, как в `CheckRollService.rollJointCheck` мока. Трудность `ask` в
совместной проверке не запрашивается и не требуется: она не участвует в
броске. Соло-проверка с `difficulty_input.kind = ask` без `askedDifficulty`
по-прежнему отклоняется. Сервер считает
`roll`, `difficulty`, `success`, `rating` для каждой стороны и складывает в
JSON `rolls`:

```text
{ initiator: { roll, difficulty, success, rating, faces, advantages, ... },
  opponent:  { ... } }
```

Броски обоих пулов и запись листов идут в одной транзакции с `resolve`
process. Пока список операций листа пуст, листы только проверяются на версию.

### 3.5 Чат

Сервер пишет в чат игры:

1. объявление: кто какую проверку предлагает и против кого;
2. после `accept` — бросок каждой стороны и итог;
3. после `decline` / `cancel` — короткий отказ.

Сообщения проверки идут без боевого треда: сворачивание проверок — отдельная
задача. Текст и вложения броска собирает отдельный `GameCheckChat`, чтобы
`CheckLaunchDialog` не был источником истины.

### 3.6 Ожидающие предложения

`game.getCheckOffers` отдаёт `pending`-строки в форме `CheckOffer`:
`id` = `processId`, `checkCode`, `initiator`, `opponent`, `proposal`,
`waitingOn`, `status`, `updatedAt`. `GameChatTab` уже опрашивает этот список
раз в две секунды, поэтому отдельный канал доставки в этом срезе не нужен.

## 4. Физическая схема

Новых таблиц нет. На `game_check` появляются два необязательных `JsonField`:

- `proposal` — блоки сторон, `waitingOn`, `revision`, версии листов;
- `rolls` — результаты совместного броска.

Колонки соло (`asked_*`, `difficulty_*`, `success_*`, `passed`, `rating`)
остаются и заполняются для соло. У предложения до принятия они пустые.
`offer` принимает `pending`, `accepted`, `declined`, `cancelled`.
`game_process` колонками не растёт.

## 5. Фронт

- `GameApi.createCheckOffer` → `game.proposeCheck`;
- `reviseCheckOffer` → `game.reviseCheck`;
- `cancelCheckOffer` → `game.cancelCheck`;
- `acceptCheckOffer` → `game.answerCheck` с `accept`;
- `getCheckOffers*` → `game.getCheckOffers`;
- `CheckLaunchDialog` в real не вызывает `checkRollService` и не списывает
  жетоны; показывает ответ сервера и ждёт броска после `accept`;
- `resumeOffer` гидрируется из ответа сервера, как сейчас из мока.

## 7. Тесты

- MySQL: соло отдаёт грани и преимущества; клиентский бросок не принимается.
- MySQL: предложение `pending`, чужая сторона не правит чужой блок, `revise`
  поднимает ревизию, `decline` и `cancel` не бросают.
- MySQL: `accept` бросает оба пула, сложность каждой стороны — успехи
  другой, результат в `rolls`, process `resolved`.
- MySQL: конфликт версии любой стороны не оставляет частичной записи.
- MySQL: повтор `idempotencyKey` не бросает второй раз.
- MySQL: `getCheckOffers` отдаёт только `pending` и нужного участника.
- MySQL: серверное сообщение проверки появляется в чате.
- Frontend: маппинг `CheckOffer` ⇄ ответ сервера, `resumeOffer`, отсутствие
  клиентского броска в real.

## 8. Сделано

- соло в real: `game.declareCheck` отдаёт грани, успехи и преимущества,
  `GameApi` больше не бросает кубики на клиенте;
- двусторонняя оферта: `proposal`/`rolls` на `game_check`, `proposeCheck`,
  `reviseCheck`, `cancelCheck`, `answerCheck`, `getCheckOffers`;
- совместный бросок: у каждой стороны свой пул, сложность — успехи другой;
  версии обоих листов проверяются в одной транзакции;
- серверный чат: предложение, отказ, отмена, два броска после согласия;
- `GameChatTab` получает ожидающие предложения через `game.getCheckOffers`
  один раз при открытии вкладки и по realtime-событию `source = 'check'`
  (без таймера); каждый `propose`/`revise`/`answer`/`cancel` пишет строку
  outbox, SSE доставляет её курсором, клиент перечитывает pending-оферты;
- ведущий (`canEdit`) отвечает за сторону, на которой стоит `waitingOn`,
  независимо от выбранного «говорящего»: окно открывается самому ведущему,
  «Принять и бросить»/«Вернуть правку» работают от имени ждущей стороны;
  сервер подтверждает право владельца/`gm`/`EDIT_ALL`;
- окно проверки закрывается само, когда привязанная оферта перестала быть
  `pending` (бросок, отказ, отмена) — у обеих сторон, без ручного закрытия;
- `game.answerCheck` принимает правку ждущей стороны в `answer.proposal`:
  блок стороны сливается до броска, обе версии листов проверяются в одной
  транзакции; ответ отдаёт `sheetVersions` обеих сторон для контекста фронта;
- концентрация: стороны передают `spendConcentration`, сервер проверяет
  спеку, максимум и цикл, списывает жетоны и добавляет преимущество;
- `Расчётливая атака`: режим `accuracy` в `tokenSpend` удара, мастерство
  оружия `4|0`, контент — ревизия 34.

Тесты: `GameCheckMysqlTest` (соло, оферты, правка, отмена, бросок, чат),
`GameStrikeMysqlTest` (жетон преимуществом и Точностью), unit цикла.

## 9. Открытые вопросы

- Нужен ли проверкам боевой тред и сворачивание, как у ударов.
- Кто может отменить предложение: только инициатор или любая сторона.
- Что считается ничьей в совместной проверке, если обе стороны получили
  одинаковый рейтинг; для проверки достаточно двух `success`, для Обмана
  понадобится явный победитель.
