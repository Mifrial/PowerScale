## Что PHP Rule уже разбирает

- `DefenseSlot`: пара `defense`, целая `durability`, optional `source_code`.
- `ResistanceSlot`: optional `damage_type_code`, пара `value`, целая `durability`, optional `source_code`.
- `BlockProfile`: пары `efficiency` и `defense`, список `resistances`. У защиты профиля поля надёжности нет.
- `DamageTypeSpec::isDefenseIgnored()`.
- `WeaponProfile`: формула `penetration`, не готовая пара.
- Свёртка модификаторов одного source в [`rule-system.md`](rule-system.md): сильнейший плюс и сильнейший минус. Это сказано про модификаторы, не про отбор слоёв удара.

`GameStrikeRules` по-прежнему суммирует только совпавшие слоты сопротивления надетой брони. Защиту, надёжность, пробитие и источник он не читает.

## Почему расчёт здесь не закрывается

Срез надёжности по РУ включается хуком механики `pay_sr_vs_reliability` на типе урона. В spec типа такого поля нет. Код механики в Rule зашивать нельзя: соответствие `(code, version) → handler` — ответственность Mechanic. Хендлер этим шагом не добавляется.

Список слоёв цели — надетая броня, сопротивления вне брони и выбранный блок — не лежит в spec предмета. `FormulaContext` считает формулу по уже собранному листу и не говорит, какие слоты надеты. Второго листа заводить нельзя. Пробитие профиля считается тем же `evaluateDimensional`, но только после того, как вызывающий собрал контекст. Это не замена проекции защиты.

У защиты блока нет `durability`. Подставлять порог, чтобы срез РУ «как-нибудь» сработал, нельзя: во frontend для этого стоит константа 99, это не spec.

Пока нет отдельного контракта «какие слои на цели» и «когда тип платит РУ за надёжность», Rule не может честно вернуть effective resistance.

## Чего нет

Новых DTO, порта и тестов расчёта. Сложения пар на `DimensionalNumber`: его по-прежнему держит Game для удара. Каталога, ран, DOT, каста, `throw`/`shoot`.
