## Цель

Сделать изучение карточки **в рамках пути** реальным на сервере:

- обычный путь открывается грантом `magic_path`; `magic_study` может дать
  ограниченное изучение и без него (`psionic-awakening`);
- изучение разрешается грантом `magic_study` с потолком стоимости и списком
  путей;
- путь, опыт пути и требования `has_magic_path` / `magic_path_experience`
  считаются в Character, а не остаются `null`;
- покупка карточки без подходящего `magic_study`-гранта отклоняется
  сохранением.

Правило не делит карточки на «заклинания» и «не-заклинания». Изучаться в
рамках пути может любая карточка: заклинание, оружейный/магический навык,
улучшение пути.

## Принципы

- В PHP нет кодов `arcanist`, `becoming-arcanist`, `discharge`, `spell`,
  `magic`, `magic-path` как веток логики. Все коды приходят из данных.
- Если спеку не хватает, чтобы выразить правило, расширяется спека. Если
  правило процедурное — используется механика/процесс. Ветка «если код такой,
  то поведение такое» запрещена.
- `spell`/`non_spell` из `magic_study.scope` не используются: это деление не
  описывает, как карточка изучается.
- Старые ревизии остаются читаемыми: парсер понимает прежние `path_code` и
  `scope`, но новая логика их не интерпретирует.

## Модель

### Карточка

У способности появляется правило «изучается в рамках пути»:

```json
"study": {
  "paths": "any"
}
```

или

```json
"study": {
  "paths": ["arcanist"]
}
```

- `paths: "any"` — карточку можно изучать на любом открытом пути.
- `paths: ["code", ...]` — только на перечисленных путях.
- Путь экземпляра хранится в `choices.abilities[].domainCode`; карточка с
  `study` обязана иметь `domain_ref: magic-path`, чтобы этот код был путём, а
  не произвольным доменом.
- Правило `study` — явный маркер, а не вывод из грантов. Карточка, которая
  сама даёт `magic_study`, не освобождается от гейта автоматически: иначе
  продвинутые карточки вроде «Составных структур» станут входами без пути.
  Освобождаются только карточки, которые контент явно объявил входами
  (дают путь или новый набор для изучения); список фиксируется в миграции.
- Карточки с `parent_ability_code` (улучшения) собственный путь не выбирают:
  они наследуют путь родителя. Это отдельное правило, см. «Открытые вопросы».

### Грант пути

`magic_path` открывает путь для силы/контроля, проверки пути и
`has_magic_path`. `includes_path_codes` расширяет набор путей односторонне:
шаман включает псионика, псионик шамана — нет.

`magic_path` **не является** обязательным условием изучения: `psionic-awakening`
даёт `magic_study` на `psionic`, но пути не даёт. Персонаж может выучить одно
псионическое заклинание без пути. Поэтому гейт изучения смотрит только на
`magic_study`, а не на пересечение с `magic_path`.

### Грант изучения

`magic_study` заменяет `scope` и одиночный `path_code` на список путей:

```json
{
  "type": "magic_study",
  "paths": "any",
  "max_cost": 2
}
```

или

```json
{
  "type": "magic_study",
  "paths": ["arcanist", "psionic"],
  "max_cost": { "type": "to_scalar", "value": { "type": "characteristic", "characteristic_code": "intellect", "modifier": 0 } },
  "max_instances": 1,
  "paid_cost": 0
}
```

- `paths: "any"` — грант открывает изучение на любом пути, который есть в
  ревизии.
- `paths: ["code", ...]` — только на этих путях; включения пути раскрываются
  транзитивно.
- `max_cost` — потолок **базовой** стоимости карточки (первый уровень), не
  сумма до текущего уровня. Поле остаётся обязательным: отсутствие — битая
  форма, а не «без потолка». Число и формула поддерживаются, формула
  считается `IFormulaEvaluations`, не хардкодом.
- `max_instances` читается и ограничивает число экземпляров на путь.
  `paid_cost` — цена экземпляра в билде, а не серверная проверка бюджета ОС;
  в этом плане он остаётся за редактором (см. «Границы»).

Доступность карточки = пересечение:

```
пути карточки (study.paths)
∩ пути активных грантов magic_study (paths, с includes)
```

`magic_path` в это пересечение не входит. Пустое пересечение — карточка
недоступна. Если путей несколько, редактор показывает выбор одного; для
`multiple` можно взять несколько экземпляров на разных путях в пределах
`max_instances`.

Пример: `psionic-awakening` даёт `magic_study(paths: ["psionic"], max_cost: 1,
max_instances: 1, paid_cost: 0)`. Карточка `paths: "any"` → доступен ровно один
псионический spell ≤1, хотя `magic_path` у персонажа нет.

### Опыт пути

Опыт пути `P` — сумма стоимостей активных карточек с доменом пути `P` или с
его признаком (`арканист`, `псионик`, …), включая пути, которые `P` включает.
Это касается и заклинаний, и не-заклинаний, и входной карточки пути
(`becoming-arcanist` даёт 2 опыта Арканиста).

Для `max_cost` берётся **цена первого уровня**; для опыта — **сумма до взятого
уровня**. Это разные величины, их нельзя считать одним методом.

Стоимость берётся из зон спеки. Поддержаны `array`, `progression` и
`parameter`; `parameter_table` и `parameter_sum_tables` возвращают `null`, а
не 0. `CharacterDerivedLevels` сохраняет прежнее поведение (null как 0), а
study-гейт для карточки с такой зоной даёт явную ошибку формы. Логику цены
выносим из `CharacterDerivedLevels` в общий сервис, второй расчёт не пишем.

### Требования

`CharacterRequirementFacts` заполняет:

- `magicPaths` — пути из `magic_path` с учётом включений;
- `magicPathExperience` — опыт по путям (включая пути, изученные без
  `magic_path`, например через `psionic-awakening`).

После этого `has_magic_path` и `magic_path_experience` перестают возвращать
`null`. В ревизии 45 уже есть 5 карточек с такими требованиями; сейчас они
проходят всегда.

Проверка требований становится **жёсткой при сохранении**, но не удаляет уже
изученное. Новая покупка, у которой эффективный уровень ниже купленного, —
problem. Если способность уже была в предыдущем листе (например, Интеллект
снизили позже), она остаётся изученной, но неактивной: уровень 0 не блокирует
save. Это соответствует канону «изученное сохраняется, доступность теряется».

Для update нужен предыдущий лист/choices, чтобы отличить новую покупку от
уже изученной карточки. Create проверяет всё как новое. Старые сохранённые
листы читаются; отказ возникает только при новом save/update.

### Формулы

`max_cost` и другие формулы считает единственный `IFormulaEvaluations`.
Контекст собирает существующий `ICharacterFormulaContexts::build($sheet)`, а не
новый параллельный сборщик:

1. `CharacterSaveAssembly` сначала строит лист: `CharacterSheetLive` считает
   живые характеристики и эффективные уровни;
2. по готовому `sheet` вызывается `ICharacterFormulaContexts::build($sheet)`;
3. `IFormulaEvaluations` считает `max_cost` и другие формулы;
4. проверка study и требований идёт **после** compute, в
   `CharacterSaveAssembly`, где уже есть `sheet`, `choices` и `previousSheet`;
5. `GameCardAvailability` использует тот же `CharacterRequirementFacts` по
   документам `choices` и `sheet`, без второго расчёта.

Так формулы не считаются по купленным уровням: контекст всегда из готового
листа. Формульный `max_cost` делается сразу, без временного числового
варианта.

## Что сейчас в PHP

- `CharacterRequirementFacts::forModel` и `forDocuments` передают пустой
  `RequirementUnmodelled()`, поэтому магия в требованиях — `null`.
- `CharacterAbilityActivity::blockPasses` блокирует только явный `false`;
  `null` считается проходом.
- `MagicStudyGrant` разбирается, но `scope`, `max_cost`, `max_instances` и
  `paid_cost` нигде не читаются. `CharacterGrantCoverage` использует только
  `path_code` для `coveredPaths` и проверки указателя донора.
- `coveredPaths` считается и сохраняется, но покупку не ограничивает.
- `CharacterDerivedLevels` умеет считать стоимость, но метод приватный и
  привязан к производным уровням.
- `has_ability` в PHP не знает домен пути. В текущем контенте таких требований
  нет; для каста на нескольких путях это понадобится отдельно.

## Перепроверка 2026-11-09

Что уточнено после сверки с кодом:

- **Маркер `study` — явный.** Нельзя освобождать карточку только потому, что
  она даёт `magic_study`: так «Составные структуры» и «Конструирование»
  выпадут из гейта. Входы перечисляются в миграции.
- **`max_cost` — первый уровень, опыт — сумма до уровня.** Это разные
  величины; смешивать нельзя.
- **Формулы — сразу и в одном месте.** Вычисление остаётся за
  `IFormulaEvaluations`; контекст — существующий
  `ICharacterFormulaContexts::build($sheet)`. Проверки идут после compute,
  когда лист уже посчитан; отдельного числового `max_cost` не будет.
- **Требования отклоняют save.** Новая покупка без выполненных требований —
  problem. Уже изученная карточка при падении характеристики остаётся, но
  становится неактивной и save не блокирует. Старые листы читаются, отказ
  только при новом save/update.
- **Уровни для гейта — из готового листа.** Study и требования проверяются
  после `CharacterSheetLive`, по эффективным уровням, а не по купленным. Иначе
  путь с невыполненными требованиями мог бы открыть study, хотя в листе
  уровень 0.
- **`magic_study` без `magic_path`.** `psionic-awakening` даёт изучение
  псионического заклинания без пути. Пересечение с `magic_path` из гейта
  убрано.
- **`coveredPaths` не потребитель гейта.** Его читают только маски видимости;
  для study он не нужен. Не расширять его и не добавлять новые ключи в sheet
  без потребителя: `magicPaths` и опыт считаются в
  `CharacterRequirementFacts` на месте.
- **`paid_cost` и бюджет ОС.** Сервер не считает стоимость способностей и
  бюджет ОС; `paid_cost` остаётся редакторским. Гейт проверяет `max_cost` и
  `max_instances`, но не пересчитывает ОС.
- **Документы расходятся.** `spell-roadmap.md` §12, `character-plan-01.md` и
  `magic-content-plan-01/03/04` ещё описывают `scope` и `path_code`; их надо
  обновить или пометить, что новый контракт — `paths`.

## Работы

### 1. Rule

- `MagicStudyGrant`: `scope` и `path_code` заменить на `paths`
  (`"any"` или список). Старые поля читать для ревизий ≤45; `scope`
  игнорировать, пустой `path_code` даёт пустой список, не `"any"`.
  `max_cost` остаётся обязательным; старый `path_code` без `paths` читается
  как `[path_code]`.
- `AbilityBase`: добавить `study` (`paths: "any" | string[]`), геттер и
  валидацию формы. `study` без `domain_ref` — ошибка формы; путь экземпляра
  дополнительно проверяется как живой `magic_path` ревизии.
- `AbilityRequirements`: если понадобится `has_ability` с доменом пути —
  отдельный маленький шаг, не смешивать с этим.
- Тесты парсера: `any`, список, пустой список, старый `path_code`, битая форма,
  `study` без `domain_ref`.

### 2. Контент — ревизия 46

`tools/rule-migrate-46.php` из 45:

- `magic_study` переписывается в `paths`:
  - непустой `path_code` → `[path_code]`;
  - пустой `path_code` → пустой набор (ничего не открывает);
  - `scope` удаляется;
- карточки, которые изучаются в рамках пути, получают `study`:
  - заклинания — `paths: "any"`;
  - не-заклинания с путём — `paths: ["<path>"]`;
  - входы (`becoming-arcanist`, `structure-substitution`,
    `psionic-awakening`, `psionic-control`, `otherworldly-contact`) — без
    `study`. Это явный список контентного решения, а не вывод из грантов;
  - продвинутые карточки, которые сами дают `magic_study`
    (`composite-magic-structures`, `magic-structure-construction`), **получают**
    `study`: иначе они станут бесплатным входом;
- карточкам с `study` гарантируется `domain_ref: magic-path`;
- улучшения с `parent_ability_code` остаются без собственного `study` до
  решения о наследовании пути.

Список карточек для `study` фиксируется в миграции явно: это контентное
решение, а не вывод из ключевого слова в рантайме. После миграции обновить
`spell-roadmap.md` §12, `character-plan-01.md` и `magic-content-plan-01/03/04`,
где ещё написаны `scope`/`path_code`.

### 3. Character

- `CharacterMagicPaths`: пути из активных `magic_path` для силы/контроля,
  проверки пути и `has_magic_path`; транзитивные включения, чтение
  `MagicPathSpec`.
- `CharacterStudyPaths`: пути из активных `magic_study` (с включениями) — это
  источник разрешения на изучение, без обязательного `magic_path`.
- `CharacterSaveAssembly`: после `Character::fromDocument(...)` (там уже
  посчитан `sheet`) вызвать проверку study и требований. Формулы считать
  через `ICharacterFormulaContexts::build($sheet)`; порт пробросить в
  `CharacterSaveAssembly` или `CharacterSheetPortFactory`.
- `CharacterAbilityCost`: цена первого уровня и стоимость до уровня; вынести
  из `CharacterDerivedLevels`, старый вызов переиспользовать. Неподдержанная
  зона — `null`; производные уровни трактуют его как 0, study-гейт — как
  ошибку формы.
- `CharacterPathStudy`: для каждой карточки с `study` проверить путь, грант
  `magic_study`, `max_cost`, `max_instances`; `magic_path` не требовать.
  Нарушение — проблема сохранения.
- `CharacterRequirementFacts`: заполнить `magicPaths` и
  `magicPathExperience`; уровни для опыта — эффективные из `sheet`, не
  купленные.
- Жёсткая проверка требований: сравнить купленные уровни из `choices` с
  эффективными из `sheet`. Ниже — problem, если такого уровня не было в
  предыдущих `choices`; уже изученная карточка остаётся неактивной. Это
  использует существующее `CharacterAbilityActivity`, а не второй обход
  требований. Предыдущие `choices` передаются в `CharacterSaveAssembly`
  отдельно от `previousSheet`.
- `coveredPaths` для гейта не использовать; его чтение переведено на `paths`,
  новые ключи в sheet не добавлялись.
- Сохранение: билд с карточкой без подходящего study-гранта, с невыполненным
  требованием новой покупки или с битой формулой отклоняется, а не молча
  принимается.

### 4. Vue

- DTO `Grant`/`magic_study` — `paths` вместо `scope`/`path_code`.
- `MagicStudyUnlockService` и `EditorMagicPathViewsService` читают `study` и
  `paths`; конвенция по `magic`/`spell` убирается.
- Редактор при покупке карточки с `study` показывает пути из пересечения с
  `magic_study.paths` и потолок стоимости; сохраняет выбранный путь в
  `domainCode`. Отдельный `magic_path` для этого не нужен: `psionic-awakening`
  показывает `psionic` без пути.
- Мок не используется как источник правил; после изменения он должен давать тот
  же результат, что и real.

## Приёмка

- Новый персонаж покупает `becoming-arcanist`, сохраняет и перезагружает:
  путь считается в фактах, опыт пути доступен редактору и Game.
- `discharge` покупается в пределах `max_cost` на пути, открытом
  `magic_study`, и сохраняется.
- `psionic-awakening` открывает ровно один псионический spell ≤1 без
  `magic_path`; второй такой spell отклоняется по `max_instances`.
- Отказ: заклинание без study-гранта, заклинание дороже `max_cost`, карточка
  с чужим путём, новая покупка с невыполненным требованием уровня.
- Продвинутая карточка с `magic_path_experience` без опыта отклоняется
  сохранением, а не получает уровень 0.
- Старая игра на ревизии 45 читается и не ломается. Новая покупка без
  требований отклоняется; уже изученная карточка при падении характеристики
  остаётся неактивной и save не блокирует.
- В PHP нет захардкоженных кодов карточек/путей; поиск по `arcanist`,
  `becoming-arcanist`, `discharge` в логике пуст.

## Решено

- Явный `study` на карточке; `study.paths` остаётся ограничением путей.
- `domain_ref: magic-path` — отдельное правило «экземпляр живёт на пути», не
  замена `study`.
- Формульный `max_cost` делается сразу через существующий
  `ICharacterFormulaContexts::build($sheet)` и `IFormulaEvaluations`.
- Жёсткий отказ по требованиям — глобально при save для новых покупок; уже
  изученная карточка остаётся неактивной.
- `magic_study` без `magic_path` разрешён (`psionic-awakening`).
- Улучшения с `parent_ability_code` в этом срезе без `study`; наследование
  пути — отдельный шаг.
- Пустой `paths` в новой ревизии — ошибка формы; прежний пустой `path_code`
  читается как пустой набор.
- `coveredPaths` переведён на `paths`; гейт его не использует.
- Уже изученная карточка определяется по предыдущим `choices`, а не по
  `previousSheet`: уровень 0 в листе не означает «не куплена».

## Осталось отдельными шагами

1. **Улучшения:** `parent_ability_code` наследует путь родителя. В этом срезе
   улучшения (например `chain-lightning`) остаются без `study`: в `choices`
   нет ссылки на экземпляр родителя. Отдельный шаг — связать экземпляр
   улучшения с родительским и проверять его путь.
2. **`has_ability` с доменом пути:** нужен для каста `lightning-strike` на
   нескольких путях, чтобы требование `discharge` не срабатывало от чужого
   пути. Отдельный маленький шаг.

## Границы

- Game-каст, `ActiveSpell`, сложность сотворения и урон — не этот шаг.
- Бюджет ОС и `paid_cost` сервером не пересчитываются; это редакторский слой.
- Скидка пути и «два за 1 ОР» (`MagicPathSpec::study_cost`,
  `CharacterStudyPairs`) — отдельный шаг.
- `has_ability` с доменом пути — отдельный маленький шаг; без него
  `lightning-strike` на одном пути может увидеть `discharge` с другого.
