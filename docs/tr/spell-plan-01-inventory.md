# План M1 — inventory магии из AI.html

**Статус:** завершён, 2026-09-07. Родительская нарезка — [`spell-roadmap.md`](spell-roadmap.md). Источник — [`docs/rule/spell/AI.html`](../rule/spell/AI.html). Канон текущей модели — [`rule-system.md`](rule-system.md), [`decisions.md`](decisions.md), [`../specs/ability-parameters.md`](../specs/ability-parameters.md).

## Цель

Получить проверяемый inventory содержимого `AI.html`, не расширяя пока DTO и runtime. `AI.html` — неполная рабочая вырезка из старой версии правил, которую автор существенно переписывал по ходу подготовки. Она является источником наблюдений и вопросов, но не полным или нормативным описанием системы.

Результат должен позволить выбрать M2 — representative vertical slice — и отделить:

- сущности, которые можно импортировать как Rule;
- зависимости, которые нужно сначала нормализовать;
- текстовые эффекты, которые пока остаются в description;
- неоднозначности, требующие решения;
- возможные пропуски и места, где нужно восстановление контекста от автора;
- контуры, которые сознательно остаются `DEFERRED`.

M1 не реализует заклинания, не меняет `SpellSpec`, не создаёт backend-таблицы и не объявляет runtime-механику подтверждённой.

## Артефакты M1

Результаты не прятать только в этом plan-файле:

- [`spell-inventory-01.md`](spell-inventory-01.md) — каталог сущностей, терминов и зависимостей;
- [`spell-review-01.md`](spell-review-01.md) — очередь вопросов автору, включая возможные пропуски;
- этот файл — scope, порядок работ и гейт M1;
- [`spell-roadmap.md`](spell-roadmap.md) — агрегированный статус и переход к M2.

Если inventory вырастет слишком сильно, каталог и review можно разделить по партиям, но ссылки из review должны оставаться устойчивыми.

## Результаты

### 1. Каталог сущностей

Для каждой сущности зафиксировать:

| Поле | Назначение |
| --- | --- |
| `source_locator` | заголовок/фрагмент или устойчивый ориентир в `AI.html` |
| `source_name` | имя как в источнике |
| `canonical_code` | предварительный семантический код, `TBD` при конфликте |
| `kind` | `ability`, `spell`, `upgrade`, `path`, `source`, `resource`, `state`, `damage_type`, `characteristic`, `keyword` или `concept` |
| `parent_code` | путь, школа, базовое заклинание или улучшение |
| `keywords` | признаки и принадлежность к контуром |
| `cost` | стоимость и её зона/единица, если подтверждены |
| `requirements` | требования и ссылки по смыслу |
| `grants_effects` | структурируемые дары/эффекты |
| `parameters` | переменные `X`, `х`, `РУ` и другие параметры |
| `references` | ссылки на другие сущности и их ожидаемый тип |
| `disposition` | решение по импорту |
| `confidence` | `high`, `medium` или `low` |
| `notes` | противоречия, ручная интерпретация и остаток текста |

`canonical_code` на M1 является рабочим кодом inventory, а не финальным публичным кодом Rule. Изменения кодов и причины фиксируются в журнале.

### 1a. Обязательный review автора

Для каждого спорного места не выбирать молча один вариант. Завести review-запись:

| Поле | Назначение |
| --- | --- |
| `review_id` | устойчивый номер вопроса |
| `source_locator` | место в `AI.html` или отметка «ожидаемый, но отсутствует» |
| `observation` | что буквально видно в выгрузке |
| `problem` | конфликт термина, пропуск, старая формулировка или неясная семантика |
| `hypothesis` | предлагаемая интерпретация и почему она нужна |
| `alternatives` | другие разумные варианты |
| `impact` | какие DTO/runtime/контентные решения затрагиваются |
| `question` | короткий вопрос автору |
| `answer` | ответ автора, пока пусто |
| `decision_ref` | ссылка на принятое решение после ответа |

В review обязательно выносить:

- термины, которые названы по-разному в разных местах;
- поля, которые выглядят как остаток старой модели;
- правила, на которые есть ссылка, но которых нет в HTML;
- сущности, которые логично ожидать по контексту, но они отсутствуют;
- числа, размерности и стоимости, смысл которых нельзя восстановить однозначно;
- места, где «описание эффекта» может скрывать настоящую механику;
- несогласованности между вводной частью и конкретными карточками.

Ответ автора может быть коротким: подтвердить термин, переименовать его, дать пропущенный фрагмент или сознательно отложить вопрос. До ответа review-запись не закрывается, а связанная сущность получает `needs_decision` или `defer`.

### 2. Реестр терминов

Отдельно собрать термины, которые влияют на контракт:

- Магическая мощь, Контроль магии, Магия ядра;
- путь, источник, опыт пути, стоимость изучения;
- создание, ОД, секунды, ход, поддержание, обновление;
- длительное, мгновенное, обновляемое, поддерживаемое;
- РУ, размерность, сложность, эффективность проверки;
- компоненты, цель, дистанция, проводник, накопитель;
- сопротивление, дестабилизация, стабильность, магическое отклонение;
- улучшение, копия заклинания, ограничение применений.

Для каждого термина указать:

1. буквальное значение в источнике;
2. ближайшее существующее понятие в коде/ТР;
3. несовпадение или пропуск;
4. предварительное решение: `reuse`, `new_concept`, `text_only`, `needs_decision`.

Если термин встречается в нескольких вариантах, завести одну canonical-запись и список aliases. В код и DTO попадёт только canonical name после review; варианты из источника сохраняются как aliases/source text.

### 3. Карта зависимостей

Собрать directed graph ссылок:

```text
source/path/characteristic/resource
  → magic skill
  → spell
  → upgrade
  → damage/state/effect
```

Для каждой ссылки определить:

- сущность-источник и цель;
- semantic relation (`requires`, `grants`, `upgrades`, `available_for`, `uses`, `modifies`);
- обязательна ли цель для импорта;
- можно ли временно оставить ссылку как unresolved;
- образуется ли цикл.

## Правила разбора источника

### Типы сущностей

- «Навык», «Заклинание», «Улучшение» — кандидаты на `Ability` с явным `type` и level/upgrade relationship.
- «Путь волшебства» — отдельная группа контентных правил/способностей только после проверки повторного использования общей Ability-модели.
- «Источник волшебства», «Магическое ядро», «Магический накопитель» — не считать автоматически ресурсом или item; сначала зафиксировать их свойства и lifecycle.
- «Правило», «Особенность», пояснение и пример — сохранять как concept/source note, не создавать DTO без подтверждённой структуры.
- Урон, состояние, характеристика, ресурс и предмет — связывать с существующим RuleType только при явном evidence и достаточных полях.

### Стоимости

- Не угадывать зону `os`/`ol`/`or`, если источник её не задаёт.
- «Стоимость 0», «авто» и отсутствие стоимости различать.
- `X`, `х`, «за каждый», «до N» и зависимость от опыта фиксировать как параметр/условие, но не переводить в `Formula` без отдельного решения.
- Текстовые скидки пути («половина стоимости») помечать как candidate mechanic, а не вычислять при inventory.

### Требования и эффекты

- Явные требования переносить в нормализованный список с исходным текстом.
- Ссылки на характеристики и способности фиксировать отдельно от локализованной формулировки.
- Эффект считать структурируемым только если его форма однозначна и уже имеет доменный аналог.
- Сложные формулировки про РУ, дистанцию, концентрацию, провал, разрушение и выбор цели сначала сохранять как `text_only`/`needs_decision`.

## Disposition

Использовать ровно один основной статус:

| Disposition | Смысл |
| --- | --- |
| `import_candidate` | достаточно данных для M2/M3, ссылка и тип понятны |
| `text_only` | сохраняем описание, структурированный runtime не подтверждён |
| `defer` | сознательно не входит в первые срезы |
| `needs_decision` | без решения нельзя безопасно выбрать модель |
| `duplicate_or_variant` | вариант/дубликат, связать с основной сущностью |
| `source_artifact` | пример, повтор, редакционная заметка или ошибка источника |

Статус `import_candidate` не означает готовность runtime. Для него всё равно указываются confidence и missing dependencies.

`needs_decision` имеет приоритет над `import_candidate`: даже если сущность технически легко выразить, спорная семантика сначала проходит review автора.

## Рабочие партии

Порядок разбора:

1. общий вводный контур: правила, источники, пути и термины;
2. навыки магического ядра и базовые пути;
3. общие навыки волшебства;
4. электромансия и её damage/state-зависимости;
5. улучшения и цепочки;
6. остальные найденные направления и контент, не вошедший в M2.

После каждой партии обновлять:

- каталог сущностей;
- терминологический реестр;
- карту ссылок;
- список unresolved;
- предварительный список M2-кандидатов.

## Кандидаты для M2

Пока рассматривать как кандидатов, не как принятое решение:

- путь Арканиста;
- источник магического ядра;
- `Разряд` как мгновенное заклинание;
- `Удар молнии` как дистанционное мгновенное заклинание;
- `Генератор молний` как поддерживаемое заклинание;
- `Цепная молния` как upgrade;
- `Накопление зарядов` как upgrade с состоянием/ресурсом.

Окончательный slice выбирается после проверки ссылок, а не по именам из списка.

## Что не делать в M1

- не изменять [`SpellSpec.ts`](../../draft-front_1.2ds/src/modules/Roleplay/Rule/Dto/Ability/SpellSpec.ts);
- не добавлять новые `RuleType`;
- не писать importer, который сразу мутирует mock catalog;
- не проектировать PHP persistence;
- не принимать source/path/mana как готовые контракты;
- не считать все числовые формулировки параметрами;
- не исправлять источник молча: артефакт должен попасть в notes/disposition.

## Гейт M1

M1 закрыт, когда:

- каждая содержательная секция `AI.html` имеет inventory-представление или явный `defer/source_artifact`;
- у каждой сущности есть `source_locator`, `kind`, `disposition`, `confidence` и заметка о ссылках;
- нет безымянных unresolved-ссылок;
- все спорные места имеют `review_id`, сформулированный вопрос и ответ автора либо явное решение `defer`;
- canonical terms отделены от source aliases и не выбраны молча по одному варианту;
- термины «Мощь», «Контроль», источник, путь, создание, duration, РУ и мана имеют отдельную disposition;
- выбранный M2 slice покрывает минимум два типа duration, upgrade и один effect/failure-кандидат;
- итоги inventory не требуют молчаливого изменения текущего канона;
- roadmap M1 переведён в `DONE`, а M2 — в `IN_PROGRESS`.
