# Контекст обсуждения ТЗ — вспомогательный файл

## Этап 1: Анализ общего описания системы

### Предыстория обсуждения

Вопросы, которые задавались в ходе обсуждения, и ответы на них.

### 1. Наследование пространств — какой вариант выбрать?

Исходная идея: пространство B наследовало от A через parent-child связь. Рассматривались три варианта:

- **А) Ссылка на родителя** — нет дублирования, но сложные запросы просмотра (UNION, COALESCE), сложность растёт с цепочками.
- **Б) Копирование снепшота** — в момент наследования копируются все актуальные правила A в B. Простые запросы, полная независимость.
- **В) Гибрид** — копирование + мета-информация (`inherited_from`, `inherited_at`) для UI.

Решение: ✅ **Б — копирование снепшота**. Цепочки наследования разрешены, но при копировании каждая операция независима и цепочки не создают дополнительной сложности.

### 2. Может ли наследование быть цепочкой?

✅ Да, может (A → B → C). При выборе варианта Б (копирование) — не имеет значения, каждое копирование независимо.

### 3. Очистка истории

Обсуждалась возможность удалять неактуальные версии правил для снижения объёма БД. Варианты:
- Полное удаление — опасно, ломает ссылки от персонажей.
- Архивация в отдельную таблицу — данные сохраняются, но усложняет запросы.
- Soft-delete (`archived_at`) — безопасно, обратно совместимо.
- Ничего не делать — объём данных для текстовых правил невелик.

Решение: ✅ **Не делать.** Если в будущем понадобится — добавить `archived_at`.

### 4. Удаление правил

Решение: ✅ **Маркер-версия.** Создаётся запись `rule_versions` с типом `deleted`. `created_at` = время удаления. При просмотре на момент T: если последняя версия до T имеет тип `deleted` — правило считается удалённым.

Рассматривалась альтернатива: отдельная таблица `rule_deletions`. Отклонена — усложняет запросы, удаление логичнее как частный случай версии.

### 5. Права доступа

Решение: ✅ Система `permissions(group_id, permission_key)`. Ключи: `read`, `comment`, `edit`, `add_space`, `delete_space`, `manage_users`, `manage_groups`. Новые ключи добавляются без миграции схемы.

Обсуждалось: нужны ли права на управление пользователями и группами. ✅ Нужны.

### 6. Параллельное редактирование

Исходно был вопрос: нужен ли механизм синхронизации (блокировки и т.д.)?

Решение: ✅ Не нужен. Изменения — одна транзакция. Если хотя бы одно правило конфликтует — не сохраняется ни одно. Пользователь видит diff и выбирает: оставить чужую / оставить свою / редактировать. После разрешения конфликтов — повторное подтверждение всей пачки.

Обсуждалась альтернатива (частичное сохранение неконфликтующих правил) — отклонена, т.к. пакет правил может быть логически связан для администратора.

### 7. Персонаж и версии правил

Вопросы:
- Кто инициирует переход персонажа на новую версию правил?
- Что происходит с персонажем в игре при смене версии?
- Нужно ли разделение на две сущности?

Решение: ✅ 
- Владелец персонажа инициирует переход в любой момент.
- Если персонаж в игре — старая версия остаётся замороженной в игре (read-only).
- Ведущий может перевести игру на новые правила → старые персонажи становятся неактивными.
- При переходе образуются P_v1 (старый, в игре) и P_v2 (новый, на модерации). После одобрения P_v2 замещает P_v1.

### 8. Терминология — версия правила

Было замечание: версия правила определяется не только `created_at`, но и пространством.

Итоговое определение: **Версия правила** = комбинация `(rule_global_id, space_id, created_at)`. Две версии одного правила в разных пространствах — разные. **Версия правил** (набор) — состояние всех правил в данном пространстве на данный момент времени.

### 9. Пользователь

Решение: ✅ Базовая учётная запись (имя, логин, пароль). Набор полей может расширяться в будущем (email, аватар, настройки).

### Выявленные проблемы

1. **Валюты (1–3) — не типы правил**, а механики расчёта. Должны быть отдельной настройкой системы.
2. **Раса — контейнер/категория**, не тип наравне с характеристиками. Её иерархия (вид → подвид) — отдельный механизм наследования контента, не связанный с пространствами.
3. **Способности — слишком широкая категория.** Черты, навыки, действия, пассивные, улучшения — у всех разная структура.
4. **Характеристики и Ресурсы — похожи.** Возможно объединение.
5. **Эффекты и Состояние — runtime.** Не относятся к созданию персонажа напрямую.

### Предложенная реорганизация

- **Валюты** (ОС, ОЛ, ОР, ОУ, ОВ) — вынесены из типов правил, отдельная сущность.
- **Раса** — тип правила-контейнер, иерархический (parent_race_id). Наследование контента расы (вид → подвид) не связано с пространствами.
- **Характеристика** — размерное число [3–5|*]. Базовая или производная.
- **Ресурс** — упрощённая характеристика, размерный/безразмерный.
- **Способность** — общий тип с подтипами: черта, особенность личности, навык, действие, пассивная, улучшение.
- **Эффект** — тип правила для статусов.
- **Состояние** — не тип правила, а runtime-агрегат.

## Этап 3: Размерные числа

**Контекст из описания и доков:**
- Размерное число = `[a|b]`, где a — значение (целое), b — размер (показатель степени двойки)
  - `[3|2]` = 3 × 2² = 12, `[4|-1]` = 4 × 2⁻¹ = 2
- В игре используется стрелочная нотация: `5↓` = `[5|-1]`, `3↑↑` = `[3|2]`, `4` (без стрелок) = средний размер
- Характеристики: a = [3, 5], b — любой
- При выходе за 5 или ниже 3 — меняется размер (не значение):
  - `[5|5] + 1` → значение 6 (>5) → `[3|6]` (size+1, value сбрасывается на 3)
  - `[5|5] - 3` → три шага: 4, 3, 2 (<3) → `[5|4]` (size-1, value сбрасывается на 5)
  - `[5|-1] + 2` → 6 → `[3|0]`, ещё +1 → `[4|0]`
- Модификаторы вида `+3 к Силе` = +1 к размеру (не к значению). `+6` = +2 к размеру и т.д.
- Сравнение: приводить к **меньшему** размеру. `3↓ vs 2` (средний) → 2 приводим к малому: `2 × 2 = 4` малых. `3 < 4` → 3↓ проиграл
- Сложение: приводить к меньшему размеру (`[2|2] + [1|1]` → `[2|2] = [4|1]` → `[5|1]`)
- Размерные не складываются с безразмерными (ошибка)
- Округление: `[...]` = floor, для не-промежуточных результатов (`[5/2] = 2`)
- Где применяются: характеристики (всегда размерные), ресурсы (могут быть безразмерными), проверки (размер успехов = размеру характеристики)

**Обсуждение реализации:**
- Хранение в БД: два поля `value INT, size INT` (size=NULL для безразмерных)
- Для характеристик: `min_value=3, max_value=5`
- PHP-класс `DimensionalNumber` с методами:
  - `toFlat()`: `value * (2 ** size)`
  - `add(DimensionalNumber $other, ?int $min, ?int $max)`: привести к меньшему размеру → сложить → скорректировать по диапазону
  - `sub(...)`: аналогично
  - `step(int $delta, int $min = 3, int $max = 5)`: поэтапное изменение на ±1 с коррекцией размера при выходе за [min, max]
  - `compareTo(DimensionalNumber $other)`: привести к меньшему размеру → сравнить flat-значения
  - `toArrowString()`: преобразование в строку со стрелками
- UI: компонент `DimensionalValue`, отображающий `(value, size)` со стрелками. При >1 стрелке — степень (`↑⁷`). Поддержка ввода `5↓`
- Размерные не складываются с безразмерными (исключение/ошибка)
- Стоимости способностей — целые числа, не размерные
- В проверках: размер успехов = размеру проверяемой характеристики

**Граничные случаи:**
1. `[3|b] - 1` → значение 2 → size-1 → `[5|b-1]`
2. `[5|b] + 1` → значение 6 → size+1 → `[3|b+1]`
3. Многократное изменение: `[3|-5] + 10` — поэтапно
4. Экстремальные размеры (`[3|-100]`) — корректное отображение

**Коррекция по отображению (из обсуждения):**
- При >1 стрелке: `↑⁷` вместо `↑↑↑↑↑↑↑` (одна стрелка + степень)
- Сравнение: приводить к **меньшему** размеру (не к большему)

**Решения:**
1. ✅ Хранение: `value INT, size INT` (size=NULL для безразмерных)
2. ✅ PHP-класс `DimensionalNumber` с методами add, sub, step, compareTo
3. ✅ Коррекция диапазона при выходе за [3,5] — смена размера
4. ✅ Отображение: стрелка + степень при >1, поддержка ввода
5. ✅ Округление: floor для не-промежуточных результатов
6. ✅ Размерные + безразмерные: не складываются
7. ✅ Сравнение: приводить к меньшему размеру

## Этап 4: Создание персонажа

**Контекст из описания + доков + предыдущих этапов:**

Из описания:
- Два режима: свободное создание (ОС/ОР задаются или пустые) и через Игру (ОС/ОР от игры)
- Перетрата лимита → статус «Черновик»
- Последовательность: раса → ОС (черты) → ОЛ (особенности) → ОР (способности)
- Фильтры черт: доступные, потенциально доступные (для расы), недоступные, доступные благодаря расе, общедоступные
- Live-изменение характеристик при выборе черт
- Черновик в любой момент. Готов — только при соблюдении лимитов и требований
- В будущем: Закупка, История персонажа

Из доков (Основа персонажа):
- Расовая структура: Вид → Раса → Подвид
- У каждой расы: ОС, характеристики (базовые + опции), бесплатные черты, доступные черты, признаки
- Пример: Алиерец (10 ОС, Выносливость 5, опция Магия 5, бесплатно: черта до 2 ОС)
- Пример: Конструкт — особая механика (тело + разум + энергоблок)
- Возрастные ориентиры (для расчёта ОЛ)

Из Этапа 1:
- Статусы: Черновик → Готов → Модерация
- Персонаж версионируется
- Привязка к игре (старая версия заморожена, новая на модерации)

Из Этапа 2:
- Этапы создания: основа (ОС), личность (ОЛ), развитие (ОР)
- Не во всех версиях правил есть ОЛ
- visibility способностей определяет, на каком этапе показывать

Из Этапа 3:
- Характеристики — размерные числа с коррекцией диапазона

**Обсуждение и итоги:**

1. **Live-пересчёт:** ✅ Фронт делает минимальный пересчёт при каждом изменении. Бэк только валидирует при сохранении.
2. **Фильтры черт:** ✅ Избыточные категории убрать.
3. **Редактирование в игре:** ✅ Любое изменение в игре требует одобрения ведущего. Вне игры — нет.
4. **Расширения:** ✅ «Инвентарь» = этап создания, редактируемый и в игре. «История» = имя, предыстория + хронологический лог. Учитывать при архитектуре.
5. **Отрицательные ОЛ:** ✅ Сгорают.
6. **Свободное создание:** ✅ Если лимиты пусты — готовность возможна. Черновик не снимается автоматически (кнопка «Готов»).

**Ключевое архитектурное решение — copy-on-write:**
При редактировании готового персонажа создаётся копия-черновик. Оригинал не трогается. Копия проходит проверку и подменяет оригинал. Этот же механизм для перехода между версиями правил.

## Этап 5: Скрытые проблемы

**Происхождение:** Проход по всей системе с целью выявления узких мест до начала реализации.

### Выявленные проблемы и решения

1. **Производительность запросов «на момент времени T»** — композитный индекс `(space_id, rule_id, created_at DESC)`, в перспективе таблица `current_rules` (materialized view).

2. **Наследование пространств — операция копирования** — асинхронно через очередь, UI с прогрессом.

3. **Циклические зависимости в характеристиках** — детектор циклов при сохранении формулы, ограничение глубины вычислений.

4. **Лавинная перепроверка персонажей при смене версии правил** — асинхронная очередь, по одному персонажу на задачу.

5. **Copy-on-write — уборка мусора** — периодическая чистка старых черновиков (>30 дней), переиспользование существующих.

6. **Эскалация привилегий** — запрет давать себе прав больше, чем есть. Разделение `manage_users` и `manage_groups`.

7. **Конкурентное создание персонажа в игре** — блокировка на уровне игры или optimistic locking.

8. **Миграции JSON-блоков** — каждый блок имеет `type` + `version`, рендерер обратно совместим.

9. **Архивация (задел)** — поле `archived` в модели БД на будущее.

10. **Тестирование** — модульные тесты DimensionalNumber, валидация, версионность, Requirement-система.

**Права на пользователей — переосмысление:**
- Изначально было монолитное `manage_users`. В ходе обсуждения разбили на отдельные ключи:
  - `view_users` — просмотр списка и чужих профилей
  - `view_sensitive_user_fields` — просмотр скрытых полей (email, группы)
  - `create_users` — создание
  - `edit_users` — редактирование
  - `deactivate_users` — деактивация (бан)
- 🟡 *Позже (итоги второй сессии) формат изменён на `объект.действие`: `user.view`, `user.view_sensitive`, `user.create`, `user.edit`, `user.deactivate`.*
- 🟡 *То же для групп: → `group.*`, игр: → `game.*`, пространств: → `space.*`.*
- То же для групп: `view_groups`, `create_groups`, `edit_groups`, `deactivate_groups` вместо `manage_groups`.

**Супер-админ:**
- Один при установке. Состоит в группе «Администраторы» (которая имеет все права).
- Нельзя: удалить супер-админа, снять с него группу «Администраторы».
- В группу «Администраторы» можно добавлять других пользователей.

**Деактивация пользователя:**
- Только с правом `deactivate_users`.
- Soft-delete — данные сохраняются, вход блокируется.
- Возможна временная (до даты) с причиной.

**Группы:**
- Изначально создаёт супер-админ. В будущем — с правом `create_groups`.
- Безопасность: нельзя дать группе прав больше, чем у создателя; нельзя отнять то, чего создатель не имеет.
- Группу можно деактивировать (перестаёт давать права, скрывается из UI).

**Права на объекты (игры/пространства):**
- Два механизма одновременно: группы назначаются на объект + индивидуальные назначения.

## Принятые решения в ходе доработок

### Этап I, тема 1: ORM + SmartTable + Миграции (19.07.2026)
✅ **Выбрана Doctrine ORM** (DataMapper). Отказ от своей ORM.

**SmartTable — концепция API:**
- Название: `SmartTable`
- Получение: `ServiceLocator::get('Core.SmartTable.Service.Container')->getSmartTables()`
- `->open('name')` — открыть существующую таблицу. **Не создаёт таблицу в БД.**
- `->create('name')` — создать новую таблицу. Полная цепочка: `→addField(...)→saveTable()`.
- Работа с таблицей: `$table->add([...])`, `->update($id, [...]), `->delete($id), `->getList([...])`.
- Транзакции: **локальные** — `$table->transaction(function($t) { ... })`. **Глобальные** (на несколько таблиц) — `$smartTables->beginTransaction()` / `->commit()` / `->rollback()`.
- Кэш: тегированный, `getList()` с параметром `cache: ['ttl'=>3600,'tags'=>[...]]`.
- События: методы `onBeforeAdd`, `onAfterAdd`, `onBeforeUpdate`, `onAfterUpdate`, `onBeforeDelete`, `onAfterDelete` в классе-описании таблицы.
- Identity Map: одна таблица — один объект в рамках запроса.
- Типы полей: `IntegerField`, `StringField`, `TextField`, `MultipleField`, кастомные поля через `UserTypeField`.
- Динамические таблицы (без класса): мета-описание хранится в служебных таблицах `smart_tables`, `smart_table_fields`.
- Статические таблицы (с классом-описанием): `extends SmartTableDefinition`, поля в `getMap()`.

**Миграции:**
- Движок: DoctrineMigrations.
- Поверх — своя админ-страница (список, накат, откат).
- Сортировка по времени, имя = дата + описание.

### Этап V, тема 24: Формула урона (19.07.2026)
✅ Атака = оружие + профиль атаки (урон, пробитие, тип урона, точность). Формула: (Урон − Сопротивление) × РУ для каждого типа урона, затем суммируется. Пробитие уменьшает сопротивление до 0. Особые правила для некоторых типов урона (лимит РУ, коэффициент).

### Этап I, тема 2: Архитектура проекта (19.07.2026)

**Название core-директории:** `engine` (не ядро).

**Структура модулей (PHP):**
```
engine/modules/
  Core/Kernel/            — точка входа, загрузчик модулей
  Core/SmartTable/        — ORM-обёртка
  Core/Auth/              — аутентификация (содержит Session)
  Core/User/              — пользователи
  Characters/Character/   — персонажи (группа Characters)
  Games/Game/             — игры (группа Games)
  Spaces/Space/           — пространства (группа Spaces)
  Spaces/Rule/            — правила
  Spaces/Tag/             — теги
  Chats/Chat/             — группа чатов
  Notifications/          — уведомления
```
Принципы:
- Core — никаких зависимостей наружу.
- Внутри группы — зависимости допустимы без фанатизма.
- Между группами — только через Core (крайне редко).
- Модули — маленькие, за свою часть.

**Фронтенд:** ✅ **Shell + модули**
- Shell — оболочка (топбар, сайдбар, роутер, сквозные сервисы).
- Каждый модуль регистрирует свои роуты, компоненты, store через Shell API.
- Сборка: Vite + glob-imports.
- Модули могут распространяться как npm-пакеты.
- Auth — часть Shell'а (обязательная зависимость).

**Git-регламент:** ✅ Git Flow.
- `main` — продакшен (только код, без ТЗ/макетов).
- `develop` — разработка (код + ТЗ/макеты).
- `feature/*`, `release/*`, `hotfix/*` — по стандарту.
- Механизм фильтрации ТЗ при слиянии в main — уточняется (CI / gitattributes).

**Code-style:**
- PHP: ✅ PSR-12 + PHP CS Fixer. Свой конфиг (адаптировать из рабочего проекта, добавить правила: пробел после каста `(int) $a`, многострочные массивы с запятой в конце, `[]` вместо `array()`).
- JS/TS: ✅ TypeScript.
- Фронт-линтеры: ✅ ESLint (логика) + Prettier (формат). Pre-commit hook для PHP + TS.
