## Маппинг — зафиксированные решения (05-11; ввод-2026-08-07)

### 1. Характеристики
- **Выносливость не трогаем: считаем `Стойкость = Выносливость`.** В доклада была попытка разделить Стойкость на «Стойкость (к урону)» и «Выносливость (долгие нагрузки)»; разделение не оправдалась — игнорируем. ВСЕ «Выносливость» транскодируем в «Стойкость».
- **Восприятие = min(Внимательность, Реакция)** (в модели уже производная).
- **Интеллект = min(Память, Мышление)** (в модели уже производная).
- Бонус «+N к производной» (Интеллекту/Восприятию и др.) означает **+N к её базе**, т.е. к обеим её производным-кым основам. См. «Модификаторы характеристик» ниже.

### 2. Модификаторы характеристик (гранты)
- `characteristic_modify` на **производную** характеристику (Интеллект/Восприятие) должен по факту ставить модификатор **на базу/компоненты производной** (Память и Мышление → для Интеллекта; Внимание и Реакцию → для Восприятия), а не на саму производную. Это правило кодируется на уровне грамата/расчёта (уточнить на шаге конкретной фазы).

### 3. Шкалы-выборы (Зрение / Слух / Внешность / Умственные)
- У таких черт разные «уровни»-ступени; у каждой ступени своя цена (отрицательная = даёт ОС) и свой дар.
- Модель обязана это выражать: зона с `levels_cost` (может содержать отрицательные значения) + `grants[level]` на ступень + запрет совмещения нескольких ступеней одной группы.
- Является ли текущая модель достаточной — проверить на шаге S1/S3 (см. план).

### 4. Прогрессивная доплата (Общие черты)
- «3-я и каждая последующая черта из Общих черт → доплата +2 ОС». **Берём.** Механику обсуждаем детально на своём шаге (S3).

### 8. Группировка способностей (S1)
- **Признак = keyword**. «Общий» и т.п. — признак (keyword) способности; признаков пока плохо прописаны в источнике, но модель — теги-кейворды.
- **Группа = отдельное группирующее правило (type `group`)** — у неё есть имя, описание, признак «Группа» и лимит выбора (`selectLimit`) в спеке. Участники ссылаются на группу через `group_code` в спеке и несут признак «Часть группы»:
  - `selectLimit: 1` → «1 из группы» (one_of, при взятии снимаются остальные);
  - `selectLimit: N>1` → «не более N из группы» (добавление сверх лимита отклоняется);
  - `selectLimit: -1` → лимит отключен.
- **Итоговое решение (S7, 2026-08-07):** группа как правило-контейнер (а не `group {groupCode, selectLimit}` на участнике) — у группы есть имя/описание, участники отображаются строго внутри группы в редакторе персонажа.

### 9. Источники модификаторов (S1)
- «от Телосложения/тела» → source **body/innate**.
- «от гибкости»/«от элластичности» → **«от совершенства»** (source `perfect`/`совершенство`).
- «от усиления» → source `enhancement`.
- «от перегрузки» → source `overload`.
- «от врождённой черты» → `innate`; «от тренировок» → `training` (есть).
- «от развития» (монстр), «от характера», «от особенности» (ОЛ) — добавим по мере фаз 4–5 (в Фазе 1 не нужны, кроме развития→`development` для черт монстра, которые отложены).

### 10. Слух/Зрение/Внешность (S1)
- **Внешность** модифицирует **Общение** (с условием).
- **Слух и Зрение** модифицируют **Внимательность** (с условием).
- **Восприятие = min(Внимательность, Реакция) — не меняем.** Открыт вопрос про саму Внимательность и чувства (см. Дискуссия 1).

### 11. Параметрические значения «X» (S1)
- **X = стоимость**, и она должна быть **числом, используемым и в дарах, и в описании** (и вообще в спечке способности; в заклинаниях параметров много и «всюду»). Механизм параметров — отдельная дискуссия (см. ниже), не решаем в S1.
- Примеры: Энергохранилище X, «Простейшее заклинание» X, Сопротивление магии x (2x), «размер» и т.п.

### 12. Сопротивления (S1)
- `ResistanceSlot { damage_type_code, value, durability, source_code }` сейчас есть на `ArmorBlock`/`BlockProfile` предметов. **Способность должна уметь даровать сопротивление** → Grant `{ type:'resistance', damage_type_code, value, source_code }` (durability нет). Решено в Дискуссии 3.
- Примеры докла: «20 сопротивления отравлению 1 типа от тела», «Стойкость к электричеству +12», «Сопротивление магии x».

### 5. Требования (Requirement)
- Покрывают «Требуется Магия 4↓» (`characteristic_value`), «Требуется Ядро монстра» (`has_ability`), «Требуется Пасть хищника» (`has_ability`).
- ~~`spent_on_category` («потрачено N ОС на категорию»)~~ — **отпал**: черты «Слабая/Сильная выносливость», которые его требовали, исключены из выгрузки (2026-08-07).

### 6. Кардинальность группы
- «можно иметь только одну черту группы X» (Слух/Зрение/Внешность/Умственные; ОЛ: Общение/Богатство). Кандидат: ограничение «макс 1 из группы признаков» (обсуждаем на S3/S11).

### 7. Тело-части
- «приобретение только если больше одной руки» — модель тел (рук) отсутствует; **откладываем** (не в этом навыке).

## Что текущая реализация УЖЕ поддерживает (модель Ability/расы)

- Типы способностей: `trait / feature / skill / action / process / spell`.
- Зоны цен по очкам `os/ol/or`: `array` (в т.ч. отрицательные), `progression`, `automatic`.
- Требования: `has_ability`, `has_ability_keyword`, `has_tag`, `characteristic_value`, `resource_limit`, `and`/`or`.
- Дары: `characteristic`, `characteristic_modify(source)`, `resource`, `resource_limit_change`, `ability`, `keyword`, `item`, `resistance` (см. №12, S3).
- Профиль основы: `cost_os` (в т.ч. отрицательный), характеристики `fixed`/`purchased` (лестница `[{cost, value}]`), способности `{ability_code, automatic}`.
- Размерные числа (база 3−5, размерность), источник-модификаторы (`source`).
- Параметры «X»: блок `parameters: AbilityParameter[]` на способности, цена зоны `{kind:'parameter', parameter_code, per_unit}`, значение на инстансе `CharacterAbility.parameters` (Дискуссия 2, S3).
- Группы-шкалы: группирующее правило `{type:'group', selectLimit}` + `group_code` на участнике, кардинальность при покупке (№8, S7).
- Механики: глобальный реестр `Mechanic {id, code, version, name, description}`; правило несёт `mechanicId`+`mechanic_payload`; реестр хендлеров `code@version` со scope; диспетчер по step; хендлер `purchase_surcharge` (Дискуссия 4, S3).
- Возраст (S11): тип правила `age` (`Age {name, ol, featureLimit, effects}`), у вида/расы `age_years {age, ageStart, ageEnd}`; ОЛ этапа «Личность» = ступень; эффекты — модификаторы «от возраста» (условные — scope). Данные: `docs/rule/age/`.
- Деньги (S11): грант `money {fixed, percent, apply max/min}` — эффективный стартовый капитал = apply(фикс, % от лимита денег игры); признак «Богатство» — вне лимита числа особенностей, взятие только при создании.

## Фаза 1 · S1 — Инвентарь ОС-черт (чек-лист)

Анализ из `AI.html`, §«Уникальные черты / Простейшие заклинания / Черты монстра / Общие черты / Черты вида» (относим целевой этап «Основа» — зона `os`).
Соглашения:
- **Цена**: числом ОС; «получаете N ОС» → отрицательная (даёт ОС в бюджет). Тип черты `trait`, если не указано иное.
- **Дар** = гранты карты уровней (уровень 1); «текст» = невыразимо дарами, идёт в описание.
- **Группа** = отдельное группирующее правило (type `group`, признак «Группа») с лимитом выбора; участники — признак «Часть группы» + `group_code` (см. №8; финально в S7).
- **Источники модификаторов**: в доке масса «от …» (телосложение/тело, гибкость, элластичность, врождённая черта, усиление, перегрузка, сторонний источник, тренировка, развитие, характер, особенность). В моках есть `source`: armor/shield/spell/training/innate/underarmor. Решение по источникам — S3 (вероятно добавить `body`/`innate`, `enhancement`, `overload`, `side_source`, `character`, `feature`, `development` или переиспользовать).

### Модельные заметки S1 (для S3)

1. **Шкалы-выборы ≠ уровни зон.** Наши зоны `array` дают накоптельную цену (уровень N платит ур.1..N). Ступени Слух/Зрение/Внешность/Умственные — **взаимоисключающие альтернативы** (возвраза: заплатил только эту ступ./получил её дар), а не накопление. => моделировать **отдельными способностями + «макс 1 из группы»** (кардинальность группы), а НЕ одним ability с levels. Проверить на S3. Это расходится с технико-репликой «уровни» — вынести на согласование.

### Дискуссия 1 — Внимательность и чувства (решена — В-2)
**Закрыто:** `Восприятие = min(Внимательность, Реакция)` — корректно, **не меняем**.
По Внимательности/чувствам выбран **вариант В-2** (подтверждён юзером):
- **Чувство = тип правила `sense`** (не характеристика — юзер отклонил «характеристику-чувство»: переиспользование механики характеристик не даёт смысла, т.к. у чувства нет лестницы/размерного значения). Ссылка по `code`.
- Инстанс чувства на персонаже **не хранит размерное значение**, а несёт:
  - `value` — **модификатор к Внимательности** (число, бонус/штраф, напр. −9..+6);
  - `type` — статус: `точное / неточное / смутное / отсутствует`;
  - `radius` — дальность (`{ value, type }`, для Вкуса/Осязания `value 0`);
  - `modificators: [{ value, source_code }]` — **массив модификаторов с источниками** (как у характеристик; пример: `Зрение.modify(2, sourceId)` → `value 2`, мод `{2, sourceId}` добавлен в список).
- Проверка чувства = `Внимательность + value(чувство)`; статус `отсутствует` → нельзя использовать.
- **Влияние на Восприятие**: мод чувства — модификатор к Внимательности; по ранее подтверждённому (Дискуссия 1) он участвует в Восприятии через `min` (зафиксировано; не меняли).
- **Слепота/Глухота** = статус `отсутствует` у соответствующего чувства (грант `sense { sense_code, status }`).
- у человека чувство по умолчанию (док):
  - **Зрение** — `точное` (точно положение цели);
  - **Слух** — `неточное` (квадрат местонахождения);
  - **Обоняние** — `смутное` (наличие/отсутствие);
  - **Вкус** — `дальность 0` (что коснулся);
  - **Осязание** — `дальность 0` (контакт);
  - дальность Вкуса/Осязания `0`, у Зрение/Слух/Обоняния — натуральная (уточняется тестом/фазой).
- реализация: на S2 черты Зрение/Слух временно пишем с таргетом «Внимательность», доводим до «Внимательность(чувство)» в Фазе 3; сами правила-чувства заводим на шаге «типы правил» (S3).
> **Реализовано (2026-08-08):** чувство = тип правила `sense` + грант `sense_modify { sense_code, amount, source_code }` (черты Слуха/Зрения дают модификатор чувству от источника «Совершенство»). Инстанс `CharacterSenseValue { ruleId, value, modifiers }` (в модели редактора и `CharacterVersion.senses`). **Значение чувства** агрегируется по общему правилу источников (у одного источника макс+/макс−), чувство без грантов = 0 (нормальное). **Внимательность** получает **максимум среди чувств** как модификатор «от {чувство}» (роль «от чувства»); модификатор применяется размерно `modify(delta, CHARACTERISTIC_BASE_RANGE)` — «Невероятное зрение» +6 на базе 3 → `{3|2}`, а не линейное 9. Статусы (`точное/неточное/…/отсутствует`) и радиус — отложены (только `value`).

### Дискуссия 2 — Параметрические значения (решён каркас)
Два вида параметров:
1. **При покупке (per-character)**: значение выбирает игрок при покупке способности; хранится на инстансе в `build.abilities`.
2. **При активации**: выбирается при активации — активацию НЕ делаем и скоро не будем; параметры активации фиксируем в спека, но не используем до появления активации.
> Типично: заклинание несёт и «сложность сотворения», и «X урона электричеством» → несколько параметров разных видов в одной способности.
**Пределы у параметров: возможны (min/max).**
**Значение параметра — не только обычное число, но и размерное (DimensionalNumber)**: особенно для `activation` это нужно. `default/min/max` тогда выражения, а не примитивы.
**Критерий:** не переделывать 10×; минимизировать переработки → единый механизм (подстановка `{code}` в цене/дарах/описании/спецках, резолв по типу параметра), чтобы заявки потом не ломали контракт. Черновик: `docs/specs/ability-parameters.md`.
> **Покупка (S8, 2026-08-07):** раса задаёт у способности **потолок «X»** (`RaceAbilityRef.parameters`, для `automatic` — значение, с которым даётся); в редакторе способность ограничена `min(макс спеки, потолок расы)` и берётся степпером (цена `per_unit × X`). Автоматические расовые способности применяют дары (уровень 1). Масштабирование даров по X — через **формулу `{type:'parameter', parameter_code, per_unit}`**: `Grant.resistance.value` = `DimensionalNumberValue | Formula`, резолв в `forEachActiveGrant` (для «Сопротивления магии X» = `per_unit × X`).
> **Докупка сверх авто (2026-08-08):** у расы могут быть **две ref-записи одной способности** — `automatic` (бесплатное значение, напр. Аэрон «Сопротивление магии 2») и доступная с более высоким потолком (до 5). Механика: автоматическое значение собирается отдельно (`racialAutomaticValues`) и попадает в `EditorAbilityParameter.freeValue`; стоимость докупки = `per_unit × (X − авто)` (`parameterCostValue`); автоматический грант применяется только если способности нет в `build.abilities` (иначе задвоение при докупке). `cappedByRace` = «потолок расы задан» → имя «до N» показывается всегда при заданных `parameters` (даже если потолок = максимуму спеки, напр. «Магия до 5»). Данные всех рас приведены к доке (`mockRaceImport`).

### Дискуссия 4 — «Прогрессивная доплата +2 ОС» как механика (решена)
Из дока (§Общие черты): «…чтобы приобрести третью или любую последующую черту **из этого раздела**, необходимо доплатить 2ОС». Это **правило-механика**, не «доплата за уровень одной способности»:
- **Общее правило**: на этапе «Основа (os)» третья и каждая последующая черта **с признаком «Общая»** доплачивает +2 ОС.
- **Зверолюди**: то же ограничение, но распространяется на **их расовые приобретаемые черты**, а не на общие (расовый вариант; фильтр — свой признак/`race_code`).

**Согласованная модель механик (каркас):**
1. **Реестр механик — глобальный справочник** `Mechanic { id, code, version, name, description }`; разные версии одного кода = разные строки. В правиле выбираем нужную версию (по `mechanicId`), а не вводим `code+version` руками.
2. **Правило** несёт `mechanicId` + `mechanic_payload` (контекст инстанции: `{ filter, free_count, surcharge }`). «Механики ревизии» = объединение `mechanicId` её правил; привязки «ревизия→механики» нет.
3. **Реестр хендлеров**: `code@version` → класс. **Scope — свойство хендлера** (для нашей механики `'character.edit.osSteps'`), индекс `Map<step, Handler[]>`.
4. **Контракт хендлера — чистая функция**: `run({ payload, state }) → { effects, ui }`, где `state` — **read-only снимок** (build+rules+текущая модель), передаётся **по ссылке, одна на проход**, без копий. Механика **не мутирует** стор: в редакторе стора для расчёта нет (immutable `build` → чистая `build()`), мутации физически некуда применять. Эффекты применяет модуль (редактор сворачивает в `os.spent`, game — к своему состоянию).
5. **UI-канал**: `effects` для расчёта, `ui` (аннотации) для интерфейса — карточка показывает доплату, бюджет — разбивку с причиной; без хардкода текста в UI.
6. Обе инстанции («Общая», «Зверолюди») = **две data-строки** одного хендлера `purchase_surcharge` (разные `payload.filter`).
7. **Две категории механик**: **пассивные** (правят бюджет/валидацию на пересборе шага — наша доплата) и **активные** (дайс-роллер «получает значения → отдаёт результат», эффекты действий; вызываются **по месту использования**, на пересборе не участвуют).
8. **Бэкенд при сохранении обязан пересчитать те же механики** теми же хендлерами (версия-aware), НЕ хранить результат как отдельное хранимое число — доплата производная от выборов (ТР §7: бэк валидирует). Юзер согласен.
9. **Фильтр доплаты — по признаку = keyword**: для «Общей» нужен keyword **«общая»** у черт (признак способности); для зверолей — свой keyword/`race_code`. (Юзер: признак нужен.)

### Дискуссия 3 — Сопротивления (решена)
- **durability НЕТ** у сопротивления, даруемого способностью. Grant: `{ type: 'resistance', damage_type_code, value, source_code }`, где `value` — **размерное число** (DimensionalNumberValue), подтверждено юзером (с S8 может быть и формулой параметра `{type:'parameter', per_unit}` — «Сопротивление магии X» = `per_unit × X`).
- **«Сопротивление магии X»** = сопротивление против **конкретного типа урона** (+ спец-правило: увеличивает сложность проверок сотворения волшебства по цели на X; при оговорённом X — на X средних). Модель: тип урона «магия» + resistance к нему; спец-правило для волшебства фиксируем/отмечаем отдельно.
> **Решение:** спец-правило «сложность сотворения по цели +X» храним как **описание** (другой механики DC сейчас нет), а Grant `{ type:'resistance', damage_type_code:'magic', value }` несёт размерное число. Если появится модель DC — вынесем.
